# VI. Поведение, управление, звук и сеть

Шестой том описывает подсистемы, которые превращают загруженный мир в
реагирующую игру: AI, Behavior, Wizard, Control, ввод, камеру, звук и сеть.
Эти области нельзя восстанавливать только по структуре файлов. Для них важны
порядок кадра, ownership объектов, timing событий и доказуемые границы между
решением, движением, presentation и транспортом.

Ключевой принцип: reader compatibility не равна gameplay compatibility.
Корректно разобранный ресурс ещё не доказывает, что runtime выбирает ту же
цель, строит тот же маршрут, применяет ту же collision correction, создаёт тот
же sound event или отправляет тот же network payload. Поэтому все утверждения
ниже разделяют подтверждённую структуру, восстановленный архитектурный
контракт и открытые участки, требующие динамической трассировки.

```text
AI / mission script
  -> стратегическая цель, условия, команды миссии
Behavior
  -> состояние объекта, target, global/local path
Wizard
  -> локальная коррекция траектории
Control
  -> physical step, collision proxy, итоговый transform
World3D
  -> очередь событий, ownership, deferred deletion
Render / Sound / Net
  -> представление, listener, mirrors и сообщения
```

Связанные главы: [мир и миссии](04-world.md), [геометрия и рендер](05-render.md)
и справочный [render frame](../reference/render-frame.md).

## AI, Behavior и Wizard

Iron3D разделяет стратегическое принятие решений, поведение конкретного объекта
и локальную коррекцию движения. Это разделение должно сохраниться в новой
реализации: стратегический AI не меняет transform напрямую, а collision manager
не выбирает игровую цель.

```text
ai.dll / SuperAI
  -> цель клана, миссии и группы
Behavior.dll
  -> состояние юнита, target, global path, local corridor
Wizard.dll
  -> ближайшая допустимая траектория
Control.dll
  -> физическое движение и столкновения
```

### Behavior

`CreateBehaviour` создаёт controller для отдельного игрового объекта.
`CreateDistributor` восстановлен по consumers как посредник распределения
команд или ресурсов; это высокоуверенный архитектурный вывод, а не доказанное
имя внутреннего класса. Behavior получает `IArealMap` через AI/клановый
контекст, ведёт radar/target state, строит global path, превращает его в local
corridor и передаёт движение Wizard.

Ошибочные состояния проверяются явно:

1. отсутствует system map;
2. отсутствует terrain interface;
3. active behavior не имеет `IArealMap`;
4. объект попал в non-reachable area;
5. объект пытается выйти из non-walkable area;
6. path generator вошёл в infinite cycle.

Эти случаи являются fatal или diagnostic conditions. Совместимая реализация не
должна тихо исправлять их teleport-ом, потому что такое исправление скрывает
ошибку areal graph, terrain query или state machine.

### Параметры Behavior.ini

Подтверждены настройки:

```text
PathFind_BuildingHitDist
PathFind_BuildingNearestDist
PathFind_NearBuildSpeedPercent
PathFind_CorridorRadius
PathFind_NearDoorCoeff
PathFind_fStepOffBuilding
PathFind_MaxAccel
PathFind_MaxRotation
PathFind_fStepDist
PathFind_MinPointInTrajectory
Network_ResourceTransferMaxDelay
```

Они задают геометрию corridor, дистанции реакции на здания, снижение скорости
возле препятствий, пределы ускорения и поворота, дискретизацию trajectory и
сетевой timeout передачи ресурсов. Значения читаются как runtime-конфигурация,
а не компилируются в код. Parser должен поддерживать комментарии `//`, пробелы
вокруг `=` и CRLF.

Файл также содержит logging/debug switches: `Behavior.log`, уровни ошибок,
show vectors и z-buffer debug. Эти переключатели полезны не только для
совместимости, но и как модель современных trace flags.

### Wizard

Wizard получает желаемое направление и corridor, анализирует ближайшие
ограничения и выдаёт скорректированную локальную траекторию. Behavior может
очищать её через `ClearWizardPath` при смене цели, повреждении global path или
переходе объекта в неактивное состояние.

Нужно различать четыре уровня движения:

- **global path** -- последовательность areals;
- **local path** -- точки или сегменты внутри corridor;
- **wizard path** -- краткосрочное движение с учётом ближайших препятствий;
- **physical step** -- фактически разрешённое Control перемещение.

Хранение всего маршрута одним массивом лишает систему возможности локально
обойти препятствие без полного повторного поиска. Граница Behavior/Wizard
существует именно для того, чтобы краткосрочная геометрическая коррекция не
ломала стратегический path state.

### SuperAI и миссионные сценарии

`CreateSuperAI` создаёт центральный controller клана; `GetSuperAI` возвращает
его. AI загружает файлы из `MISSIONS\SCRIPTS\`, проверяет версию и пишет ошибки
в `ai.log`. Несовпадение версии является отдельной ошибкой, а не неизвестной
командой.

Сценарный корпус содержит binary `.scr`, formula exports `.fml`, таблицу
переменных `varset.var` и `.trf`-данные. `.scr` хранит именованные секции и
события, например `Init`, `Mission`, `Problems0`, `Fort_Task_Complete` и
`Hero_Teleported`, вместе с числовыми ссылками на compiled instructions.
`.fml` является текстовым экспортом formula set. `varset.var` декларативно
описывает типы, defaults, ranges и строки через макросоподобные формы
`VAR(...)` и `STRING(...)`.

Compiled package больше не opaque blob: `fparkan-script` losslessly читает
проверенный внешний framing. Сначала идут `opcode_handler_count` и
`event_count` (`u32 LE`), затем именованные события с NUL-terminated raw
именем и nested records. Reader сохраняет все seven raw header words и
references каждого record, жёстко ограничивает counts/allocations и отдельно
сохраняет trailing bytes. На `c1m2p.scr` GOG reader получает `73` handlers,
`9` events, `17` records и `20` references без trailing bytes. Это структура
файла, но не таблица семантик: названия opcode/words появятся только после
handler contracts и runtime traces.

Связь первого header word с dispatch доказана статически: `ai.dll`
создаёт 73 handler pointers в известном порядке и копирует table без
перестановки. По всем 58 GOG packages первый word — индекс `0..72` либо
`0xffff_ffff` sentinel; `fparkan-script` отражает это как typed
`ScriptDispatchSelector`, сохраняя неожиданные значения `Unknown`. Первый
handler лишь инициирует execution context (`+0x50 = 1`); его gameplay meaning
пока не назван.

Когда в `.scr` есть событие `Init`, сценарная машина ищет его имя как C-строку:
сравнение учитывает регистр, останавливается на первом NUL, а среди повторов
выбирает первое событие. В проверенном AutoDemo это событие содержит один
`Handler(19)`. Он записывает в переменные клана координаты его основания и номер
клана:

```text
первый Init -> действия по порядку -> ClanBaseX, ClanBaseY, ClanID
```

На пути к этим переменным координаты сначала округляются оригиналом до ближайшего
целого с правилом ties-to-even, затем сохраняется младшее 32-битное слово.
Например, `-0.6` даёт `0xffffffff`. AI хранит это слово как `float`, поэтому
`0xffffffff` становится `2^32`; `Handler(19)` усекает значение и снова берёт
младшие 32 бита, что даёт `0`. Значение `10001` также проходит дальше: оригинал
показывает предупреждение для чисел выше `10000`, но не отменяет создание AI.

Rust исполняет подтверждённый поднабор первого `Init`: действие `Handler(19)`
и формулы из одного атома либо двух атомов с бинарным `+` или `-`. Здесь атом —
число или имя переменной. Поддержанные шаги сразу обновляют временную копию
varset, поэтому следующая формула читает уже записанные значения. К состоянию
клана записи попадают лишь после успешного прохода всего первого `Init`.
Если встретилась неподдержанная форма, preview сохраняет пакет, сообщает
`Unsupported` и оставляет значения по умолчанию; при полной загрузке та же форма
становится ошибкой. Это политика Rust для ограниченного исполнителя, а не правило
оригинального обработчика. Отсутствующее событие не создаёт записей; пустое
событие считается исполненным без записей. Остальные события пока не образуют
исполняемую VM.

В `Init` встречаются и отдельные присваивания результатов формул. Их запись
выбирает строку формулы по порядковому номеру из соседнего `.fml`; этот файл
относится к конкретной базе сценария, а строки после нужного номера сохраняют свои позиции.
Для первой кампанийной миссии `Mission.01` (`tut1_pl2.fml`) строка 0 записывает
нули в `df0..df3`; в миссии `Single.01` (`scr_pl_1.fml`) строка 0 записывает
нули в `dT8` и `dT9`.
Клан 1 той же миссии использует первые девять строк `scream.fml`: восемь
проверенных значений попадают в `DWORD` с усечением дробной части, а `0.8`
сохраняется как число `float`. Например, если `source` равен `10`, выражение
`source + 2.0` записывает `12`; следующее `target - source` читает новое значение
`target` и получает `2`. Каждая операция работает с `f32`: значение ячейки
`DWORD` сначала читается как беззнаковое число и переводится в `f32`, а результат
сохраняет тип целевой ячейки. Поддерживаются только один или два атома и один
бинарный `+` либо `-`; произвольная грамматика формул и остальная VM не
восстановлены. В отдельной точечной проверке вычисления и записи оригинальной
DLL и Rust совпали для 13 выбранных формул. Эта сверка проверяет только
эти значения и не запускает исходную миссию. Тест полной загрузки подтверждает,
что `Mission.01` проходит этот `Init`; у `Single.01` следующий неподдержанный
`Handler(43)` встречается в clan 1, записи 10. Никакое значение не подставляется
вместо этого действия.

### Пополнение кланов в AutoDemo

В карте AutoDemo расставлено по два боевых робота на клан. При запуске
демонстрации ведущий код читает `MinBotsNum` из `mission.cfg`. Здесь минимум
равен трём. За один проход каждый клан с заводом и числом боевых роботов
ниже минимума получает одного робота из общего каталога
`units/units/autodemo`. Очередь схем общая для кланов и после последней
схемы начинается сначала. Созданный робот появляется на рельефе с
прибавкой высоты 2 единицы в случайной точке на окружности вокруг завода.
Демонстрация вызывает создание напрямую. Производственный заказ завода
идёт другим путём.

В GOG `iron3d.dll` (SHA-256
`d1dc4ea8535e2069b0a05c9e8be2724dd438ba44cca7a83007d8b2e50f9e35fa`)
RVA `0x2c560` загружает каталог, `0x2c9c0` пополняет кланы, а
`0x77970` создаёт юнит из Unit DAT. В первой выборке мира оригинала уже
есть по три робота. FParkan готовит модели и регистрирует первые два
пополнения при загрузке, чтобы они были в мире и на экране с первого
кадра. Во время демонстрации проверка повторяется после боевого шага.
Когда клан теряет робота, следующий юнит из общего каталога появляется
у его завода и получает начальные оружие, запас прочности и патруль.
Случайные точки пока приближены. Рендер заранее готовит модели каталога
и повторно использует освободившиеся места. В мире каждое подкрепление
получает новый handle, поэтому попадание или камера со старым handle
не обращаются к новому роботу.

### Патруль AutoDemo

Журнал запущенного оригинала показывает, что оба клана получают один и тот
же участок патруля. Параметр приказа `PatrolPlace` задаёт полуразмер области.
При значении 150 каждая координата точки выбирается отдельно в пределах
±150 от центра. Поэтому область выбора точек квадратная, хотя в журнале
параметр назван `Radius`. В GOG `Behavior.dll` (SHA-256
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`)
приказ принимает RVA `0x2d520`, точки выбирает RVA `0x2dd90`.

В FParkan координаты центра берутся из округлённого якоря первого клана.
Патруль точки хранит циклический список из 15–19 случайных целей. Отдельный
генератор из двух 16-битных слов выбирает длину списка, а CRT-генератор
Behavior — обе координаты каждой цели. Он общий с ресурсными и рабочими
таймерами Behavior: патруль меняет положение этого потока RNG, а не получает
собственную последовательность случайных чисел.

RVA `0x2dd90` сначала проверяет отступ 100 единиц от границы карты, затем
для наземной машины — допустимость области. На одну цель допускается 350
попыток; после их исчерпания сохраняется последний кандидат. Список
обходится по кругу до обновления: стандартные 20 секунд и случайная добавка
до 10 секунд проходят через тот же таймер с шагом 64 мс. Равенство сроку не
считается просрочкой. Начальный запуск и обновление находятся по RVA
`0x2d7c0` и `0x2dbf1`; переход к следующей цели по модулю длины списка —
по RVA `0x2dcdf`. Координаты, состояния обоих RNG и следующий срок проверены
вызовом DLL; отдельный вектор воспроизводит список из работающего AutoDemo.

Скорость в приказе — доля возможностей машины. Для `PatrolPlace` стандартный
коэффициент равен 0,8: RVA `0x2dc57` умножает его на текущий предел хода
из `Actor+0x5fc`. Например, предел 20 задаёт скорость 16, а нулевой предел
оставляет машину неподвижной. Это запрошенная скорость, а не обещание
мгновенно пройти такое расстояние: разгон и поворот выполняет контроллер
движения.

Предел берётся из слова 7 изменяемого профиля Control. В той же сборке
Behavior RVA `0x1bbe0` запрашивает селектор `0x12` интерфейса Control и
копирует это слово в свойства движения; селектор `0x11` возвращает исходный
профиль. Различие подтверждено вызовом DLL с разными значениями полей.
В работающем оригинале предел с битами `0x416b55d8` и коэффициент 0,8 дали
запрос `0x413c44ad`. FParkan использует изменяемый профиль для свободного
патруля точки и пересчитывает его после изменения узлов на ресурсном такте.
Бюджет движущейся машины и смена активности владельца ещё открыты.
Отчёт сохраняет число запросов и последнее значение
для каждой машины; при отсутствии профиля явно считает подмену скоростью 9.

Сценарный Go берёт тот же текущий предел, но умножает его на
`Go_SpeedPercent` из профиля Behavior. Стандартное значение равно `1`:
машина с пределом 20 запрашивает 20. При следующем запросе уменьшившийся после
повреждения предел даст меньшую скорость. Нулевой предел или коэффициент дают
нулевой запрос.
Декодер профиля применяет второй блок значения первой одноимённой записи;
при отсутствии поля сохраняет нативное значение по умолчанию. В штатных
классовых профилях `behpsp.res` это поле отсутствует.

В GOG `Behavior.dll` ([сборка](../reference/original-binaries.md)) значение
по умолчанию задаёт RVA `0x16250`, привязку `Go_SpeedPercent` — `0x16480`.
Умножение исполняется при старте Go (RVA `0x2b595`) и повторной передаче цели
(RVA `0x2b932`). Вызов обеих нативных ветвей с игровым x87 `0x007f` подтвердил
значения запроса, в том числе нулевые. Измерение завершается перед MWalker:
физическое движение и хронология миссии этим не подтверждаются.

FParkan использует профильный запрос вместо постоянной скорости 9 для Go.
`go_speed_profile_approx` сохраняет предел, коэффициент и запрос по объекту;
`go_speed_stub` считает отсутствие необходимых данных и явную подмену 9.
После выпуска машины её профиль Behavior привязывается к новому полному
handle, включая поколение, и остаётся доступным для следующих приказов.
Временный контроллер подставляет этот запрос на каждом шаге движения;
нативное удержание запроса MWalker между передачами цели ещё открыто.

Патруль ищет путь к цели по связям областей `Land.map`. При пересечении
строения или машины общий контроллер прокладывает обход. Наземная машина
опирается на нижние точки корпуса, а шасси с `CanFly` набирает высоту и держит её
над низиной. Проверку проходимости наземной области пока заменяет наличие
области.
Начальные состояния генераторов и общий порядок обновления владельцев ещё не восстановлены.
Отчёт считает списки, цели и такие проверки по ID машин и сохраняет счётчики
после уничтожения машины. Разгон, правила разворота и выбор воздушного
маршрута остаются приближёнными.

### Бой роботов в AutoDemo

Патруль может уступить место задаче атаки. В журнале оригинала после
`Attak … interrupt` появляется выбор цели по её логическому ID.
В той же сборке `Behavior.dll` RVA `0x34510` создаёт задачу атаки,
а RVA `0x25320` передаёт орудию команды наведения и пуска.
В начальных параметрах родной Behavior дальность поиска на патруле
равна 400, а предельная дальность огня — 200 единиц (RVA `0x16250`).

FParkan выбирает ближайшего живого противника среди роботов в пределах
поиска. На патруле по месту новая цель должна попасть в круг исходного
радиуса патруля. В `Behavior.dll` эту проверку делает RVA `0x2d4a1`.
Уже начатая атака может продолжаться за этим кругом. При переходе к атаке
RVA `0x2d250` передаёт предел `радиус + 60`, а код по RVA `0x16cf`
прерывает задачу, когда сам робот выходит за предел. В журнале оригинала
патруль с радиусом 150 передаёт предел 210 и возвращается к патрулю после
его истечения. Эти правила применяются к патрулю по месту. При явном
приказе атаковать объект зона патруля отсутствует.

Робот меняет маршрут, а на дистанции огня поворачивается к цели.
Если между корпусами нет рельефа, орудия отрабатывают цикл своих записей
Control. Снаряд использует скорость, время жизни и геометрию своего
ресурса. Попадание расходует объём цели, и при его исчерпании робот
исчезает из мира и окна. Формула урона пока та же приближённая, что у
оружия героя. После потери цели робот снова ищет противника или патрулирует.

### Заряд орудия и питание робота

Орудие хранит число патронов и отдельный запас заряда. Ёмкость и цена выстрела
берутся из коэффициентов Control с индексами 1 и 2. При чтении профиля заряд
заполняется до ёмкости. Если ёмкость положительна, новый цикл ждёт, пока
заряда хватит на выстрел; равенство разрешает пуск. Списание происходит при
завершении цикла вместе с патроном. Ёмкость не больше нуля отключает только
это ограничение, сохраняя обычный учёт патронов.

Ресурсный бюджет восполняет заряд из питания владельца. Орудие запрашивает
недостающий запас даже в выключенном состоянии. Включённое устройство
дополнительно оплачивает свою текущую ставку потребления. Например, при
ёмкости 10, заряде 3, ставке 4 в секунду и интервале четверть секунды
заявка равна −8. Если бюджет выделяет половину, из четырёх полученных единиц
одна уходит на текущее потребление, и запас становится равен 6.

У игрока и AI общий запас в таблице Control. Перед выборкой стрельбы банк
орудий читает его, после завершения циклов публикует расход. Пауза в огне
даёт бюджету восстановить заряд; ожидание не создаёт выстрел задним числом.
Общий ресурсный шаг также обслуживает устройство tag 10 в штатном режиме
`0x2000`. Фабрика 1 использует те же бюджетные методы, что простые устройства.

Расход ходовой пока подменён нулём с отдельным счётчиком по владельцу:
оригинал использует в нём динамические поля полного контроллера движения.
Активный режим tag 10 и неполные бюджетные таблицы останавливаются явно;
для такого владельца ограничение стрельбы зарядом временно отключается.
Поэтому этот путь ещё не устанавливает точный энергетический баланс боя.

### Заявка на захват строения

`Handler(35)` даёт сценарию две величины: ID строения и оценку боевой силы
вражеских машин вокруг него. Сценарий передаёт радиус этой оценки. Среди
строений противника без действующей заявки на захват выше всего стоят
генератор, завод, шахта, институт и склад, в таком порядке.

Вызов GOG `ai.dll` по RVA `0xc847` на контрольной карте выбрал генератор
и вернул силу охраны `8`. После добавления заявки на этот генератор вызов
выбрал завод с оценкой `0`. При пустом списке строений вернулся ID
`0xffffffff`. SHA-256 этой сборки DLL
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`.

Секция заявки обращается к `Handler(14)` за варботом с лёгким или малым шасси
и передаёт его ID в `ORDER_ROBOT_CAPTURE`. `ai.dll` по RVA `0x8a99`
делит расстояние в плоскости карты на текущий передний предел Control,
который селектор `0x91` читает из профиля. При пределе в одну единицу
в секунду и ниже кандидат пропускается. Если варбот покрывает расстояние
за секунду, его оценка равна нулю. При равных оценках сохраняется первый
кандидат. Вызов оригинальных `ai.dll` и `Control.dll` подтвердил, например,
выбор варбота в 30 единицах со скоростью 10 вместо варбота в 20 единицах
со скоростью 2. Если варбот ещё собирается, FParkan включает его в список
после выпуска.

Задача оригинала сначала пытается войти в строение (`Behavior.dll`, RVA
`0x3094f`). Ветка `0x1402` запрашивает граф проходов и передаёт маску
`0x40`. В GOG `ArealMap.dll` (SHA-256
`a25f9254ebb339d70e2e07c8121950191e9584ca0858d8e9c2e2b6c671edf6ea`)
выбор по RVA `0xa7e0` возвращает первую подходящую точку, а `0xa760`
переносит её из координат узла MSH в мир. У малого завода в штатных
«Двух крепостях» это точка 31 в подземной рубке.

Граф хранится в `Res17` модели. Запись точки занимает 20 байт и содержит
три координаты, флаги и индекс узла MSH. Запись связи занимает 40 байт
и содержит два индекса точек и четыре пары условий прохода.
`ArealMap.dll` по RVA `0x9cb0` разрешает ключ устройства и проверяет
его состояние. Маска `0xffffffff` разрешает проход без устройства,
нулевая маска закрывает его. Это различие проверено прямым вызовом
из оригинальной DLL. FParkan исключает закрытые симметричные связи
ещё при поиске пути, поэтому ближний закрытый вход уступает дальнему
проходимому. Для устройств типа 12 ветка `0x9b40` опрашивает
селекторы `0x70`, `0x71` и `0x52`. На симметричных связях малого
завода ключи 22 и 7 совпадают с узлами дверей в записях CTLD типа 12.

FParkan прокладывает внешнюю часть пути до двери с запасом по ширине
корпуса. Внутри робот движется по трёхмерным отрезкам графа, поэтому
может спуститься ниже поверхности. Связь с дверью ждёт окончания её
анимации и расходует то же время кадра, что разворот и движение. Темп
открытия унаследован от дверей игрока и остаётся приближением.
Со штатного старта «Двух крепостей» захватчик проходит к рубке генератора.
При прибытии запись строения переносится между распределителями.

Если вход не удаётся, RVA `0x309ce` выбирает ближайшую доступную точку
через селектор `0x203` строения. В оригинале десять точек склада и
двенадцать у генератора совпадают со второй секцией BAS после переноса
в мир. Замыкающая копия первой вершины в список не входит.

### Выбор строения для атаки

Перед приказом атаки сценарий может проверить, остался ли нужный объект в
мире. `Handler(39)` из GOG `ai.dll` по RVA `0xce59` передаёт логический
ID в ArealMap и возвращает единицу, если поиск дал ссылку. Изолированный
вызов подтвердил единицу для зарегистрированного ID и ноль для отсутствующего
ID и `0xffffffff`. SHA-256 сборки
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`.

В `Problems0` миссии 20 эта проверка позволяет сценарию отдать приказ группе
варботов, когда погибнет варбот с ID 25. Каждый приказ использует ту же задачу
атаки, что и команда из `Init`.

`Handler(64)` берёт ближайшее вражеское строение за радиусом своей базы.
В `scream.scr` ветку штурма открывает `dLargeResearched == 1`, результат
`Handler(65)`. При нуле сценарий использует ветку захвата. GOG `ai.dll` по
RVA `0x111d0` ищет изученную схему с размером от 3 и рейтингом вооружения
от 105000. Строения из поиска исключены. Размер для объектов класса Control
4 задан третьим байтом имени корневого компонента Unit DAT. Вызов GOG
`Behavior.dll` по RVA `0xcee0` подтвердил соответствия `t → 1`,
`h/l → 2`, `m → 3` и `b → 4` в обоих регистрах. FParkan может завершить
проверку, пока изучены только лёгкие схемы. Прямой вызов `ai.dll` на
каталоге штатной миссии дал ноль. После смены статуса подходящей схемы на
изученный оригинал сохраняет единицу при последующих запросах.

Рейтинг схеме выдаёт селектор `0x204` в `Behavior.dll` по RVA `0xa7b1`.
Изолированный вызов сумматора RVA `0x1ccb0` подтвердил, что в рейтинг
входят сгруппированные орудия. Каждое орудие даёт вклад
`(исходная оценка / ёмкость) × остаток боеприпасов`. Нулевая ёмкость
исключает вклад. Источник исходной оценки в живом объекте пока требует
сверки. Для `lwing1.dat` существующая проекция суммы NDP даёт 41300
против 201400 в каталоге оригинала. SHA-256 проверенной `Behavior.dll`
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`.

`Handler(68)` меняет предел расчёта этого радиуса. Код GOG `ai.dll` по
RVA `0x6700` ищет самое дальнее строение клана внутри предела, прибавляет
100 единиц и ограничивает результат тем же пределом. По умолчанию предел
равен 700 единицам. FParkan применяет это правило к живым строениям карты.

Вызов оригинала по RVA `0xe8e7` подтвердил выбор ID за радиусом базы.
Для оценки охраны DLL передаёт отдельный вектор со стека, который эта
функция явно не заполняет. В контрольном вызове оценка менялась даже
при повторе с теми же данными. FParkan использует начало координат карты
как постоянную точку оценки.

### Свободный исполнитель

`Handler(72)` запрашивает размерный класс объекта по его логическому ID.
Это отдельное свойство `0x201`, которое не зависит от владельца. GOG `ai.dll`
по RVA `0xf477` читает его через интерфейс объекта; для отсутствующего ID
возвращается `ERROR`. Вызов DLL вместе с исходным getter из `Behavior.dll`
подтвердил передачу класса и результат при отсутствии объекта.

Класс задаётся прототипом. Метод `Behavior.dll` по RVA `0xcee0` для типа
дескриптора 3 читает четвёртую букву имени: `l → 2`, `m → 3`, `b → 4`,
`e → 5`. Для типа 4 он читает третью: `t → 1`, `l/h → 2`, `m → 3`, `b → 4`.
Регистр не важен, короткое или неподходящее имя даёт 0. Например,
`R_H_03` относится к классу 2. Эти значения сверены вызовом исходного метода.
SHA-256 `Behavior.dll`:
`ddfbdbde07832358fe6e35e01c8cdba9b58e7313789498b6049ed51d4ed9baf99`.

Сценарий может искать свободный объект заданного класса через `Handler(13)`
с режимом `UNIT_FREE_UNIT`. GOG `ai.dll` по RVA `0x86fb` идёт по реестру
своего клана и возвращает первый объект с точным совпадением класса и
состоянием назначения `0xffffffff`. Занятая или зарезервированная запись
пропускается. Если подходящих записей нет, результат равен `ERROR`.
Это правило подтверждено вызовом DLL; SHA-256
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`.

Например, заявка `PBM_ROBOT_NEEDED` ищет `BUILDING_PLANT` (`0x80000010`).
Полученный ID поступает в приказ производства. Пока завод занят сборкой,
FParkan пропускает его при следующем поиске. Выбор также учитывает живого
владельца, резервирование и действующие назначения AI.

### Боевые группы

`Handler(71)` выбирает цель среди вражеских строений указанного класса.
Он оценивает охрану каждого в заданном радиусе по горизонтали и возвращает
ID наименее защищённого. При равной силе сохраняется первая запись. Своё
строение, союзник и отсутствующий объект не становятся кандидатами.
Оценка охраны отдельным выходом передаётся в сценарий как усечённый DWORD,
в том числе при записи в переменную `float`.

Вызов GOG `ai.dll` по RVA `0xf12e` подтвердил выбор, равенство оценок,
точное совпадение класса и строгую границу радиуса. При отсутствии цели
возвращается `ERROR`, а выходная сила получается из исходного `1e12_f32`
после усечения и преобразования в DWORD.

`Handler(67)` находит первый завод в списке клана и суммирует силу
своих машин ближе 250 единиц к нему. Сценарий получает ID завода и
отдельное число, по которому может решить, нужно ли прикрытие.
Вызов GOG `ai.dll` по RVA `0xeec7` подтвердил порядок выбора,
строгую границу радиуса и исключение чужих машин. При отсутствии
завода вызов вернул `0xffffffff` и силу 0.

`Handler(47)` ищет противника внутри радиуса базы с добавленным
сценарием запасом. Он пропускает цели, на которые уже заведена заявка
обороны. Герой имеет приоритет, затем выбирается самая сильная машина.
Вызов по RVA `0xd79b` подтвердил выбор героя, пропуск уже назначенной
цели и переход через строгую границу поиска.

`Handler(25)` в режиме `TAKE_BY_HITS` набирает свободных варботов по
расстоянию до цели. Когда суммарная сила достигает запроса, набор заканчивается.
Если сил не хватило, сценарий получает набранную силу и может запросить
подкрепление. `Handler(28)` передаёт один приказ каждому участнику. В
«Двух крепостях» захватчик идёт к зданию, а группа получает приказ
патрулировать вокруг самого захватчика.

Режим `TAKE_ALL_FREE` набирает группу без порога силы и без цели. Он идёт
по реестру клана и берёт все записи со свободным назначением `0xffffffff`
в исходном порядке. Ограничения по классу здесь нет: вызов оригинальной
DLL включил в группу свободные варботы, транспорт и завод, пропустив занятые
и зарезервированные записи. Пустой набор вернул `ERROR`.
Цель и действие задаются следующим `Handler(28)`, поэтому набор не привязывает
группу к объекту заранее. Действующий приказ атаки удерживает юнита в группе
так же, как патруль. Освобождение старой группы сохраняет новый приказ юниту.

`TAKE_ALL_BATTLE_UNITS` тоже не требует цели и порога, но берёт только
варботов. Вызов DLL подтвердил ещё одно отличие: занятость другой заявкой
не всегда мешает набору. Сравнивается вид заявки, а не её номер: варбота
с другим видом задачи можно забрать, с таким же — оставить на месте.
Резерв `0xfffe` сохраняется. При переназначении FParkan исключает робота
из прежней группы или маршрута захвата. Так сценарий игрока `c5m1p`
собирает собственную оборону базы и направляет её к заданной точке.

В GOG `ai.dll` обработчики находятся по RVA `0xab85` и `0xba01`.
SHA-256 DLL `c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`.

Целью группы может быть и точка карты. `TARGET_BY_PLACE` передаёт два
целочисленных значения XY: например, `(395, 781)`. Перед преобразованием
в float они читаются как DWORD. Заявка `PBM_PLACE_PROTECT` сохраняет набранную
группу между вызовами `_Continue`; следующая проверка может добавить
выпущенные заводом машины. Один и тот же юнит повторно в группу не входит.
При освобождении группы снимается её патруль, если юнит ещё выполняет его.
Новый приказ движения или атаки этим освобождением не отменяется.

Вызов GOG `Behavior.dll` по RVA `0x2d520` подтвердил настройку точечного
патруля: центр берётся из XY, радиус `0` или `0xffffffff` даёт 60 единиц,
остальные значения задают радиус непосредственно. SHA-256 DLL
`ddfbdbde07832358fe6e35e01c8cdba9b58e7313789498b6049ed51d4ed9baf99`.
Это подтверждает параметры задачи; маршрут движения и хронология миссии
остаются отдельной проверкой.

`Handler(27)` по RVA `0x94f1` добавляет к заявке условия. Например,
прикрытие можно снять, когда целью завладел свой клан, цель уничтожена
или группа осталась без приказа. Цикл по RVA `0x4ee0` проверяет список,
а RVA `0x5180` определяет, выполнено ли отдельное условие. В режиме
`OR_TASK` достаточно одного. Пока заявка ждёт, её секция `_Start`
не отправляет ту же группу повторно.
Изолированный вызов RVA `0x5180` подтвердил два условия. Захват
засчитывается при смене владельца на клан заявки, а уничтожение — после
исчезновения объекта из реестра. Исчезновение объекта само по себе
условие захвата не выполняет.

### Патруль у завода

`Handler(37)` расширяет выбор охраны на все свои строения с логическим ID.
Для каждого он складывает силу своих машин ближе 250 единиц по горизонтали
и выбирает строение с наименьшей суммой. На самой границе машина не входит
в охрану. При равенстве сохраняется первое строение в реестре.
Поэтому сценарий может отправить свободных варботов к удалённому зданию,
у которого пока нет прикрытия.

Вызов GOG `ai.dll` по RVA `0xcedf` подтвердил границу, выбор меньшей силы
и порядок при равенстве. SHA-256 DLL
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`.
При пустом списке возвращается ID `0xffffffff`, а выходная оценка получает
DWORD от усечения исходного значения `1e12_f32`.

`Handler(44)` оценивает охрану уже заданного места. Сценарий передаёт радиус,
клан и координаты XY либо логический ID объекта. Команда складывает силу
машин выбранного клана строго внутри радиуса и возвращает усечённый DWORD.
Высота машин не участвует в расстоянии. Значение `ERROR` вместо номера клана
означает сумму по враждебным кланам, а отсутствие объекта с заданным ID даёт
ноль. Координаты можно передать как DWORD или float.

В GOG `ai.dll` эта команда находится по RVA `0xd57e`, общий расчёт области —
по RVA `0x6130`. Изолированный вызов подтвердил обе формы цели, выбор клана,
строгую границу радиуса и преобразование координат. В сценариях эта оценка
определяет, требуется ли дополнительный патруль в указанном месте.

`PBM_BUILDING_PROTECT_Start` сравнивает силу машин возле завода с порогом
сценария. При достаточной охране заявка переходит в `ST_SOLVING` без нового
приказа. В действующей заявке `PBM_BUILDING_PROTECT_Continue`
считает силу уже назначенных роботов, набирает недостающих и может запросить
варбота у завода. В «Двух крепостях» приказ задаёт радиус патруля 150 единиц.
В FParkan охрана освобождается, когда здание исчезает или меняет владельца.

В исходной AI DLL проход по активным заявкам идёт перед `Problems0`
(RVA `0x1780` и `0x1e50`). Изолированный вызов `Handler(45)` по RVA
`0xd753` подтвердил сумму рейтингов участников с пропуском свободных слотов:
две машины с рейтингом около 8,2 и свободный слот дают ответ 16. В FParkan
для суммы используется модель боевой силы на основе таблиц Control.

У цикла клана есть собственные часы. GOG `ai.dll` (SHA-256
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`)
по RVA `0x17ae–0x1817` запускает цикл, когда текущее время строго больше
сохранённого срока. Новый срок равен `сейчас + 7000 + rand() % 1000`
миллисекунд. При опоздании выполняется один цикл; пропущенные циклы не
догоняются. Логические часы, которыми пользуются сценарные таймауты,
прибавляют ровно семь секунд, независимо от случайной добавки и опоздания.

Это правило подтверждено в работающей игре: следующий вызов каждого клана
пришёл после записанного срока, а добавка совпала с результатом генератора.
Сам `rand()` по RVA `0x1d6d0` использует отдельное состояние DLL и ту же
формулу CRT, что описана для Behavior. Вызов DLL с начальным состоянием 1
даёт задержки 7041, 7467 и 7334 мс. FParkan хранит отдельный генератор AI
на время жизни движка и применяет эти правила в окне и отчёте симуляции.

Свежий контекст уже готов к первому проходу. При штатном старте «Двух
крепостей» оригинал входит в первое обновление с отрицательным сроком и
назначает следующий срок после этого прохода. FParkan выражает готовность
значением `−1`. Семисекундного ожидания перед первым проходом нет.
Точки RVA `0xf755`, `0x1780` и `0x17ff` связывают это наблюдение с
конструктором, проверкой срока и его первой записью в той же сборке DLL.

Клан игрока участвует в этих часах даже с пустым `Problems0`: при свежем
запуске он получил добавку 41 мс, а противник — следующую добавку 467 мс.
Поэтому FParkan обновляет часы всех инициализированных сценарных контекстов
по порядку кланов. Непустой `Problems0` исполняется также у клана игрока;
например, в начале пятой кампании он ставит заявку на защиту базы.
`Mission` и `Problems0` читают один счётчик своего клана в поле `AI+0x854`,
поэтому сценарные таймауты зависят от числа проходов AI.
При повторном штатном запуске первый вызов `Mission` по RVA `0x11f10`
прочитал ноль до первого цикла AI, а следующие вызовы — семь.
`script_clan_clock_approx` считает проходы по кланам; остальные потребители
RNG ещё требуют сверки всей хронологии.

У таймеров AI есть отличие от часов движения: они продолжают отсчёт во время
паузы. В живом оригинале после долгой паузы `Mission` сработал до обновления
часов мира, а следующее обновление AI сразу увеличило логический счётчик на
семь. Это следует из системных таймеров по RVA `0x1b80` и `0x1780`, а не из
ускорения игрового мира. FParkan передаёт длительность паузы отдельным
уведомлением: на следующем кадре проверяется один срок, затем назначается
новый. Роботы за время паузы не перемещаются, производство не догоняет часы.

Новая машина не обязательно ждёт весь очередной интервал. Обработчик регистрации
`ai.dll` по RVA `0x1880` находит объект по ID и проверяет, что этого ID ещё нет
в реестре клана. Затем по RVA `0x1a9d` он вычитает 1400 мс из срока ближайшего
цикла. Повторный ID и отсутствующий объект оставляют срок прежним; RNG и
логические часы при этом не меняются. Эти ветви проверены вызовом DLL, а сдвиг
при появлении варбота также пойман в работающей игре. Несколько регистраций
складываются. Срок хранится как знаковое 64-битное число: после перехода через
ноль следующий вызов допускается сразу, без зажима к нулю.

FParkan уведомляет инициализированный сценарный контекст клана через общий путь создания
машины, строения, шахты или подкрепления. При захвате уведомляется новый
владелец. Так свежий варбот быстрее получает сценарное задание.
`script_clan_registration` показывает число таких уведомлений по клану.

### Сценарный заказ транспорта и строителя

Когда складам не хватает свободного места, сценарий «Двух крепостей»
проверяет транспорт и просит завод собрать машину. Приказ
`ORDER_BUILDING_CONSTRUCT` с `TARGET_BY_NAME` ищет готовую к производству
схему в `UNITS/UNITS/AI`. Список `prebuild` в настройках миссии задаёт
схемы для игрока. Сценарный транспорт проходит проверку технологий своего
клана и занимает обычную очередь своего завода.

Вызов GOG `ai.dll` по RVA `0x10be0` подтвердил выбор `SELECT_FASTEST`:
чужой класс и недоступные схемы пропускаются, при выключенном случайном
смещении выбирается максимальная скорость, а при равенстве первая схема.
В FParkan подключён случай с одной доступной схемой. В «Двух крепостях»
таблица `scream.trf` допускает `sml_cargo.dat`.

Тем же путём идёт заявка на строителя класса `0x01004000`. Вызов селектора
GOG `ai.dll` по RVA `0x107c0` на каталоге штатных «Двух крепостей» выбрал
единственную доступную схему `sml_bldr.dat`; выключение её статуса даёт отказ.
FParkan при загрузке готовит единственную доступную схему каждой служебной
категории клана и передаёт заявку в обычную очередь завода. После выпуска
строитель получает сценарный ID и состояние
рудного отсека, поэтому его находят запросы клана и строительные задачи.
Начальные значения руды берутся из классового инициализатора Behavior,
описанного ниже; полный заводской жизненный цикл ещё требует живой сверки.
Рейтинг при нескольких доступных служебных схемах остаётся открытым.

Для боевого варбота `SELECT_STRONGEST` сортирует допущенные технологии
клана по выносливости корпуса и запасу оружия. В GOG `ai.dll` ветка
RVA `0x1099d` передаёт пару в `0xfc70`, где оценка равна
`(запас оружия + 0,8) × выносливость × 0,00001`. При равной оценке
выигрывает ранняя запись каталога. Вызов RVA `0x107c0` на каталоге
штатных «Двух крепостей» вернул `12spd1.dat`. После последовательного
отключения лидеров он выбрал `spider1.dat`, `spider12.dat` и `12hel1.dat`.
В FParkan начальный допуск берётся из TRF, запас из банков Control,
а выносливость оценивается по NDP с поправкой на сопротивление Control 27.
Для заводского выпуска резервируются слоты только выбранной схемы.

После выпуска сценарий находит свободный транспорт по классу и передаёт
`ORDER_ROBOT_TRANSPORT`. Вызов `Handler(14)` из GOG `ai.dll` по RVA
`0x8a99` вернул логический ID первой свободной машины подходящего класса.
При резервировании первой машины он выбрал следующую. Behavior берёт руду в шахте своего клана и
отвозит на склад. В GOG `Behavior.dll` (SHA-256
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`)
поиск шахты и склада идёт по RVA `0x32a00` и `0x32c50`, а перенос
по RVA `0x32000` ограничен темпом перегрузки, количеством у источника
и свободным местом у получателя.

### Залежь или готовая шахта

`Handler(40)` помогает клану получить следующую шахту. Сначала он выбирает
ближайшую свободную залежь относительно базы. Расстояние перед сравнением
усекается до целого, поэтому внутри одного целочисленного интервала выигрывает
первая запись. Координаты тоже усекаются. Команда возвращает `0xffffffff`,
записывает координаты и силу вражеской охраны в радиусе 350 единиц и резервирует
точку на минуту. Сценарий отличает этот результат от отсутствия кандидата по
ненулевой координате X и переходит в событие `BUILD_MINE`. Там он выбирает
строителя, при его отсутствии заказывает нового, а затем отдаёт приказ постройки.

Если свободных залежей нет, выбирается вражеская шахта с самой слабой охраной.
Возвращается её логический ID и оценка охраны; координаты остаются прежними.
Когда подходящей шахты тоже нет, координаты обнуляются, а оценка сохраняется.
Такой порядок и записи выходов подтверждены вызовом GOG `ai.dll` по RVA
`0xd030`, SHA-256
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`.

Каталог обновляется по RVA `0x10e40`: оригинал просматривает шахты в ареале
залежи и проверяет полосу X ±150 включительно. Координата Y в этом условии
не используется. FParkan пока подставляет существующую привязку `MineSite`,
которая ищет шахту по расстоянию до залежи; перенос ареальных записей открыт.

Переход с control `4` содержит индекс другого события, а не индекс переменной.
VM продолжает с его первой инструкции, сохраняя ячейки, и не возвращается к
оставшимся инструкциям исходного события. Исполнение GOG VM по RVA `0x11f10`
подтвердило этот переход и его пропуск в ложной ветви; сам переход расположен
по RVA `0x12225`. Поэтому `BUILD_MINE` видит выбранные координаты и текущую
заявку. Строитель оплачивает детали рудой на борту, едет к залежи и ждёт
секунду. Появившаяся шахта занимает подготовленный слот этой залежи и
включается в общий цикл добычи. Для огромного запаса залежи небольшое
списание может теряться при округлении `f32`; работа видна по росту буфера шахты.

### Площадка для постройки

`Handler(18)` ищет точку вокруг базы клана кольцами с шагом 150 единиц.
GOG `ai.dll` по RVA `0xa148` проверяет четыре угла квадрата
со стороной 150 единиц. Среднее отклонение их высот от средней высоты
должно уложиться в 20 единиц. Точка должна быть на расстоянии не менее
250 единиц от строений, свободных залежей и площадок, зарезервированных
другими заявками. Резерв хранится минуту. Сценарий передаёт найденные
координаты строителю в `ORDER_ROBOT_BUILD`. Если площадки нет, он
получает нули и откладывает постройку.

Изолированный вызов DLL на ровной поверхности выбрал центр базы, а
повторный вызов с активным резервом выбрал точку на следующем допустимом
кольце. При недоступных областях вызов вернул `(0, 0)`.

Строитель получает первую схему категории из `BuildDat.lst` через
`ArealMap.dll` по RVA `0x20e80` (SHA-256
`a25f9254ebb339d70e2e07c8121950191e9584ca0858d8e9c2e2b6c671edf6ea`).
Задача из GOG `Behavior.dll` по
RVA `0x28800` проверяет детали и считает цену. Когда деталей нет в
технологиях клана, приказ возвращает отказ. Задача может пополнить руду
в шахте или на складе, затем едет на площадку. Через секунду ожидания на месте
создание объекта списывает руду (RVA `0x28e89` и `0x29240`).
Штатный приказ на среднюю башню в «Двух крепостях» получает отказ из-за
деталей, которых ещё нет у клана.
Изолированный вызов расчёта цены по RVA `0x29810` подтвердил отказ по
штатным флагам и цену 1100 руды после открытия деталей.

То же правило действует для склада, завода и лаборатории: первая схема
категории, разрешённые детали и цена из таблицы клана. Исполнение того же
расчёта в DLL на исходных технологиях «Третьей части» даёт соответственно
670, 770 и 560 руды, 177, 178 и 145 энергии. Строитель расходует руду;
энергия здесь не списывается как отдельный ресурс заказа.
Пополнение зависит от отдельного параметра `Building_Cost`, штатно равного
100. Вызов задачи по RVA `0x28ff0` подтвердил: при меньшем бортовом запасе
строитель ищет источник, при запасе от 100 едет сразу, независимо от цены
выбранной схемы. Шахта пропускает поиск источника. Поэтому оплата может
оставить отрицательный запас; нативный setter сохраняет это значение.

Поиск по RVA `0x29110` выбирает ближайшую свою шахту или склад с запасом
строго больше `Building_Cost × 1,5`, то есть 150 при штатной настройке.
На источнике задача по RVA `0x28b80` переносит минимум из доступной руды,
остатка цены и `dt × Transport_OreOnBoardPerSecond`. Штатная скорость —
100 единиц в секунду. Достигнув цены схемы, строитель едет на площадку.
Эти пороги и переходы проверены вызовами DLL вместе с конструктором
параметров по RVA `0x16250`; FParkan использует те же штатные значения.
Подъезд к источнику пока заканчивается снаружи здания, без нативного порта.

В FParkan сценарий этой миссии со штатного старта уже ставит завод и
лабораторию. Готовое здание получает контроллер, запас руды и логический
ID, а завод входит в список производства и принимает заказ транспортника.
В кадре завершения сценарной стройки окно ставит подготовленную модель
на высоту основания и применяет её BAS к рельефу. Подземные пути используют
пол и стены здания, а снаружи движение снова опирается на грунт.

### Проверка улучшения здания

`Handler(58)` выбирает по индексу из зданий клана, прошедших проверку.
Учитываются расстояние до базы, класс здания и его занятость. Если у
здания есть следующая ступень в `BuildDat.lst`, оригинал проверяет
технологии этой схемы. Вызов GOG `ai.dll` по RVA `0x68b0` подтвердил
сравнение расстояния по XY, переход к следующей ступени и пропуск
занятого здания или здания последней ступени.

`Behavior.dll` по RVA `0xa7ff` отдаёт номер ступени, начиная с нуля.
Для зданий среднего, большого и сверхбольшого размеров это 1, 2 и 3.
При проверке технологий `ai.dll` по RVA `0x10100` считает найденные
детали, для которых в TRF ещё сброшен бит изученности. Наличие такой
детали в следующей схеме останавливает улучшение. Проверка в FParkan
использует это правило для корня схемы и учитывает исследования,
завершённые во время миссии. Полный отбор допустимого здания и
приказ строителю пока остаются открытыми.

### Первый запуск сценария

В FParkan для одиночной миссии завершённый `Init` оставляет движение и бой исполняемым
приказам сценария. До первого приказа машины сохраняют исходные позиции.
Периодический `Problems0` назначает защитников и передаёт заявки заводам;
назначенный патруль может искать противника и стрелять. Заглушка каталога
исследований учитывается отдельно и не включает дополнительную охрану или
рейд на завод. Эти аварийные подмены остаются только при настоящем обрыве `Init`.

Перед настройкой первого шага каждый AI получает начальный массив DWORD. В
`iron3d.dll` SHA-256
`d1dc4ea8535e2069b0a05c9e8be2724dd438ba44cca7a83007d8b2e50f9e35fa`
`FUN_100392e0` (RVA `0x392e0`) повторяет вызов слота AI `+0x38` столько раз,
сколько задаёт `second_resource.tag` этой строки TMA. Этот слот ведёт в
`ai.dll` SHA-256
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`:
метод RVA `0x2010` передаёт коллекцию при `AI+0x83c` в `FUN_10002980`
(RVA `0x2980`), а она добавляет один DWORD через `FUN_100048f0` (RVA
`0x48f0`). Каждый вызов копирует `0xffffffff`; входное слово не меняется.
Поэтому тег `3` даёт `[0xffffffff, 0xffffffff, 0xffffffff]`. Это число
начальных ячеек, а не назначение трёх ID.

Изолированная x86-проверка вызовом оригинальной `ai.dll` подтвердила пары
«число слотов/ёмкость» `0/0`, `1/17`, `17/17` и `18/34`. Все добавленные слова
равны `0xffffffff`, а входное значение, контрольные поля, память вне заголовка
массива и указатель стека сохраняются. Это подтверждает добавление начального
слова, но не работу последующих обработчиков.

Rust хранит такой снимок в отдельном `MissionAiStartupState` для каждого TMA-клана,
а не в пакете сценария. При полной загрузке (`Full`) создаётся запись для каждого
клана, в том числе если у него нет пути сценария или пути таблицы исследований. Счётчик
берётся из сырых битов `second_resource.tag` как `u32` у обеих форм записи —
`Standard` и `Spatial`; нулевой счётчик даёт существующее состояние с пустым
списком. Статический режим предпросмотра не создаёт состояний AI.

Загрузка отклоняет суммарный объём свыше 1 000 000 DWORD и резервирует память
проверяемой операцией; это защита Rust от чрезмерного выделения памяти, а не
ограничение оригинальной игры. Rust сохраняет начальные слова, но не
восстанавливает работу последующих обработчиков и не назначает этим словам ID
объектов. Этот массив также не является списком
`BehaviorDistributorState.registered_objects`.

До регулярной работы Behavior настраивает расписание своего первого шага. Он
берёт текущее 32-битное время игровой очереди и назначает проверку через три
интервала по 64 мс, добавляя небольшую случайную задержку от 0 до 63 мс. Эта
задержка нужна каждому экземпляру, но случайные числа берутся из общего
генератора, поэтому порядок запуска кланов влияет на их значения. При первой
подготовке controller также очищает несколько внутренних слов. В проверенном
повторном вызове до назначенного срока ненулевое сохранённое время оставило
срок прежним, не потребовало нового случайного числа и не очистило эти слова;
поведение после срока пока неизвестно.

В оригинале вызов идёт через обратный вызов движка: Iron3D сначала создаёт
SuperAI для записей кланов, затем обновляет Behavior и ищет `Init` для
соответствующего AI. Если `Init` не найдено, одноразовая метка остаётся
выключенной. Если оно найдено, диспетчер запускается только при свободной защите
от повторного входа; при занятой защите вызов пропускается, но одноразовая метка
всё равно устанавливается. В полной загрузке Rust вызывающая сторона передаёт
значение времени очереди; после регистрации объектов загрузчик последовательно
подготавливает каждый сценарный пакет и выполняет восстановленные действия
`Handler(19)` и поддержанные формульные присваивания из первого `Init`. Статический
просмотр не запускает Behavior, но может сохранить эти записи `Init` в сценарном
varset.

Это полезное начало сценария, но ещё не целая игровая жизнь AI. Текущий runtime
не воспроизводит аргумент обратного вызова в `AI+0x3fc`, защиту от повторного
входа `AI+0x78`, одноразовую метку `AI+0x8a8` или полное обновление Behavior на игровых
тиках. Распределение ресурсов исполнено на исходной DLL с искусственными
объектами и подключено к Rust `step_headless`: явное время очереди определяет,
какой клан должен выполнить очередной ресурсный шаг.
При полной загрузке Rust уже восстанавливает членство объектов в клановых
списках Behavior и задаёт их начальные доли. Остальные слова записи хранятся
сырыми: семантика только первого из пяти слов хвоста установлена для
нормализации.
Runtime также не подменяет очередь оригинала: вызывающая сторона сама передаёт
время, а локальный генератор Rust пока учитывает только случайные числа
восстановленного стартового шага и ресурсного планировщика.

### Откуда берутся объекты распределителя

Для каждого клана Iron3D создаёт AI независимо от того, найден ли его `.scr`.
Таблица `GetSuperAI` получает указатель только для клана, чей пакет сценария
успешно загружен. У размещённого объекта первое DWORD после имени ресурса
выбирает индекс этой таблицы; второй соседний DWORD для этой цели не используется.
World3D получает индекс через дескриптор создания объекта и передаёт его в
Behavior. Отдельно DWORD по смещению `+4` от начала Unit DAT задаёт class word
объекта. Это второе 32-битное слово файла; его старший бит приводит к созданию
registration key, который проходит защиту Behavior вместе с проверками AI и
distributor.

Для обычной полной загрузки Rust сохраняет по одной записи состояния на клан.
Каждый размещённый объект с известным Unit DAT и установленным старшим битом
получает существующий `ObjectHandle` и попадает в список только при точном
совпадении индекса `raw_after_resource` с доступной записью `GetSuperAI`. Индекс
не перенумеровывается: например, пакет клана 1 остаётся слотом 1 даже если
пакет клана 0 отсутствует. Preview сохраняет свои статические данные, но не
создаёт эти связи.

В лицензированной AutoDemo это даёт четыре членства: TMA объекты 4 и 6 идут
в слот 0, а объекты 5 и 7 — в слот 1. У парных записей первого клана raw
селектор равен 0, у второго — 1; классы из Unit DAT равны `0x80000010` для
`wor_l_n1.dat` и `0x80000002` для `gener01.dat`. Тот же обычный путь в исходном
Behavior добавил четыре ключа `0x80000003..0x80000006` в два distributor-а.
Rust-тест повторно читает лицензированную миссию, связывает результаты с её
TMA-записями и проверяет реальные `ObjectHandle`, но помечен `#[ignore]`, чтобы
не требовать оригинальных ресурсов от остальных разработчиков.

После подготовки Control-таблицы можно разобрать и её начальную группировку для
Behavior. Важны текущая метка записи и её порядковый номер в общей таблице:
метка `1` начинает пустую группу, метка `2` становится кандидатом последней
группы, а метка `30` записывает строку в отдельный список той же группы.
Кандидат, встретившийся до первого заголовка, остаётся в списке без группы;
ранняя метка `30` игнорируется. Например,
для текущих меток `[2, 30, 1, 30, 2]` получаются незагруппированный кандидат
`[0]` и группа с заголовком `2`, кандидатом `[4]` и строкой с меткой `30` под
порядковым номером `[3]`. Все номера начинаются с нуля и отсчитываются по общей
Control-таблице, а не по ключам устройств или записям CTLD.

Полная загрузка Rust сохраняет это начальное состояние рядом с подготовленными
Control-таблицами по исходному TMA ID и `ObjectHandle`. Если таблица недоступна,
проекция сохраняет причину ошибки; доступная пустая таблица означает пустую
группировку. При предварительном просмотре список группировок не создаётся. Здесь
разбирается только подготовленный порядок текущих Control-дескрипторов. Проекция
не устанавливает, когда список присоединяется к живому Behavior, как он затем
обновляется и как работает полный игровой цикл.

Список распределителя хранит не только участников, но и долю каждого. При
добавлении двух объектов оба получают по половине общего веса. Если добавить
третий, движок оставляет долю новой записи около одной трети, а оставшийся вес
делит между прежними изменяемыми записями. Помеченная запись сохраняет свой вес,
как закреплённая часть общего набора. Повторное добавление того же объекта не
создаёт вторую строку и оставляет остальные слова записи нетронутыми.

Rust хранит этот небольшой начальный список с долями. Он не смешивает selector
из TMA, владельца мирового объекта и внутренний ключ Behavior: связь в Rust
опирается на уже созданный `ObjectHandle`. Регулярный обмен ресурсами пока
остаётся отдельным этапом, потому что для него нужны интерфейсы игровых объектов.

### Начальные свойства запасов руды

Behavior хранит `CurrentOre` и `MaximumOre` в одной записи свойства с ключом
`0x02000100`: текущее количество лежит в основном float-слове, предел — в
дополнительном DWORD. В TMA это не означает, что оба значения свободно задаются
файлом. При загрузке `MisLoad.dll` ищет первое свойство с точным, чувствительным
к регистру совпадением имени и передаёт его второе raw-слово в setter. В
Behavior дескриптор `CurrentOre` записывает это слово в основное значение;
дескриптор `MaximumOre` читает дополнительное слово, но его setter ничего не
меняет.

Оба дескриптора регистрируются как коды `4` и `5`. Это коды обработчика, а не
позиции в таблице дескрипторов: исходная DLL корректно работает и после
перестановки строк, потому что callback выбирает обработчик по коду строки.
Поэтому начальное состояние можно описать так, сохраняя биты без пересчёта
через `float`:

```text
current = first_exact("CurrentOre").raw_value[1] ?? class_default_current
maximum = class_default_maximum
```

Класс задаёт значения по умолчанию в Behavior RVA `0x8790`:

| Слово класса | `CurrentOre` | `MaximumOre` |
| --- | ---: | ---: |
| `0x80000004` | 0 | 500 |
| `0x80000008` | 0 | 4000 |
| `0x01002000` | 0 | 2000 |
| `0x01004000` | 2000 | 2000 |
| прочие слова в этой ветви | 0 | 0 |

Вызов RVA `0x8790` на синтетической структуре подтвердил эти значения для
классов таблицы, включая `0x01008000`; он проверяет тело native initializer-а,
но не его полный жизненный цикл в игре.

В полной загрузке Rust сохраняет эти два raw-значения рядом с исходным TMA ID
и `ObjectHandle` каждого объекта с Unit DAT; список участников распределителя
для этого не требуется. Это важно для объектов, у которых есть компонент
Behavior, но нет членства в ресурсном distributor. Preview намеренно не создаёт
начальное состояние. Лицензированная AutoDemo показывает восемь объектов с
Unit DAT, включая объекты класса `0x01008000` вне списков distributor; в этом
снимке TMA `CurrentOre` равен нулю у всех восьми. Нативный x86 oracle отдельно
проверяет ненулевое raw-слово, чтение предела, отсутствие записи в `MaximumOre`
и переставленные строки дескрипторов.

Эта модель покрывает именно начальную загрузку полных TMA-объектов. Она не
утверждает, что уже восстановлены все пути создания Behavior, отложенное
создание объектов или внешняя подмена class defaults конфигурацией.

### Регулярная передача ресурсов

Resource Distributor работает со списком зарегистрированных объектов. За один
шаг он сначала проходит список и собирает нужные значения, а затем проходит его
ещё раз и применяет результат. Во втором проходе объект ищется заново, поэтому
его состояние или ответ getter-а может измениться между чтением и записью.
Нулевой временной шаг ничего не делает. Состояние объекта с младшим словом
`0xfffe` пропускает строку в обоих проходах ещё до запросов ресурсных
интерфейсов. В FParkan этот признак берётся из маркера истощения Control:
истощённый источник перестаёт снабжать клан, а истощённый потребитель больше
не создаёт спрос. Сам объект и его запись остаются, доли остальных участников
не пересчитываются. Сохранённые поля спроса и выделения также не очищаются:
они описывают прежний шаг, но в новые итоги уже не входят.

Пропуск проверен вызовом GOG `Behavior.dll` (SHA-256
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`,
RVA `0x19e80`): для синтетического объекта со статусом `0xfffe` в каждом
проходе выполняются только поиск и чтение состояния, без ресурсных callbacks;
заранее заполненные служебные поля остаются прежними. Штатный рейд миссии 19 проверяет связь
этого правила с игровым Control: после истощения корня бункера его подача
энергии исчезает из итогов клана, хотя строение ещё остаётся в мире. На этой
карте общая скорость подачи меняется с `10,07` на `10`: другой источник
продолжает работать, а добавка бункера `0,07` больше не учитывается.

В синтетическом примере исходного кода два объекта с ключами `41` и `42`
обрабатываются в порядке `41, 42, 41, 42`: производитель сначала сообщает
скорость `4`, затем `1`, а получатель со значением `6` заканчивает шаг со
значением `7`. Это показывает, почему одного результата чтения недостаточно:
алгоритм снова получает величины при применении. Сценарий был запущен прямо из
исходной `Behavior.dll`, но объекты и ответы интерфейсов заданы тестом; это ещё
не воспроизведение реальной миссии.

Для правила долей есть отдельная проверка исходной `Behavior.dll` на синтетических
записях при игровом x87 control word `0x007f`: проверены добавление, повторный
ключ, закреплённая запись, нулевая сумма и округление. Это позволяет Rust
сохранять начальный список, но пока не подтверждает веса реальных объектов в
живой миссии.

Узкая часть регулярного шага уже связана с загруженным состоянием движка.
`advance_loaded_mission_resources(engine, queue_time_ms)` принимает явную
метку времени общей 32-битной очереди. Для каждого видимого Behavior clan он
проверяет срок запуска, выполняет два прохода по списку и сохраняет пять
итогов: доступную энергию и руду, буфер руды, потребление энергии и потребление
руды. В обоих проходах объекты разрешаются заново по исходному TMA ID. Первый
проход измеряет поставки и потребность, второй повторно читает представленные
профильные и Control-значения перед применением выделения. Нативный код также
запрашивает интерфейсы во втором проходе, но динамические getter-callbacks в
этом снимке Rust не воспроизводятся.

Планировщик использует беззнаковое сравнение времени: равенство ненулевому
сроку ещё не запускает шаг, а нулевой срок не задерживает его. Переполнение
вычитания даёт 32-битную длительность. Затем
длительность переводится в секунды с округлением, подтверждённым x87-путём
оригинальной DLL. Нативный oracle проверяет его на длинных интервалах, включая
значения около границы точного целого `f32`, а также на равенстве и строгом
проходе срока. Формула запуска, native vectors и команда воспроизведения
описаны в технической главе [script VM](../appendices/script-vm.md).

Шаг работает только с уже созданными полными объектами миссии и снимками тех
профилей и Control-таблиц, чьи запросы и setters представлены в runtime. Он
обновляет загруженные `CurrentOre`, поля строк распределителя и поддержанный
Control selector `1`; неподдержанное свойство, запрос Control или невозможное
арифметическое значение возвращает ошибку. Обновления нескольких кланов, их
расписания и RNG фиксируются одной транзакцией: если обязательный запрос
позднего клана не разрешён, ранее подготовленные изменения остаются
неприменёнными. Обычные `step_headless(engine, input, queue_time_ms)` и
`frame(engine, queue_time_ms)` запускают этот расчёт до обработки очереди мира.
Они сначала готовят ресурсные изменения, затем выполняют шаг мира и публикуют
ресурсное состояние после его успеха. Ошибка любой стадии сохраняет прежние
ресурсы; ошибка подготовки также не продвигает мировой tick. До срока
планировщика большие таблицы ресурсов не копируются.

Оконное приложение вызывает тот же расчётный путь. Полнота динамических
интерфейсов и жизненного цикла Control остаётся отдельной границей: поддержка
распределителя сама по себе не подтверждает полный паритет миссии.

Для настоящих ресурсов AutoDemo тест проходит несколько временных точек:
генераторы `ObjectId 6` и `ObjectId 7` читают `Transfer_Power_Out = 10` из
`prof_generator.var`; после шага в 500 мс каждый сообщает 5 единиц доступной
энергии. Это подтверждает связь загруженного профиля с runtime-расчётом, но не
сравнение полной миссии с оригинальной игрой. Native oracle сверяет исходные
планировщик и распределитель GOG `Behavior.dll`; техническая процедура и
проверяемые векторы описаны в [script VM](../appendices/script-vm.md). Остальные ограничения собраны в
[границах знания](../appendices/knowledge-boundaries.md).

Первый часто встречающийся table entry с side effect — `Handler(2)` (176
records в corpus). Он берёт active instruction, разрешает семь slots через
varset, приводит три значения к float по observed kinds `5`/`3`, затем
materializes или refresh-ит внутренний event record. Его base string связывает
`<base>_Start` и `<base>_Continue` с event table; прямого World3D/Behavior
call на этой ветке не найдено. Slot names и consumer record ещё не установлены
динамически, поэтому Rust не исполняет handler как гипотетическую команду
движения/атаки/строительства.

Безопасная runtime-модель:

```text
load script bundle
  -> validate version and symbol tables
  -> create global/formula variables
  -> bind named events to instruction offsets
  -> instantiate SuperAI per clan
  -> dispatch MISSION_START and object events
  -> update timers/conditions each simulation tick
  -> enqueue game commands through World3D/Behavior
```

Сценарий не должен владеть игровым объектом напрямую. Он хранит logical/object
IDs и отправляет команды через игровые interfaces, чтобы удаление объекта или
сетевой mirror не оставили dangling pointer.

Полная grammar compiled instructions и точное значение всех opcodes остаются
открытым направлением. До появления decompiler-а `.scr` binary body сохраняется
lossless, а доказанные symbol/event tables документируются отдельно.

### Подтверждённый evaluator записей условий

У сценарного слоя есть не только последовательность инструкций, но и отдельные
короткие проверки состояния. В GOG `ai.dll` версии `1.00` evaluator таких
проверок расположен по RVA `0x5180` (VA `0x10005180` при image base
`0x10000000`; SHA-256 сборки —
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`). Он
получает индекс 16-byte записи и смотрит на её tag, subtype и payload. Для tags
1–3 допустим subtype `0`, для tags 4–5 — subtype `1`; другие сочетания не
завершают условие. Байт по смещению `+0x0c` — флаг завершения: evaluator ставит
`1`, когда проверка проходит, и оставляет запись как есть, когда не проходит.
Вызывающая функция позже пропускает уже завершённые условия.

Tag выбирает конкретное правило. Для tag 1 запись завершается, когда поиск
объекта по payload ничего не нашёл. Для tag 2 объект, наоборот, должен
существовать: затем игра проверяет одно из его свойств и, в более сложной
ветви, принимает только три числовых кода результата — `1`, `0x12` и `0x13`.
Для tag 3 найденное значение сравнивается с первым числом текущего контекста.
Мы не знаем из одного этого кода, каким игровым словам соответствуют эти поля,
поэтому не называем их владельцем, жизнью или приказом.

Теги 4 и 5 обходят дочерние ссылки выбранного списка. Значение `-1` означает
«элемента нет» и пропускается. Тег 4 завершается, только если ни один дочерний
ключ не нашёл объект. Тег 5 тоже пропускает отсутствующий объект, но для
найденного смотрит результат другого виртуального вызова: ноль разрешает
продолжить, а первый ненулевой результат прекращает обход и оставляет условие
незавершённым. Так различаются два алгоритма проверки набора объектов без
предположений о том, почему сценарист выбрал один из них.

У списков обнаружена нетипичная граница. Программа сначала сравнивает индекс
списка с его длиной как unsigned число и отбрасывает только значения строго
больше длины. Равный длине индекс проходит первую проверку, но следующий
проверенный доступ обнаруживает выход за границу и возбуждает C++ exception.
Поэтому в будущем движке это нельзя незаметно заменить на «все неверные
индексы просто дают ложь».

Это статическая реконструкция ветвей, а не доказательство исполнения условия
в работающем оригинале. Сам вызов RVA `0x5180` и внешний object interface не
проверялись динамически; неизвестен и код, который создаёт эти 16-byte записи.
Считыватель `.scr` хранит описатели событий и вложенных записей во внутренних
контейнерах с шагом `0x14` и `0x20` соответственно. На диске же `.scr` использует
переменные поля: имя события задаётся длиной, а вложенная запись содержит
заголовок и список ссылок. Связь этих структур с evaluator-ом не доказана.
Подробные смещения,
виртуальные слоты и границы анализа приведены в
[`приложении о сценарной VM`](../appendices/script-vm.md#evaluator-записей-условий-ai-dll-rva-0x5180)
и [`границах знаний`](../appendices/knowledge-boundaries.md#script-vm).

### Исход миссии и состояние игры

«Конструктор» проверяет захват завода и ангара через `Handler(52)`: сценарий
передаёт логический ID здания и сравнивает текущий клан с кланом игрока.
ID остаётся прежним при смене владельца. Оригинал возвращает `0xffffffff`,
когда объект отсутствует. FParkan сопоставляет ID со вторым словом TMA после
имени ресурса и читает владельца из живого объекта мира.

В сборке GOG этот обработчик находится в `ai.dll` по RVA `0xe0e4`
(SHA-256 `c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`).

В «Полевом лагере» сценарий проверяет, появилась ли шахта у игрока.
Он запрашивает число живых объектов с кодом шахты в своём клане. Склад
и шахта другого клана в этот счёт не входят. Когда число достигает единицы,
сценарий может засчитать третью цель и поставить в очередь следующие реплики.
Запрос описан в [приложении о сценарной VM](../appendices/script-vm.md#периодическое-событие-mission).

В этой же миссии заводская цель зависит от того, сколько роботов появилось
после старта. Сценарий сохраняет исходное число при загрузке и прибавляет к
нему порог, по которому позже проверяет живой состав клана.

После выпуска четырёх варботов сценарий задаёт трём противникам патрули
вокруг двух точек. Сначала он записывает номер робота и координаты
в рабочие переменные, затем отдаёт приказ. FParkan читает значения
в момент приказа, строит путь по областям карты и позволяет патрулю
переходить в бой. Последняя цель засчитывается, когда у вражеского клана
заканчиваются живые роботы. Поддержанный вход VM и параметры патруля
описаны в [приложении о сценарной VM](../appendices/script-vm.md#handler15-typed-target-call-boundary).

Сообщение сценария об успехе или провале проходит ещё один рубеж — обратный
вызов в игровое приложение. У этой границы есть собственные правила: в режиме
отдельной миссии вызов может записать новый исход, а в автоматической демо-игре
та же ветвь подавляется. Повторный сигнал не обязан исправлять соседний флаг
или сохранённый Rust-исход: оригинал решает по своему слову состояния, а не по
сравнению всех полей между собой. Поэтому загрузка карты не означает, что игра
уже перешла в активный игровой цикл; это отдельный шаг запуска. Технические
смещения, начальное состояние и граница проверки описаны в
[`приложении о сценарной VM`](../appendices/script-vm.md#состояние-обратного-вызова-исхода-миссии).

### TRF и preload-данные

TRF-архивы используют несколько потребителей; один подтверждённый путь ведёт
из `Handler(43)` к вычислению стоимости исследования. В проверенной сборке GOG
`CalcFullResearchCost` из `ArealMap.dll` получает таблицу, загруженную через
`MisLoad.dll`. Для этого пути `TRF0` содержит строки по десять сырых `u32`,
`TRF1` — байты флагов, `TRFB` — пары «смещение имени и номер строки», а
`TRF6` — пул строк с нулевыми окончаниями. Слово 8 строки связывает её с
`TRFB` через младшие 16 бит; старшая половина сохраняется как неизвестное
значение. `TRF2` и `TRF3` образуют упорядоченные списки предварительных
исследований, которые читает этот путь стоимости. `TRF4`/`TRF5` образуют
отдельную пару таблиц, но `CalcFullResearchCost` её не использует. Непрозрачные
`TRF7`–`TRFA` остаются в архиве и требуются загрузчику.

Модуль `fparkan-assets` разбирает этот профиль в `ResearchTrfDocument` и
вычисляет пару результатов для одного Unit DAT:

```rust
let table = ResearchTrfDocument::decode(archive_bytes)?;
let cost = calc_full_research_cost(&candidate, &table)?;
```

Расчёт проходит компоненты Unit DAT в порядке дерева. Компонент с нулевым
`kind` завершает весь свой участок вместе с потомками. Для остальных ключ
ресурса ищется среди имён `TRFB`; повтор строки добавляется лишь один раз.
После прямых компонентов алгоритм обходит список `TRF2`/`TRF3` в его исходном
порядке, углубляясь сразу в найденные предварительные исследования. Общая
таблица посещений не даёт повторно добавлять узел и завершает циклы. В `TRF1`
бит 0 означает доступность, бит 1 — изученность, бит 2 — включённую технологию.
Остальные сырые биты и слова не получают игровых имён без отдельного доказательства.

Результат первого native-выхода подписан в отладочной строке как ore и
суммирует слово 1 `TRF0`, второй подписан как power и суммирует слово 0. Каждое
сложение сохраняется как `f32` в порядке найденной последовательности. В
принятом наборе из 23 синтетических тестов оригинальных DLL проверялись
`CalcFullResearchCost` и два AI-предиката; именно вызовы `CalcFullResearchCost`
подтвердили порядок обхода, дедупликацию, циклы, флаги и отсечение дерева.
Две проверки суммы показали чувствительность округления: одна и та же сумма
`1, 2^24, -2^24` даёт `0`, а в другом порядке `2^24, -2^24, 1` даёт `1`.

Эти результаты относятся к синтетическому исследовательскому контексту;
штатный Handler(43) и запуск миссии здесь не проверялись.

Владелец начальной записи исследования — индекс текущего прохода по кланам.
В GOG-сборке `iron3d.dll!FUN_1005ff40` (RVA `0x5ff40`) проходит записи кланов
и вызывает для каждой `FUN_100392e0` (RVA `0x392e0`), которая создаёт AI;
`ai.dll!CreateSuperAI` (RVA `0xf710`) выделяет объект и вызывает конструктор
по RVA `0x1000`, не проверяя наличие сценарного пути. Для исследовательского
пути нужны отдельный флаг включения и непустой `second_resource.path`; наличие
сценарного пакета условием не является. Индекс клана сохраняется в
`descriptor[0]` и переносится в контекст, чтобы связать запрос с AI-данными
того же клана.

Это значение отдельно от аргумента 1 `AddNewObjectToGame`, берущегося из
`GetNetPlayerNum`, и от TMA-тега `second_resource`, задающего число вызовов
AI-слота `+0x38`. Передача поля подтверждена по статическому коду; выполнение
Handler(43) и штатный запуск миссии остаются непроверенными. Технические
сведения и адреса исходных сборок приведены в [границах знания](../appendices/knowledge-boundaries.md).

Полный Rust-загрузчик принимает явный `MissionStartupInput`: время очереди
и отдельный `research_creation_gate`. Режим миссии и имя файла этот
флаг не заменяют. При включённом флаге загрузчик использует уже имеющееся
`MissionAiStartupState` каждого TMA-клана, даже если у него нет сценарного
пакета; путь берётся из второго ресурса как C-строка до первого NUL. Пустой
путь и выключенный флаг пропускают чтение, а не-ASCII байты дают явную ошибку.
Предпросмотр тоже не читает TRF. Клан индексируется по порядку в TMA, а тег
`second_resource` задаёт число слотов AI, не владельца. Если несколько кланов
указывают на один файл, каждый получает отдельно декодированную таблицу со
своими строками TRF0.

```rust
MissionStartupInput {
    queue_time_ms: 100_000,
    research_creation_gate: true,
}
```

Это сохраняет декодированные таблицы и связь с владельцами. Игровой `Init`
затем создаёт отдельный контекст клана и каталог для `Handler(43)`.
Нативные побочные записи при создании контекста пока не воспроизводятся.

Отдельная frozen-матрица непосредственно вызвала chooser GOG `ai.dll` SHA-256
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`: функция
`FUN_10010f90` (RVA `0x10f90`) прошла три guard-case и все 15 проверок.
Конструктор находится в RVA `0x10480`, raw DAT parser — `0x102c0`,
предикаты — `0x115f0` и `0x11530`. Матрица передавала кандидатов в заданном
порядке. Обёртка `Handler(43)` по RVA `0xd54a` загружает каталог через RVA
`0x104e0` и вызывает chooser. В штатных пакетах команда не принимает
аргументов и не записывает результат в переменную. Игровой загрузчик FParkan
создаёт каталог и выбирает первый проект; `Handler(41)` передаёт его лаборатории.
Расчёт цены принадлежит
`ArealMap.dll` SHA-256
`a25f9254ebb339d70e2e07c8121950191e9584ca0858d8e9c2e2b6c671edf6ea`,
`CalcFullResearchCost` RVA `0x16280`; для сравнения x87 был явно задан как
`0x007f`.

`ResearchCandidateSet` держит упорядоченный каталог, выбранный индекс, байт
scan-status и флаг `loaded` каталога; TRF-контекст передаётся отдельно.
При наличии каталога и контекста set-status начинает со значения `1`, затем
перед чтением каждого entry со status `0` становится `0`. Ненулевой entry
пропускается. Первый предикат требует info words 1 и 2, соответствующие битам
TRF1 0 и 2; второй требует words 0 и 2, то есть биты 1 и 2. Второй status
сохраняется в entry, а cost вызывается даже при status `1`. Выбор записывается
сразу, когда second predicate ложен и ore строго ниже текущего минимума,
изначально `f32::from_bits(0x4b18967f)`. Равенство сохраняет первого, NaN индекс не меняет.

В Rust ошибка VFS-чтения и невалидный DAT пропускают entry; неизвестный TRF-
ключ даёт false predicate. Ошибка стоимости `EmptyResearchTable` тоже
пропускает entry и сохраняет его второй status. Остальные ошибки таблицы и
`UnsupportedNonAsciiLookup` возвращаются явно, причём уже сделанные изменения
индекса и status остаются. Общий Rust-предикат может закончить обход раньше
native callback `0x11530`, который продолжает накапливать неиспользуемые float
sums. Первый проход уже проверил enabled keys в той же неизменной таблице,
поэтому подтверждается эквивалентность состояния и выбора для этого входа,
но не callback-trace parity. Это не подтверждение цены на живой миссии или
порядка AI-каталога.

Источник каталога установлен по обёртке `43` и загрузчику: непосредственные
файлы `UNITS\UNITS\AI\*.dat`. В штатном запуске «Третьей части» память
оригинала содержит этот список в порядке имён, приведённых к верхнему ASCII-
регистру. Обычная сортировка по байтам меняет место имён с подчёркиванием.
FParkan воспроизводит наблюдённый порядок через VFS и хранит TRF-контекст
вместе с состоянием выбора для каждого клана. Остальные метаданные записей
и выполнение исследования не следуют из самого выбора проекта.

### Стабильность AI-слоя

`ai.dll`, `Behavior.dll` и `Wizard.dll` побайтно идентичны в Частях 1 и 2. Это
подтверждает, что разделение SuperAI -> Behavior -> Wizard и бинарная
реализация этих трёх уровней не менялись.

Сценарный корпус:

```text
Часть 1: 58 SCR, 58 FML, 29 TRF
Часть 2: 59 SCR, 59 FML, 44 TRF
```

Все TRF являются структурно валидными NRes. Неизменность DLL усиливает вывод о
стабильной VM, но не закрывает instruction grammar `.scr`: для неё нужен
dispatcher/jump-table decompiler. Дополнительные сценарные данные расширяют
differential corpus, но не заменяют анализ VM.

## Control, физика и коллизии

Control превращает желаемое движение в физически допустимое изменение
состояния. World3D владеет жизненным циклом объекта; Terrain предоставляет
поверхность и world queries; Behavior/Wizard задают намерение; Control создаёт
physical controller и collision representation.

Публичная поверхность:

```text
InitializeSettings
LoadControlSystem
LoadPhysicalModel
CreateCollManager
CreateCollObject
```

Модуль импортирует World3D queue/object functions, `Terrain::GetWorld`, часы,
тригонометрию и `g_FastProc`. Это подтверждает его положение между gameplay
object и геометрией мира.

Статическая сверка GOG `Control.dll` уточняет границу, но пока не раскрывает
per-tick solver. PE32 image base — `0x10000000`; exports имеют следующие RVA:

```text
InitializeSettings  0x32260
LoadControlSystem   0x32280
LoadPhysicalModel   0x32580
CreateCollManager   0x325d0
CreateCollObject    0x32600
```

`LoadControlSystem` возвращается `ret 0x20`, следовательно ABI снимает со
стека восемь 32-bit аргументов. Оно выбирает allocation размером `0x668` при
mode `9` и `0x670` для другого mode, создаёт внутренний reader через virtual
dispatch с selector `10`, переносит несколько caller strings в локальные
buffers и передаёт собранную settings-структуру дальше через virtual slot
`+0x08` с key `0x80000020`. Это доказывает loader/configuration boundary и
два layout variants, но не даёт права назвать поля скоростью или acceleration.
`LoadPhysicalModel` аналогично создаёт `0xa0`-byte reader и возвращается
`ret 0x0c`; `CreateCollManager` и `CreateCollObject` возвращают interface
pointer с поправкой `+4` после внутренней инициализации.

Инструкциям x86 в GOG `Control.dll` (`+0x32280`) и caller-у в `AniMesh.dll`
(`+0x32e7`) соответствует ABI `LoadControlSystem(char*, char*, char*, char*,
char*, char*, void*, i32)`: шесть C-string pointers, resource context и mode.
Функция заканчивается `ret 0x20`, то есть снимает все восемь 32-bit stack
arguments; arg7 передаётся constructor-у как context, arg8 выбирает mode.
Прежняя декомпиляция ошибочно определяла шестой строковый аргумент как `u32`.
Остальные exports имеют формы
`LoadPhysicalModel(u32, u32, u32)`, `CreateCollManager(u32)` и
`CreateCollObject(u32, u32)`. `InitializeSettings` получает
`CreateGameSettings()` из World3D и делает virtual call slot `+0x24` с literal
`0x15` и строкой по RVA `0x42478`.

Именно update methods этих private objects, а не пять exports, остаются
следующим объектом динамической трассировки. Поэтому reference movement в
новом runtime намеренно не использует неподтверждённые параметры Control.

### Связь с AniMesh

PE import table GOG `AniMesh.dll` показывает, что это прямой consumer
`CreateCollManager`, `CreateCollObject` и `LoadControlSystem`; других DLL,
которые статически импортируют эти три named exports, не найдено. Внутренний
AniMesh path по VA `0x100032e7` вызывает Control thunks в строгой наблюдаемой
последовательности:

```text
LoadControlSystem  (thunk 0x1001934e)
  -> CreateCollObject (thunk 0x10019348)
  -> CreateCollManager (thunk 0x10019342)
```

После factory calls caller immediately берёт returned interface vtable и
делает дальнейшие virtual calls; это связывает Control с загрузкой
AniMesh/unit components, а не с одной глобальной настройкой процесса. В
частности, `CreateCollObject` получает два stack arguments, а
`CreateCollManager` — один. Предметные значения этих arguments, ownership
private objects и per-tick update slots пока не восстановлены; порядок
создания не доказывает скорость, collision algorithm или AI semantics.

Headless Ghidra call-site decompile уточняет configuration provenance:
AniMesh передаёт в `LoadControlSystem` шесть 32-byte strings из одного
configuration block по offsets `+0x80`, `+0xa0`, `+0xc0`, `+0xe0`, `+0x100` и
`+0x120`, затем resource context и mode из owner `+0x6d8`. Returned Control
interface сразу получает пять virtual calls, связывающих его с owner slots
`+0x158`, `+0x160`, `+0x164`, `+0x168` и `+0x18c`; collision object затем
связывается с `+0x170`. Это достаточное основание хранить будущий Control
component как ordered raw-string/resource provenance, но не для присвоения
этим строкам смысловых имён до трассировки private update methods.

Runtime сохраняет ordered raw Unit DAT records рядом с каждым mission object
draft. Теперь подтверждена связь Unit DAT с descriptor-ом AniMesh, который
передаётся в Control: порядок узлов задаётся деревом immediate-child counts,
а `parent_or_link` попадает в descriptor как локальное поле. Его смысл зависит
от registry type и состояния Control manager-а; в частности, для `INTO` это
локальный индекс устройства, а `EXTO` проходит отдельную ветвь.

### От Unit DAT к Control descriptor

В GOG `ArealMap.dll` (SHA-256
`a25f9254ebb339d70e2e07c8121950191e9584ca0858d8e9c2e2b6c671edf6ea`)
`FUN_10016a10` (RVA `0x16a10`) читает запись Unit DAT в дерево узлов по
`0x78` байт: перед сырыми полями узла находятся указатель и количество детей,
а байты файла копируются начиная с node `+0x0c`. `FUN_10015290` (RVA
`0x15290`) передаёт каждый непосредственный узел корня в `FUN_10014b90`
(RVA `0x14b90`) с начальным parent ID `0`.

Для узла с ненулевым raw kind `FUN_10014b90` формирует descriptor размером
`0x4c`: две строки ресурса копируются из node `+0x0c` и `+0x2c`, поле
descriptor `+0x40` получает parent ID, `+0x44` — DWORD node `+0x50`, а
`+0x48` начинается со значения `-1`. Из-за смещения raw-полей на `0x0c`
node `+0x50` — это ровно `parent_or_link` по смещению `0x44` в записи Unit
DAT. Затем `ArealMap` посылает owner-у событие `6 / 0x80000020` через vtable
slot `+0x34`.

В `AniMesh.dll` (SHA-256
`65659bf67f20e5be77d67a5b2f59968f61b94293143807fa59ca451c560c4f7e`)
dispatcher `FUN_10001370` (RVA `0x1370`) передаёт это событие в
`FUN_10003760` (RVA `0x3760`). Тот выбирает следующий свободный ID, записывает
его в descriptor `+0x48` и сохраняет descriptor в списке компонентов.
Вернувшись после virtual call, `FUN_10014b90` передаёт этот ID как parent ID
рекурсивного обхода детей. Поэтому родительская связь Control descriptor-а
строится по фактически назначенному ID в обходе дерева, а локальный индекс
устройства приходит из `parent_or_link`.

У этого обхода есть ранний выход: если raw kind в node `+0x4c` равен нулю,
узел и его дети пропускаются. AniMesh начинает со служебного root ID `0`, но
из-за пропусков и других записей назначенный ID нельзя в общем случае считать
равным индексу узла или номеру его записи в Unit DAT.

Для registry type `INTO` и других не-`EXTO` значений `FUN_10003760` разрешает
parent ID через Control IID `0x202`, virtual slot `+0x44`, только если parent ID
не равен `-1` и интерфейс IID `0x202` доступен. `Control.dll`
`FUN_1002ecc0` (RVA `0x2ecc0`) возвращает индекс первого устройства, чьё поле
`+0x08` равно этому ID, или `-1`, если совпадения нет; AniMesh прибавляет
возвращённое значение к локальному индексу `+0x44` без отдельной проверки
`-1`. Если parent ID равен `-1` или IID `0x202` недоступен, используется сам
локальный индекс без смещения. Отсутствие устройства с parent ID — отдельный
случай: native path даёт индекс на единицу меньше локального, и Rust-проекции
нужно проверить это поведение явно. `EXTO` проходит отдельную ветвь, поэтому
это правило нельзя распространять на все registry types.

Ветка `EXTO` заполняет другие поля. В `FUN_10003760` RVA `0x3760` и mount
`C4`, и target `C8` сначала равны `-1`. Ветка `EXTO` вычисляет mount и
записывает его только в `C4`; `C8` остаётся `-1`. Поэтому Control добавляет
все typed records такого компонента в конец общей таблицы. Raw
`parent_or_link` здесь выбирает mount-узел, а не строку Control.

`AniMesh.dll` (SHA-256
`65659bf67f20e5be77d67a5b2f59968f61b94293143807fa59ca451c560c4f7e`)
собирает глобальную нумерацию MSH-узлов: обычная корневая модель добавляет все
`N` узлов, `EXTO`-дочерняя модель добавляет `N - 1`, начиная со своего узла `1`,
а `INTO`-компонент не добавляет узлов. `FUN_1000a460` (RVA `0xa460`) выполняет
эту загрузку MSH; `FUN_10005780` (RVA `0x5780`) находит первый глобальный узел
с заданным component ID. Если у `EXTO`-модели только один узел, она не добавляет
глобальных узлов, и поиск первого узла возвращает `-1`.

При добавлении `EXTO` Control отдельно переводит ключи CTLD в пространство
глобальной MSH-иерархии: нулевой ключ заменяется mount-узлом `C4`; ненулевой
ключ сдвигается относительно первого глобального узла компонента только при
`C4 != -1`. Например, если компонент начинается с глобального узла `22`, его
исходный ключ `1` становится `22`. Этот ключ выбирает модельный узел, а не
строку Control. Записи корня остаются в исходном виде.

#### Входной класс контроллера

Таблица устройств и класс самого Control-контроллера выбираются разными
частями загрузки. У полного объекта из Unit DAT старший бит флагов корня решает,
каким путём создать host. В ветви с этим битом объект проходит через Terrain;
эта оболочка передаёт AniMesh native-класс Control `3`. Если бит не установлен,
класс выбирает FourCC записи корневого ресурса: `BTLU` даёт `4`, `BULL` — `9`,
`WPNS` — `2`, `STAT` — `10`, а неизвестный FourCC оставляет класс `0`.

Например, `min_l_n1.dat` хранит флаги `0x80000004`, поэтому его проекция
получает класс `3`. Это аргумент конструктора Control, а не номер строки
устройства и не само по себе включение движения или обновлений. Техническая
цепочка и границы проверки описаны в [приложении](../appendices/script-vm.md#входной-класс-control-при-загрузке-unit-dat).

### Как Control добавляет и переопределяет устройства

В `Control.dll` (SHA-256
`bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`)
`FUN_10008b10` (RVA `0x8b10`) выбирает путь по полю descriptor `+0xc8`.
Значение `-1` запускает цикл по typed records; фабрика `FUN_1002d4b0` (RVA
`0x2d4b0`) создаёт по устройству на запись и сохраняет их порядок. Иное
значение вызывает `FUN_1002d890` (RVA `0x2d890`) только один раз; цикл по
typed-record count в этой ветви отсутствует. Следовательно, подтверждённый
override path применяет первую typed record и не добавляет новый объект.
Так модуль меняет характеристики уже существующего слота, не увеличивая число
устройств. Метки `24` и `29` идут через общий конструктор `0x20800` и читатель
`0x21d50`. Для метки `30` фабрика выбирает класс метки `2`, его читатель
`0x29650` начинает с того же `0x21d50`. Поэтому у всех трёх записей один
двоичный формат, а следующая запись начинается после общего переменного хвоста.
Неизвестный tag в Rust CTLD parser приводит к `Unsupported` и может
оставить typed-record list неполным. Native factory имеет отдельный default
путь `0x20800`, поэтому такой результат парсера сам по себе не доказывает отказ
оригинального loader-а и не позволяет объявить Rust merge полным.

FParkan строит базовую проекцию этой таблицы во время полного mission load для
объектов с Unit DAT. Корневые typed records добавляются в исходном порядке;
`EXTO` тоже добавляет все свои записи с remapped MSH-ключами; `INTO` обновляет
одну строку по `C8`, а при sentinel `-1` добавляет весь список. Preview таблицу
не создаёт. Проекция хранит исходный factory tag, текущий typed record и их
provenance, но не исполняет все tag-specific callbacks и не заменяет полный
Control runtime. Лицензированный `UNITS/BUILDS/MINE/min_l_n1.dat` подтверждает
10 исходных устройств, четыре `INTO`-override по индексам `0..3` и добавление
одной дочерней записи `EXTO` с ключом `22`, всего 11 устройств. Это результат
Rust full-loader теста на оригинальных ресурсах. Ветви C4/C8 и добавление
`EXTO` подтверждены статически по native ASM; отдельный native full-load oracle
для всей таблицы не запускался.

Профиль владельца читается из отдельного блока каждого CTLD сразу после пяти
слов заголовка: это 27 исходных DWORD, начиная с байта `20`. Control выбирает
для владельца только компонент с native ID `0`; его блок остаётся исходной
копией, а те же 27 слов отдельно копируются в изменяемую память владельца.
Поэтому профиль дочернего компонента, даже если его `INTO` обновляет строку
таблицы `0`, не подменяет профиль корня. В Rust `PreparedComponentControl`
сохраняет эти слова без предположений об их типах, а полная Control-проекция
хранит источник, native ID, исходный массив и отдельную начальную копию. Эти
массивы сначала равны; отсутствие CTLD у компонента с ID `0` остаётся явным
`None`, без дочернего fallback или синтетических нулей. Точные native writes и
открытые вопросы о смысле полей приведены в [техническом разборе загрузки CTLD](../appendices/script-vm.md#профиль-владельца-control-при-загрузке-ctld).

Изолированный x86-вектор подтвердил общий проход `Control.dll!FUN_1000fac0`
(RVA `0x0fac0`): этот шаг FAC0 начинает с исходного profile word 26, затем
заполняет три накопителя владельца и поле `+0x20` provider rows. Для него
выбираются два сырых слова `Slot68` через `Node38` state 0 / LOD 0, учитываются
cache tag 27 и устройства таблицы. Смысл `Slot68` и итоговых чисел не
установлен; мы не называем их массой или площадью.

Для обычной начальной загрузки AniMesh создаёт scale `[1, 1, 1]`. Проверенные
обработчики модели, FX и столкновений до FAC0 его не меняют. Поэтому первый
проход получает значения конструктора, а не scale, записанный в TMA. Отдельные
маршруты создания и последующее размещение объекта остаются другими путями.

### Начальная FCA0-проекция профиля

После FAC0 оригинальная Control выполняет второй проход FCA0 и обновляет только
выбранные слова отдельной изменяемой копии. Условие раннего выхода проверяет
**класс владельца Control**: класс `9` сразу пропускает FCA0. Это не тег
фабрики отдельного устройства `9`: в
лицензированном mine-профиле есть устройство с factory tag `9`, но класс
владельца равен `3`, поэтому FCA0 выполняется. Любой известный класс, отличный
от `9`, включая `0`, идёт по общему пути. Если Rust не смог вывести класс из
ресурсной цепочки, он возвращает отдельный статус; это означает отсутствие
проекции в Rust, а не отсутствие класса в оригинальной DLL.

На начальном пути конструктор задаёт scalar и два средних значения как `1.0`.
Устройства читаются с конца списка;
в сумму попадают только записи с текущим descriptor tag `5`. Их `0xe00`
значение использует ключ устройства и `current_type1` соответствующей строки
provider. Читатели фабрик `5` и `26` общие; для текущего tag `5` формула
`coefficient[0] * provider.current_type1` не использует ни multiplier `M`, ни
descriptor word `8`. Ветки current tag `26` дополнительно умножают на `M`, но
не участвуют в сумме FCA0, которая фильтрует текущий tag `5`.

Упрощённая карта зависимостей показывает, почему важен порядок обхода и какие
слова меняются; строки формул сами по себе не задают порядок native-вычислений:

```text
sum = 0
for index in reverse(0..device_count):
    if current_tag(index) == 5:
        sum = f32(sum + query_e00(index))

mean = (mean_a + mean_b) * 0.5
weight = mean * sum
r = current[26] / original[26]
A = (r + 1) * 0.5
B = r * 0.75 + 0.25
current[0..3] = 2 * original[0..3]
current[6..9] = native_signed_cap(original[6..9] * scalar * weight * A)
current[9..12] = 2 * (original[9..12] * weight * B)
```

Порядок x87 операций и spill границы приведены в техническом описании. Нативный
ограничитель срабатывает, когда исходный cap с сохранённым знаком меньше
`abs(value)`. Тогда проверяется `value < 0`: отрицательное значение даёт `-cap`,
иначе возвращается `cap`; ветвь `else` включает `+0` и `-0`. Поэтому
отрицательный cap способен изменить знак выхода.
Здесь в query передаётся порядковый номер устройства; его getter уже сам
использует ключ устройства для выбора строки provider. Точный порядок чтений,
промежуточных записей и проверки приведён в
[техническом разборе FCA0](../appendices/script-vm.md#изолированный-проход-fca0).

Rust хранит исходные слова отдельно, считает кандидата из копии после FAC0 и
публикует слова FCA0 только после полного успеха. Статус `load_projection`
остаётся результатом FAC0, а `fca0_projection` отдельно сообщает исход
следующего прохода; ошибка FCA0 сохраняет уже подготовленную FAC0-копию.
Обычный путь подтверждён при x87 control word `0x007f` для конечных normal-or-zero
входов и промежуточных значений. Реализация не утверждает поддержку
денормализованных, NaN, бесконечных или выходящих за диапазон промежуточных
значений.

### Пределы движения после повреждения

Изменение количества в узле отмечает владельца флагом `+0x598`. На следующем
ресурсном такте Control сначала обновляет профиль, затем распределяет бюджет
устройств: в той же GOG-сборке это вызовы RVA `0x12a40` и `0x2d340` из
`0xbcf0`. Без флага изменения первый проход сразу возвращается. Поэтому
попадание не меняет предел движения посреди текущего шага.

Обычная ветвь `0x12a40` вычисляет два средних нормализованных состояния узлов.
Группы задают биты `0x20` и `0x40` исходного NDP-дескриптора; узел с обоими
битами участвует в обеих группах. Пустая группа сохраняет прежнее среднее.
Оба значения передаются в уже описанную FCA0-проекцию. Сам предел зависит
также от состояния узла, к которому привязано устройство хода. У четырёх
размещённых роботов AutoDemo это корневой узел, поэтому обычное попадание в
корпус уменьшает и последующий запрос скорости патруля.

Вызов оригинальной Control.dll RVA `0x12a40` при x87 control word `0x007f`
подтверждает эту цепочку. При исходном пределе 20, сумме устройств хода 0,75
и средних 0,25 и 0,75 новый предел равен 7,5. Средние 1 и 0,5 дают 11,25.
Повторный вызов без флага изменения сохраняет результат и не опрашивает
устройства. В Rust исходный профиль остаётся неизменным; новый профиль и
средние публикуются вместе после успешного расчёта.

Если критических узлов больше одного, решение принимает сумма их состояний;
общий порог количества используется только при нуле или одном таком узле.
Проход с аварийным повреждением пока останавливается явно: он требует
сигнализации и дополнительного изменения количества в узлах. Динамический
расход ходовой ещё не связан с полным контроллером движения. Заряд орудий
и их пополнение уже участвуют в общем бюджете владельца.
Отчёт считает ресурсные проверки, обновления и отказы по объектам и
сохраняет эти числа после уничтожения робота.

Оригинальная FCA0 и выбранные getters совпали на изолированном x86-векторе;
точные raw bits, module hash, вызовы и ABI приведены в технической главе.

Игнорируемый corpus-тест полного загрузчика на оригинальном
`UNITS/BUILDS/MINE/min_l_n1.dat` теперь проверяет class `3`, успешный статус FCA0,
все 11 устройств, 25 provider rows, FAC0 snapshots и девять выходных слов.
Для mine-профиля первый триплет FCA0 даёт `[2, 2, 2]`, два следующих — нули;
не все целевые слова обязаны отличаться от исходных. Тест также сохраняет все
11 устройств, 25 provider rows и результаты FAC0. Это проверка Rust loader-а
на оригинальных лицензированных ресурсах, а не сравнение полного native Unit
DAT load или gameplay. Поздние изменения means/scalar, activation, tick и
placement остаются отдельными открытыми вопросами.

Для tag `19` фабрика создаёт объект с его исходными классом и vtable. Базовый
конструктор `FUN_100218b0` задаёт multiplier `+0x4c = 1.0`. Override через
`FUN_1002d890` вызывает у выбранного объекта vtable slot `+0x1c`, то есть
`FUN_10021d50` с флагом инициализации `0`. Этот вызов не создаёт объект и не
заменяет класс или vtable. Он сохраняет уже существующий ключ `+0x04`; сохраняет
текущее значение multiplier `+0x4c` (которое могло измениться после
конструктора); и копирует коэффициенты из CTLD в блок `+0x54`. Поле `+0x50`
обновляется лишь когда слово записи `+0x18` не равно `-1`. Сопоставленные
записи значений прибавляются к текущим полям объекта `+0x1c/+0x20`, а не
сбрасывают их. Поэтому «переопределение» здесь означает обновить часть данных
того же устройства, с ограничениями конкретного метода.

factory tags `2`, `3`, `4`, `5`, `8`, `9`, `10`, `15`, `19`, `21`, `25` и `27`.

component ID и multiplier `2.5` при копировании новых коэффициентов. Для новых

| `8` | `0x24310` | `0x3c800` | `5` |
| `10` | `0x26470` | `0x3ca20` | `0x2000` |
| `27` | `0x218b0` | `0x3c528` | `0` |

У всех строк таблицы multiplier начинается с `1.0`. Tags `3` и `5` проверены
через настоящую фабрику `0x2d4b0`; tag `3` попадает в её default-ветвь.
Общий reader `0x21d50` сохраняет переменный хвост: две map-строки `7` и `9`
и дополнительная строка `fx` возвращают cursor `record + 0xbf`.
Слово CTLD `+0x18 == -1` сохраняет фабричное `+0x50` и при INTO-замене.

Ветвь фабрики `0x2d4b0` направляет factory tags без отдельного случая в
конструктор `0x20800`; его vtable использует общий reader `0x21d50` в slot
`+0x1c`. Поэтому common-field override применяется и к этой default-семье,
включая tag `6`; Rust-тест проверяет его вместе с тегами `12` и `13`. Tags
`1`, `17`, `26` и `30` остаются явными границами: фабрика выбирает для них
отдельные классы, а проверки текущей реализации ещё не покрывают их полное
setter-поведение.

У tag `2` slot `+0x1c` указывает на обёртку `0x29650`. Она вызывает тот же
reader, затем сохраняет selector `1` в `+0x120`, округляет selector `0` через
x87 `FISTP` в `+0x124` и заново обнуляет массив `+0x12c` по накопленному числу
map-строк. Native тест получает `1.25`, округление `3.5 → 4` и четыре нулевых
элемента после повторного override. Rust хранит заряд `+0x120` в таблице
Control и связывает его с банком стрельбы по исходным компоненту и номеру
записи; число патронов и фазы пока хранятся в банке. Slot `+0x24`
этого класса (`0x29940`) проверен только с неизменной пустой парой ресурсов.
Tag `9` проверяется без FX-хоста (`+0x3c == 0`) и без map-строк; его FX-путь
этим опытом также не подтверждён.

Полный Rust loader на исходном `MISSIONS/Autodemo.00/data.tma` строит доступные
таблицы для всех восьми объектов: четыре робота содержат `14`, `12`, `15`, `13`
устройств, затем два завода по `12` и два генератора по `11`. Это проверка
подготовки таблиц на настоящих ресурсах, а не сравнение полного игрового Control
с запущенным оригиналом.

Статический разбор глобального Control interface показывает aggregate getters
`1/2` (`FUN_1002b410`, RVA `0x2b410`) и setter `1` (`FUN_1002ba30`, RVA
`0x2ba30`) для текущего descriptor tag `19`. Getter `1` складывает ответы
виртуального selector `0x200` в числитель и selector `0` в знаменатель; getter
`2` возвращает сумму selector `0`. Для обычного factory tag `19` эти ответы
равны `coefficient * multiplier` и `coefficient`, то есть отношение сводится к
`sum(coefficient * multiplier) / sum(coefficient)`. У factory tag `9` selector
`0` умножает коэффициент на отдельное поле `+0x11c`, тогда как selector `0x200`
использует коэффициент и multiplier; эта особая база меняет знаменатель.
Обработчик factory tag `9` расположен в Control RVA `0x255c0`, а его конструктор
RVA `0x25460` задаёт `+0x11c = 1.0`. При встрече отрицательного ответа selector
`0` getter `1` сразу возвращает `1.0`, а getter `2` — этот ответ. Если подходящих
записей нет или сумма базы неположительна, getter возвращает неуспех без записи
результата. Setter пишет multiplier `+0x4c` только устройствам с текущим
descriptor tag `19` и положительным selector-0 ответом; пустой набор возвращает
успех. Фильтр использует **текущий descriptor tag**, который может измениться
при `INTO`, а виртуальный вызов остаётся методом исходного factory-класса.

Этот путь проверяется native x86 oracle на оригинальной `Control.dll` указанной
выше: искусственные factory/descriptor пары `9`, `15` и `19` покрывают setter,
отрицательные ответы, округление и тег `9` с scale `0.5`. Для factory tag `25`
его vtable slot `+0x10` статически указывает на общий getter RVA `0x21d00`, но
отдельный aggregate oracle этот класс не запускал. Rust хранит начальный scale
factory `9` и предоставляет `query_loaded_mission_control_resource` для selector
`1`, `2` и `15`, а также `set_loaded_mission_control_multiplier` для setter-а
`1`. Вызовы сначала проверяют живой `ObjectHandle`, затем обращаются к таблице
этого объекта из полной загрузки миссии. Синтетические тесты проверяют границы
пустой таблицы, нулевого знаменателя, отсутствующих объектов фабрик и чисел за
диапазоном нормального `f32`; лицензированный тест сверяет реальные descriptor
tags и получает для `min_l_n1.dat` сумму `16` и отношение `1` до setter-а.

Сырой селектор `0x0f` соединяет два ранее созданных объекта владельца: у строки
с `factory_tag = 9` берётся коэффициент и его текущий множитель, а у строки с
`factory_tag = 21` — шесть текущих `coefficient_bits`. `INTO` может поменять
`descriptor.tag`, не заменяя объект фабрики, поэтому query выбирает последние
строки по `factory_tag`, а не по текущему tag. Если любой объект фабрики
отсутствует, ответ — `None`. Иначе шесть коэффициентов складываются с индекса `5`
к `0` с округлением до `f32` после каждого сложения; результат умножается на
selector `0` фабрики `9` (`coefficient_bits[0] * class9_selector0_scale_bits`).
Общие `multiplier_bits`, `node_provider_status` и `native_word_50_bits` в этой
формуле не участвуют.

Лицензионная проверка загружает AutoDemo с явно переданными
`MissionStartupInput { queue_time_ms: 100_000, research_creation_gate: false }`
и вызывает `query_loaded_mission_control_resource(..., 15)` для исходных
объектов `0..5`; для `6` и `7` Rust возвращает `None`, потому что не хватает как
минимум одного объекта фабрики. Native-биты для `0..5` приведены в технической
главе. Проверка сверяет результат исходного геттера на снимке входных полей,
подготовленном Rust. Время и флаг заданы самим тестом; они не доказывают
начальный режим запуска AutoDemo в оригинале и не являются захватом его фабрик
или состояния объекта Control.

Отдельный native setter selector `17`, tag-specific методы прочих factory tags,
их внешние эффекты и вызов из регулярного шага Behavior здесь не моделируются.
Числа должны оставаться конечными и нормальными либо точным нулём; произведения
и суммы за поддерживаемым диапазоном `f32` возвращают явную ошибку, а не
подменяются нулём или `None`. При проверке диапазона Rust сначала оценивает
границы в `f64`, затем выполняет каждую операцию в `f32`; это сохраняет
пошаговое округление этого getter-а, но не эмулирует весь x87 execution state.

Отдельная ветка того же GOG `AniMesh.dll` показывает, когда создаётся Behavior
для host object. В `FUN_10002ff0` (RVA `0x2ff0`, SHA-256
`65659bf67f20e5be77d67a5b2f59968f61b94293143807fa59ca451c560c4f7e`) вызывающая
сторона запрашивает IID `0x204` и сохраняет интерфейс в поле `+0x168`. Затем
отдельный импорт `GetQueue()` возвращает объект очереди; вызов метода через его
vtable slot `+0x30` даёт результат, который проверяется на ненулевое значение.
Только при ненулевом результате host class `3` вызывает
`CreateBehaviour(0, 0, self)` (RVA `0x34bd`); class `4` передаёт в
`CreateBehaviour` адреса полей prototype `+0x140` и `+0x160` (RVA `0x3426`).
Семантика метода slot `+0x30` здесь не установлена. Это подтверждает только
такую ветку и эти два класса; другие фабрики, нулевой результат и отложенные
spawn сюда не входят.

### Один запрос Control для ресурсного устройства

В CTLD запись tag `26` задаёт ресурсный множитель, но текущее значение
поставщика живёт в runtime state Control. GOG `Control.dll` (SHA-256
`bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`)
`FUN_10021d00` (RVA `0x21d00`) реализует getter selector `0x300`. Его фиксированное
слово `+0x2c` становится `fixed_words[11]` при копировании записи RVA `0x21d50`;
`fixed_words[1]` — ключ строки NDP. В объекте Control getter использует ключ
`+0x04`, provider interface `+0x44`, множитель `+0x4c` и коэффициент `+0x54`.
Provider interface направляет selector `1` и ключ в Control RVA `0xdc40`, где
читается текущее type-1 значение выбранной строки. Затем selector умножает
сначала provider на коэффициент, после чего на множитель: `provider * base *
multiplier`. Коэффициент приходит из CTLD; NDP связывает ключ с описанной
строкой. Native loader создаёт для этой строки отдельное runtime-состояние: у
`Control.dll` (та же сборка, SHA-256
`bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`)
`FUN_1000b240` (RVA `0xb240`) строит 11 слов строки provider и ставит её
selector-1 поле `+0x14` в `1.0`. `FUN_10008b10` (RVA `0x8b10`) выбирает строки
NDP, а `FUN_1000a100` (RVA `0xa100`) добавляет их в общую таблицу с шагом
`0x2c`; getter `FUN_1000dc40` (RVA `0xdc40`) использует ключ устройства как
индекс этой таблицы. Для корня загружаются все строки. `INTO` не добавляет
строк, а примонтированный `EXTO` пропускает свою первую строку. Пустая
таблица такого `EXTO` не содержит строки, которую native loader должен
пропустить, поэтому Rust оставляет provider lookup недоступным; sidecar с одной
строкой даёт пустой вклад. Если mount узел не разрешился, строки этого `EXTO`
в таблицу не попадают. Это отдельная
последовательность provider-строк: её длина берётся из NDP, она не дополняется
до числа узлов MSH и не участвует во второй перенумерации ключа.

Индексный selector `0x400` выдаёт значение выбранной строки provider как есть.
Сначала общий индекс устройств выбирает дескриптор, затем его ключ выбирает
строку NDP; это разные номера. Результатом становится текущее type-1 значение
этой строки, а не запас `CurrentOre`, предел или значение после умножения на
коэффициент и `M`. Например, provider-строка с `0.625` возвращает `0.625`, а
записанный в ней ноль тоже остаётся успешным результатом. Rust использует уже
подготовленную таблицу и сообщает отдельную ошибку, если provider-таблица или
строка по ключу недоступна. Этот запрос читает снимок состояния и сам не меняет
таблицу и не запускает её обновление.

У правила есть два разных подтверждения. Разбор AutoDemo нашёл восемь таблиц
Control и 100 устройств; все 100 значений по ключам устройств в этом корпусе
равны `1.0`, поэтому Rust-проверка подтверждает реальные ключи и доступность
строк, но сама по себе не различает выбор по ключу и по номеру устройства.
Отдельная x86-проверка исходного `Control.dll` включала шесть вызовов на
синтетической таблице, где значения строк были заданы вручную и различались.
Например, при номере устройства `2`, ключе `1` и нулевом слове
`device+0x50` оригинал вернул `0.625` из выбранной строки. Точные биты ответов
приведены в [техническом разборе](../appendices/script-vm.md#индексный-control-getter-сырой-селектор-0x400).
Этот опыт не создавал оригинальные factory-объекты и не исполнял полную миссию:
полный интерфейс IID `0x204`, интеграция Behavior и игровое поведение остаются
непроверенными.

В цепочке добычи руды оригинал использует описанный выше selector `0x300`.
В той же сборке `Behavior.dll` (SHA-256
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`)
`FUN_100186b0` (RVA `0x186b0`) перечисляет устройства типа `0x1a`, а
`FUN_100198e0` (RVA `0x198e0`) суммирует успешные запросы IID `0x204` с selector
`0xe00`. В парной `Control.dll` выше `FUN_1002bb40` (RVA `0x2bb40`) для типа
`0x1a` вызывает selector `0x300`, описанный в этом разделе. Затем Behavior query
`0x1002` (RVA `0xa490`) умножает полученную сумму на поле `+0x58`
`Transfer_Ore_OffBoard` блока `+0x820`; отдельный selector `0x1005` возвращает
`+0x60` `Transfer_Power_Out`. Имена регистрируются в RVA `0x22e20`, а конструктор
RVA `0x22d90` задаёт начальные значения 5.0 и 100.0. Восемнадцать точных class
codes выбирают записи `.var` из `behpsp.res`: например, `0x80000004` выбирает
`prof_mine.var`, `0x80000002` — `prof_generator.var`, а три кода bunker-класса
выбирают `prof_bunker.var`. Таблицу этих соответствий задаёт mapper
`FUN_10008a80` (RVA `0x8a80`) в Behavior.dll SHA-256
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`.

У бинарной строки `.var` есть имя, индекс типа, размер и две области данных.
Native parser RVA `0x49fa0` читает запись, binder RVA `0x49090` связывает её с
зарегистрированным полем, а apply-loop RVA `0x49170` копирует в поле именно
вторую область. В профиле используются точные C-string имена
`Transfer_Ore_OffBoard` и `Transfer_Power_Out`; регистр учитывается, первый
совпавший ряд побеждает. Rust ограничивает чтение исходной записи NRes её
границами и сохраняет значения как исходные 32-битные слова у соответствующего
`ObjectHandle`. Разбор профиля для полной миссии завершается до создания нового
мира: отсутствие или повреждение профиля известного класса прерывает загрузку,
не подменяя предыдущую миссию. Если mapper не знает class code, остаются
конструкторские значения 5.0 и 100.0; это не догадка о неизвестном профиле.
Preview не загружает профили.

При вычислении `0x1002` native `FUN_100186b0` (RVA `0x186b0`) добавляет в список
только текущие Control descriptor-и tag `26`, после чего
`FUN_100198e0` (RVA `0x198e0`) суммирует их успешные `0xe00` запросы. FParkan
делает то же для загруженной таблицы в её исходном порядке и затем умножает
сумму на профильный `Transfer_Ore_OffBoard`. Записи tag `5`, `10` и `21` в общей
таблице в этот список не попадают. Это фильтр самого `0x1002`, а не ограничение
доступности общего Control-запроса `0xe00`: он поддержан для текущих descriptor
tags `5` и `26` с factory tags `5` и `26`. Owner query получает порядковый
номер устройства; getter использует ключ этого устройства, чтобы выбрать строку
provider. Для current tag `5` значение равно `coefficient[0] * provider`, без
множителя `M` и descriptor word `8`; для current tag `26` результат равен
`provider * coefficient[0] * M`. Лицензированный тест загружает
оригинальные CTL/NDP и полную миссию с этим Unit DAT. В установленном
`min_l_n1.dat` class word равен `0x80000004`, поэтому исходный прогон выбирает
`prof_mine.var`. Для проверки другого отображения второй прогон оставляет тот же
TMA и компоненты, но во временном VFS заменяет слово класса заголовка DAT на
`0x80000002`; это тестовая подмена, а не содержимое лицензированного файла.
Профиль mine даёт `Transfer_Power_Out` 0.0 и `Transfer_Ore_OffBoard` 1.0;
оригинальный профиль генератора — 10.0 и 0.0 соответственно. Для исходного
tag-26 ряда получается `1.0` provider × `1.0` coefficient × `1.0` multiplier;
профиль mine умножает эту сумму на `1.0`, поэтому selector `0x1002` возвращает
`1.0`. Эти числа описывают начальное состояние после конструкторов.
Сами запросы читают текущую долю provider; отдельное прямое изменение строки
уже может изменить ответ, хотя полный игровой Control tick ещё не исполняется.

У Control есть и начальные сведения о модели узла, но их таблица не совпадает
с NDP. Sidecar задаёт состав и порядок provider-строк, а поле type-1 `+0x14`
получает начальное значение `1.0` от нативного конструктора. AniMesh отдельно
собирает глобальный список MSH-узлов. При создании строки Control берёт
mesh-состояние по её порядковому номеру в общей таблице provider, а не пытается
угадать пару по локальному номеру строки sidecar-а. Например, после 22
корневых строк номер 22 указывает на первый глобальный узел присоединённой
`EXTO`-модели, который
происходит из её локального узла `1`.

В снимке это необязательное поле: `None` означает, что для данного номера не
удалось получить MSH-узел; исходные запросы к NDP от этого не исчезают. Поэтому
начальное значение и поза модели остаются отдельными частями состояния:

```rust
initial_mesh_state: Option<MissionControlNodeInitialMeshState>
```

Внутри снимка хранятся родительский индекс, переведённые флаги Control и число
начальных стадий. Узлы корневой модели добавляются все, а присоединённая `EXTO`
начинает с локального узла `1`. Это описывает исходную настройку. Отдельный
API уже пересчитывает стадию одного узла, но полный игровой Control tick
пока не исполняется.

На той же начальной стадии Control вычисляет количество строки по NDP
`max_volume`. Для загрузки Unit DAT проверенные множители равны `1.0`, поэтому
количество совпадает с исходным значением NDP. Оригинал начинает с одинакового
текущего и последнего обработанного количества. Rust оставляет исходное число
в `initial_amount_bits`, а текущее и обработанное количество хранит отдельно.
Вместимость при этом берётся из NDP; исходный снимок не заменяет её. В лицензированном `min_l_n1.dat`
проверены, например, root row `0` со значением `1.0` и строка `EXTO` с local
row `1` в общей позиции `22` со значением `6000.0`.

Для одной строки перенесён прямой путь `Control.dll+0x10f30` с выключенным
флагом накопления анимационного изменения. API
`apply_loaded_mission_control_node_delta` принимает живой объект, глобальный
ключ строки и добавку. Например, у строки с максимумом `100` и количеством
`40` добавка `20` даёт количество `60` и долю `0.6`. Переполнение ограничивается
максимумом, отрицательный результат — нулём; при нуле ставится флаг истощения
`0x10`, а пополнение снимает его. Общий итог изменяется именно на разницу
нового и прежнего количества:

```rust
let amount = (previous + delta).clamp(0.0, maximum);
let total = (total + (amount - previous)).max(0.0);
let ratio = amount / maximum;
```

Это три отдельные операции над `f32`, с проверкой поддерживаемого численного
диапазона до записи состояния. Исходные `initial_*` поля сохраняются;
`processed_amount_bits` тоже не меняется, поскольку его обновляет другой
нативный проход — пересчёт стадий. Публикация selector `0x200` теперь применяется
к CPU-состоянию соответствующего узла модели. Результат
`ControlNodeProviderPublication` описывает уже выполненную запись. Пересчёт
стадий и вывод изменённой модели в окно этим API ещё не запускаются.

У AniMesh есть собственное поле значения узла, отдельное от доли Control.
Конструктор `AniMesh.dll+0x123e0` начинает его с `1.0`, а видимую стадию — с
`0`. Callback `+0x5750` при selector `0x200` записывает число в поле `+0x124`
строки модели с шагом `0x130`, не меняя её стадию `+0x1c` и соседние узлы.
Native oracle соединяет исходные `Control+0x10f30` и `AniMesh+0x5750`; между
ними стоит только запись диагностической трассы. Прямая добавка `20` к
количеству `40` из максимума `100` записывает `0.6` и в provider, и в узел
модели. Эти поля нельзя объединять: наследование родительской доли в отдельном
стадийном проходе меняет provider, не повторяя callback `0x200`.
В Rust `mesh_state` хранит это отдельное значение и видимую стадию;
неразрешённый узел прерывает изменение до записи остальных полей.

Истощение корня либо узла с критическим флагом `1` дополнительно ставит
маркер Control `0xfffe`. Для статического класса `3` этот путь завершается
после записи количества и доли: он не запускает таймер удаления, не посылает
уведомление Behavior и не обнуляет остальные узлы. Например, при количествах
`[100, 40]` истощение корня оставляет `[0, 40]`, а истощение критического
дочернего узла — `[100, 0]`. Такую ветвь использует бункер в штатной миссии
`CAMPAIGN.04/Mission.02`: последние попадания теперь доводят его корневое
количество до нуля. Строение остаётся в мире; это ещё не переключение модели
на руины. При ремонте снимается флаг `0x10`, но маркер `0xfffe` сохраняется.

Ветвь истощения других классов без уже установленного маркера пока возвращает
ошибку без изменения состояния: ей нужны уведомление о гибели и таймер.

Стадия пересчитывается отдельным вызовом
`update_loaded_mission_control_node_stage`. Для трёх состояний доли `1`, `0.5`
и `0.1` выбирают стадии `0`, `1` и `2`. Нулевая доля даёт служебную стадию
Control `3`, но в модель записывается последняя видимая стадия `2`. Поэтому
`current_stage` и `mesh_state.visible_stage` хранятся отдельно. Флаги `4` и `8`
могут брать соответственно долю или стадию родителя; доля самой модели этим
пересчётом не переписывается.

После успешного вызова обработанное количество становится равным текущему,
даже если стадия осталась прежней. Истощённые защищённые узлы сохраняют
нативный ранний выход и не обновляют этот снимок. Неизвестные parent/count,
неподдержанные lifecycle-вызовы, FX и пересчёт геометрии на границе истощения
возвращают ошибку до записи. Аргумент `update_effects` сохраняет нативный смысл:
его нельзя молча отключать при включении полноценного игрового цикла.

На настоящем двухстадийном узле `min_l_n1.dat` тест уменьшает количество вдвое,
явно вызывает стадийный API без FX и получает Control stage `1`, видимую стадию
модели `1` и обновлённое обработанное количество. Это проверка отдельной
операции на ресурсах, а не переключение кадра в игровом окне.

На исходном `min_l_n1.dat` прямое уменьшение количества строки ресурсного
устройства вдвое меняет ответы `0xe00` и Behavior `0x1002` с `1.0` на `0.5`.
Обычный последующий шаг runtime сохраняет это состояние. Это воспроизводимый
тест связки загрузки и запросов, но пока не автоматическое изменение через
clock Control.

После загрузки количество в строках может меняться. Контроллер распределяет
добавку либо пропорционально свободному месту, либо по очереди: при максимумах
`[30, 60, 50]`, текущих значениях `[10, 20, 0]` и добавке `22` первый способ
даёт `[14, 28, 10]`. При вычитании последовательный способ начинает с последней
строки. Пропорциональное вычитание делит запрос по текущим количествам.
У каждой изменившейся строки есть отдельный накопитель изменений количества: он
получает фактически применённую разницу, а не исходный запрос.
Большие суммы округляются в двоичном формате. Поэтому после нескольких
маленьких изменений общий запас иногда оказывается чуть больше первоначальной
ёмкости; оригинал продолжает считать с этой отрицательной разностью, а не
исправляет её отдельным правилом.

У строк есть и связи с родительскими узлами. Нативный `Control.dll` сначала
обновляет запрошенную строку через `0x11220`, затем `0x11130` ищет её детей
среди строк с большим индексом. Каждый найденный ребёнок обновляется вместе со
своим поддеревом, и только потом обход продолжается со следующим соседом.
Например, для родителей `[-1, 0, 0, 1, 3]` порядок строк становится
`1 → 3 → 4 → 2`: сначала весь первый участок дерева, затем его сосед.

Стадия увеличивается, когда доля ресурса уменьшается. Для числа вариантов
`count` внутренняя стадия вычисляется как `count - ceil(f32(count * ratio))`,
а видимое значение ограничивается диапазоном модели. Например, при трёх стадиях доли
`[0.1, 0.4, 0.5, 1, 0]` дали `[2, 1, 1, 0, 3]`; последнее значение — sentinel
истощения, а в модель передаётся индекс не выше `count - 1`. Нативные проверки
подтвердили арифметику и порядок обхода.

После обновления родителя Control сравнивает его старую стадию с новой и
проверяет флаг истощения `0x10`. Если стадия выросла либо строка истощена,
количество каждого ребёнка полностью уменьшается тем же путём, что и обычная
добавка ресурса. Для ребёнка без защитной маски родительские флаги `0xc0`
задают флаг `0x80`; в обычной ветви переход ставит `0x100` при ухудшении и
очищает у ребёнка `0x80`. Маска `0x140` запрещает только изменение этих флагов:
уменьшение количества и рекурсивный вызов всё равно выполняются. Дочерние
стадии пересчитываются и тогда, когда родитель не ухудшился.

Выбранная стадия также задаёт, какие данные MSH попадают в пересчёт видимости.
У одного синтетического узла первый слот давал `[42, 330]`, а слот другой стадии —
`[102, 570]`. В проверенных векторах одинаковые данные при скрытии и повторном
включении восстановили суммы; переходы с разными слотами — нет. Эти проверки
исполняют исходные DLL на тестовых строках, но не являются запуском Control на
полной миссии.

В Rust `update_loaded_mission_control_node_stage` сохраняет отдельный шаг одной
строки, а `propagate_loaded_mission_control_node_stage` обновляет строку и её
поддерево в том же порядке, что native `0x11130`. Весь снимок provider-таблицы
публикуется только после успешной обработки всех потомков. Если позже по обходу
понадобится неизвестная связь узлов, lifecycle, FX или пересчёт видимости,
операция сообщает об этом и оставляет снимок без изменений. Эта CPU-проекция
ещё не подключена к игровому Control clock или выводу модели в окно.
Прямой путь изменения количества остаётся отдельной операцией.
Подробные границы приведены в [техническом приложении](../appendices/script-vm.md#родители-стадии-и-видимость-provider-узлов).

Для точного повтора важен порядок округления. При исходных значениях `[2^24, 2]`
и запросе `-1` оригинал сначала складывает общий итог с изменением, затем
вычитает прежний итог. Из-за округления фактическое изменение получается `-2`.
Rust переносит этот порядок, сохраняет native накопитель каждой строки и
запускает обязательный проход стадий с effects. Если ему нужны ещё не
реализованные FX или lifecycle-вызовы, таблица остаётся без изменений. Эти
операции обновляют только CPU-снимок и пока не подключены к игровым часам Control.

Распределение по бюджету тоже доступно как отдельный CPU-вызов
`advance_loaded_mission_control_budget`. Он сначала собирает положительные
ставки, затем обслуживает категории в исходном порядке и передаёт каждому
устройству его долю. Например, при запасе `40/100`, доле `0.4` и интервале
`0.5` секунды tag 19 может принести `0.1`, а tag 15 запросить `0.2`.
Потребитель получает половину запроса: запас становится `40.1`, доля — `0.401`,
а множитель генератора уменьшается до `0.75`. Хотя генератор может стоять раньше
в массиве, его обновление перечитывает уже изменённую долю после обслуживания
категории tag 15. Этот явный вызов хранит также две выходные ставки `+0x5dc` и
`+0x5e0`, но сам по себе ещё не запускается игровыми часами.
Помимо класса `15` и генератора `19` поддержан класс `9`: он считает ставку
через шесть собственных значений и при распределении обновляет их вместе с
накопленными изменениями. Например, для доли provider `0.4`, интервала `0.5`,
`B = 0.2`, коэффициентов `C0 = 0.75`, `C1 = 0.6`, `C2 = 2` и масштаба
`1.25` исходная ставка имеет биты `0xbeae147b`; после полного выделения
обновлённые шесть значений совпадают с native побитно.

Несколько фабричных классов используют общий callback: ставка равна
`-(dt * B)`, а обновление записывает долю выделения в множитель. К этому
семейству относятся фабричные теги `12`, `13`, `25` и `21`, а также другие
классы, которые исходный диспетчер направляет в фабрику по умолчанию. Текущая
категория читается из descriptor: её native map подтверждён только для тегов
`0..=34`. Неподдержанный специализированный callback, недоступный provider или
неподдержанное число останавливают шаг без частичных изменений.

У фабричного tag `26` ставка складывается из базового значения устройства и
изменяемой добавки. Затем сумма умножается на прошедшее время:

```text
rate = -((B + extra) * dt)
```

Например, при `B = 0.2`, `extra = 0.3` и `dt = 0.5` устройство запрашивает
`0.25`. Если доступный бюджет равен `0.125`, оно получает половину запроса;
устройство сохраняет долю распределения, а сама добавка переживает замену
descriptor через `INTO`. Так разные части Control могут менять базовую запись и
текущее состояние независимо.

Эту добавку записывает исходный selector `0x500`, когда текущий descriptor
тоже относится к tag `26`. Мы восстановили его точку вызова в Behavior, но
смысл передаваемого там значения пока не установлен, поэтому этот Behavior путь
ещё не исполняется. Подтверждённые callbacks tag `26`, их native адреса и
точные проверочные векторы приведены в [техническом приложении](../appendices/script-vm.md#фабричный-tag-26-изменяемая-добавка).

Полный явный CPU-проход по исходной таблице из одиннадцати устройств
`min_l_n1.dat` тоже завершился. Этот результат проверяет вычисление для одной
загруженной таблицы; обновление пока не подключено к игровым часам и не
заменяет полный Control tick.

Устройство фабрики `2` имеет поле selector `6`, `+0x174`; конструктор задаёт ему
ноль. Позднее Control может пересчитать его по паре строк записи и отдельному
прототипу `BULL`. Только для поддержанной свежей формы одного корневого mesh
`BULL` из `objects.rlb`, без дочерних компонентов, его NDP-строки сводятся к
сумме Max; например, `[1.5, 2.25]`
превращается в `3.75` с округлением `f32` после каждого шага:

```rust
let mut total = 0.0_f32;
for row in ndp_rows {
    total += row.max_volume;
}
```

Пустая таблица даёт ноль; физическую единицу этому числу не приписываем. Пара
сравнивается как две C-строки до первого NUL: хвост не учитывается, регистр не
важен. Если после изменения любая строка пуста, старое `+0x174` сохраняется;
пустая пара конструктора не вызывает пересчёт, потому что уже совпадает. Новые
значения применяются при добавлении и первой активной записи `INTO` в исходном
порядке. Непредставленные входы оставляют селектор недоступным, а ошибка чтения
узнаваемого, но повреждённого ресурса отменяет новую загрузку и сохраняет
прежние мир и RNG. Общая формула selector 35 и условия свежей формы разобраны в
[техническом приложении](../appendices/script-vm.md).

Отдельный путь объекта класса `4` умножает интервал на контактный коэффициент и
передаёт изменение строке. В проверенном примере коэффициент `1`, интервал `2`,
и значение строки уменьшается на `2`; этот коэффициент не является ставкой
производства из профиля. Источник абсолютных часов и их доставка из World3D
в Control прослежены по инструкциям. Активная бюджетная часть проверена на
искусственном хосте класса `10`; полного тика объекта на миссии ещё нет.

У ресурсного шага отдельные часы. После принятого межкадрового интервала
Control заново разыгрывает срок обновления, даже если предыдущий вызов его
ещё не достиг. Например, с периодом `500` и начальным RNG `0x12345678`
исходная DLL пропустила времена `500` и `501`, затем выполнила ресурсный шаг
на `502`. Выбрать случайный срок один раз и ждать его было бы неверно.
Принудительный шаг тоже расходует RNG; неактивный объект синхронизирует часы
без такого расхода. FParkan подключает ресурсные часы и бюджетный шаг пока
для заводов и лабораторий. У этих владельцев класса `3` подтверждены активная
ветвь и период настройки `250` мс; отдельный native-вектор проверяет RNG и
строгую границу.
Запросы Rust `0xe00` и `0x1002` читают текущее состояние строк, которое меняют
этот бюджет и явные API, а `0x1005` — загруженную ставку профиля.
Счётчик `control_resource_clock_approx` считает бюджетные шаги по объектам:
полный порядок Control RNG с остальными владельцами ещё не восстановлен.
Неподдержанный callback сохраняет таблицу целиком и увеличивает
`control_resource_budget_stub` с указанием первого препятствия.
Точные нативные векторы и открытые границы описаны в [приложении](../appendices/script-vm.md#изменение-provider-состояния-control).

На x87 control word `0x007f` каждое умножение округляет мантиссу до 24 бит,
но промежуточная степень может выйти за диапазон `f32` и вернуться в него при
следующем умножении. Native oracle проверяет такой порядок для getter-а
`0x300`. Rust запрос сохраняет тот же порядок, но поддерживает только конечные
нормализованные значения или ноль на входе, промежуточном и конечном этапах.
Остальные случаи за этим численным диапазоном он отклоняет; полный x87
accumulator здесь не эмулируется.

Лицензированный тест на Unit DAT `UNITS/BUILDS/MINE/min_l_n1.dat` проходит через
`fr_l_mine.ctl` и `fr_l_mine.ndp`: у найденного tag-26 descriptor ключ равен
`2` в своей записи, raw коэффициент — `0x3f800000`. Корневой NDP содержит 22
строки, sidecar примонтированного `EXTO` — 4; в общую provider-таблицу входит
25 строк после пропуска локальной строки `0`. Тест также сравнивает порядок
всех source-row индексов с порядком строк самих sidecar таблиц. Он вызывает
Rust query по восстановленному native правилу адресации, а не getter оригинальной
DLL на полной миссии. Значение `1.0` подтверждает начальное состояние по native
конструктору, но не наблюдение живого Control tick-а.

### Control system и physical model

`LoadControlSystem` загружает настройки controller-а: ограничения скорости,
ускорения, поворота и режимы управления. `LoadPhysicalModel` загружает форму и
параметры, используемые для столкновений. Visible MSH не обязан совпадать с
collision representation: для физики часто нужна более простая и устойчивая
форма.

Практичная runtime-модель:

```c
struct PhysicalState {
    Transform transform;
    Vec3 linear_velocity;
    Vec3 angular_velocity;
    float requested_speed;
    float requested_turn;
    uint32_t flags;
};

struct CollisionProxy {
    ObjectId owner;
    ShapeSet shapes;
    Bounds broad_phase_bounds;
    uint32_t category_mask;
};
```

Названия полей здесь описывают контракт совместимой реализации, а не точный
layout исходного C++-объекта.

### Collision pipeline

Один расчётный шаг удобно разделить так:

1. controller получает желаемые `speed`/`turn` от Behavior или manual input;
2. вычисляет кандидатный transform на основе `dt`;
3. обновляет broad-phase bounds collision object;
4. collision manager находит потенциальные пары и terrain candidates;
5. narrow phase вычисляет контакт или допустимый остаток перемещения;
6. physical state корректируется;
7. World3D получает итоговый transform;
8. событие `GMSG_COLLISION_DETECTED` отправляется в согласованной фазе.

Позиция collision event после narrow phase является рекомендуемой фазой
реализации и согласуется с назначением сообщения, но точный call-site
относительно всех correction steps требует динамической трассировки Control.
Удаление объекта из обработчика остаётся отложенным по правилам World3D.
Collision manager не должен хранить прямую незащищённую ссылку на объект,
который уже pending-delete.

### CTLD и physical resources

Реестр прототипов ссылается на `*.ctl`, `*.cpt` и связанные control resources.
В заголовке CTLD идут пять `u32`; обозначим первые три counts как `S`, `M` и
`T`. Native layout задаёт начало control-row table формулой
`128 + S * (156 + 16 * M) + 4 * S * S`; за ним следуют `T` records по 36 байт.
В record известны node ID (`i32`, `+0`), два endpoint frame (`f32`, `+4`, `+8`),
начальный blend (`f32`, `+0x0c`) и raw flags (`u32`, `+0x20`). Остальные поля
нельзя выводить из этой позовой привязки.

Пример `fr_l_plant.ctl` имеет counts `[14, 0, 5, 11, 13]`: формула даёт
`row_start = 3096 (0xC18)`, а пять control rows заканчиваются на `+0xCCC`.
GOG `Control.dll` function RVA `0x9950` читает blend из `+0x0c` и flags из
`+0x20`. Его branch RVA `0x99C4..0x9A66` применяет flags: при `flags & 0x1`
blend один раз переносится через границу — из значения выше `1` вычитается
`1`, к значению ниже `0` прибавляется `1`; без этого флага blend ограничивается
`[0, 1]`. Затем `flags & 0x2` инвертирует значение (`1 - blend`). Константы
`Control.dll+0x3B188 = 1.0` и `+0x3B18C = 0.0` подтверждают границы этих
сравнений.

Control в call site RVA `0x99B5` передаёт в AniMesh через slot `+0x30` пару A
`[-1, -1]` и пару B из endpoint полей строки. В call site `0x9A7B` slot `+0x28`
сохраняет нормализованный blend по `+0x114` и weight `1` по `+0x118`. AniMesh
update RVA `0x8BF2..0x8C76` вычисляет
`frame = (1 - blend) * endpoint_a + blend * endpoint_b`; update RVA `0x12560`
выбирает B-state из-за weight `1`. В static preview строки с `flags & 0x4 != 0`
пропускаются до проверки float полей, поскольку endpoint поля в них могут быть
sentinel `-1`. Повторные node ID сохраняют исходный порядок, поэтому последняя
включённая строка задаёт кадр узла. Привязки сохраняются отдельно для каждого
экземпляра компонента, даже когда `PreparedVisual` разделяется через cache.
Это даёт начальную позу preview, но не запускает игровой Control, AI или полный
runtime animation path. Остальные
секции CTLD shape records и contact solver не входят в эту интерпретацию.

Читатель ресурсов проходит общую структуру typed records и сохраняет строки
эффектов type 4 как данные: индексы таблицы и строки, raw condition words,
selector, пару ресурсов и три offsets в point list компонента. Неизвестный tag
или неподдерживаемый layout задаёт `PreparedControlEffectSection::Unsupported`,
сохраняя уже разобранные pose bindings; повреждённая распознанная структура
отклоняет подготовку ресурса. В GOG corpus `fr_l_plant.ctl` содержит 38 строк
type 4, в том числе четыре `f_smalllight_y` с offsets 104–107 и `smoke_fr_02` с
offsets 119–121. В `fr_l_gener.ctl` найдено 35 строк type 4, включая
`f_gener_ball` с offset 85.

Control.dll `+0x8B10` передаёт указатель текущей записи диспетчеру `+0x2D4B0`.
Для tags `2`, `3`, `4`, `5`, `8`, `10`, `17`, `21` и `27` подтверждён общий читатель
`+0x21D50`: таблица виртуальных методов tag `2` (`+0x3CBD8`) вызывает его через
обёртку `+0x29650`, остальные перечисленные vtable указывают прямо на него в
позиции `+0x1C`. Читатель потребляет
заголовок размером `0xB0` байт со счётчиком `u32` по `+0xAC`, затем `count`
значений `u32`, слово длины и, при ненулевой длине, строку с завершающим NUL;
указатель возврата указывает на следующую запись. Rust-тест с tags `3`, `4`,
`10`, `27` проверяет переход между записями после непустых values и строк,
а также отказ при оборванном завершающем NUL. Это подтверждает структурный
формат, но не назначает смысл всем коэффициентам устройств.

Путь записи с меткой `17` проверен на GOG `Control.dll` с SHA-256
`bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`:
ветвь `0x11` фабрики `+0x2D4B0` вызывает конструктор `+0x24760`, который
устанавливает указатель на виртуальную таблицу `0x1003C840`. Ячейка `+0x1C`
этой таблицы ссылается прямо на общий читатель `+0x21D50`. В ресурсах
`weapon.rlb:bm_m_01.ctl` и `weapon.rlb:bm_l_01.ctl` таблица привязок
заканчивается на смещении `0x120`, где начинается запись с меткой `17`.
Общий префикс размером `0xB0` байт включает саму метку; счётчик по `+0xAC` и
слово длины в этих двух ресурсах равны нулю, поэтому указатель чтения
переходит на `0x1D4`. Там начинаются `0x54` байта заголовка таблиц эффектов;
таблицы содержат соответственно `4`, `2`, `2` и `2` строки по 100 байт и
заканчиваются на `0x620`. Записи из реестра объектов `bm_m_01` и `bm_l_01`
при обычной подготовке ресурсов сохраняют явно указанные списки точек CPT
(`bm_m_a.cpt` и `bm_l_a.cpt`) и таблицы узлов NDP (`bm_m_01.ndp` и
`bm_l_01.ndp`); в первой таблице эффектов находятся три строки type 4.
Синтетический тест проверяет непустые массивы значений и строки у записи с
меткой 17 и следующей записи с меткой 4, затем переход к таблице эффектов.
Если считать 17 неизвестной, чтение остановится перед
ней; общий разбор позволяет пройти запись и прочитать следующие таблицы,
оставляя слова tag 17 числами без толкования. Обработчики этой метки и их
игровое поведение ещё не восстановлены.

Resolver прототипов хранит явную registry-ссылку на `.cpt` отдельно от ссылки
на `.ctl`. Если строки type 4 разобраны и явная ссылка на CPT есть, подготовка
читает ровно указанные archive/name; имя CPT не выводится из имени CTL. В CPT
сначала идёт `u32` count, затем `count` записей по 36 байт и параллельные им
имена по 32 байта. Подготовка проверяет count, точную длину и конечность шести
float-полей. Она сохраняет flags, знаковые слова по смещениям `+4` и `+8`, два
набора из трёх float и raw name. `Control+0xB210` копирует слово `+4` в
производную запись точки, а `Control+0x1B4F0` передаёт это значение callback-у
выбора model node; роль слова `+8` и координатный frame float-полей пока не
назначены.

Native lookup выбирает первую группу CPT с тем же C0, а type-4 path прибавляет
к её началу row offset. Для корневых компонентов `fr_l_plant` и `fr_l_gener`
C0 равен 0, поэтому найденные offsets 104–107, 119–121 и 75–82, 85 указывают на
соответствующие записи в их CPT-списках. Общий путь выбора группы для других C0
и семантика sentinel `u32::MAX` пока не реализованы; reader сохраняет offsets
как raw значения. Отсутствующая явная CPT оставляет `point_list` отсутствующим,
но не мешает исследовать строки эффектов. Это только чтение ресурсов: проверка
условий, загрузка FX materials, activation, выполнение FX opcodes и видимый
рендер эффектов пока не реализованы.

После типизированных записей CTLD хранит 21 ссылку на группу эффектов. В
`fr_l_plant.ctl` первая ссылка равна `8`, остальные 20 содержат `u32::MAX`; за
ними расположены 13 таблиц групп. При разборе по адресу `+0x8B10` к каждой
ссылке, кроме `u32::MAX`, прибавляется число групп, зарегистрированных до
таблиц этого CTL; получившиеся индексы сохраняются в control mapping. При
событии `0x80000020` код по адресу `+0x7830` сразу выходит, если поле дескриптора
`+0xC0` равно нулю. Разбор по адресу `+0x8B10` вызывает диспетчер групп `+0x2800`
с индексом группы по умолчанию только при ненулевом `+0xC0`. Назначение поля
дескриптора и условия его заполнения на стороне producer пока неизвестны.
`initial_effect_group` хранит проверенную ссылку на группу по умолчанию. Это
поле описывает данные CTL и не выполняет activation, загрузку FX materials,
FX opcodes или рендер эффектов.

CPU-only обход `MISSIONS/Autodemo.00/data.tma` подготовил четыре CTL с 80
строками type 4 и четыре явных CPT-списка (всего 322 записи). Среди пар были
`fortif.rlb/fr_l_plant.ctl` и `fortif.rlb/fr_l_plant.cpt` (155 точек), а также
`parts.rlb/u_all_def_a_01.ctl` и `parts.rlb/u_all_def_a_01.cpt` (6 точек). Среди
240 raw offset words не встретился `u32::MAX`; наибольшее значение — 121. Это
наблюдение ограничено указанной выборкой и не определяет sentinel для других
ресурсов.

### Terrain queries и movement handoff

Control получает world-interface Terrain и использует поверхность, faces и
ускорители для высоты, нормали и пересечений. Навигационный маршрут сообщает,
куда двигаться, но итоговый transform определяется по физической поверхности.
При переходе через склон controller должен согласовать горизонтальный шаг,
высоту и ориентацию с terrain normal.

Герой в обычном окне FParkan получает команды из тех же клавиш, что и
в исходной таблице `hero.tbl`. Стрелки задают ход вдоль и поперёк
корпуса, а смещение мыши по горизонтали поворачивает корпус вокруг
вертикальной оси. В GOG-комплекте `World3D.dll` сопоставляет имена
`MCMD_WALK_F`, `MCMD_WALK_B`, `MCMD_LEFT`, `MCMD_RIGHT` и
`MCMD_ANGLE_Z` кодам команд (RVA `0xd7b0`, сборка в
[перечне оригинальных модулей](../reference/original-binaries.md)).

Горизонтальная команда `MCMD_ANGLE_Z` получает долю полного оборота.
`World3D.dll` сначала умножает свежий отсчёт X на `MOUSE_SENS / 100`
из секции `[CS]` файла `Iron_3D.ini`. Фильтр берёт 95% этого
значения и 5% предыдущего отфильтрованного отсчёта. Когда обе оси
неподвижны, фильтр обнуляется (RVA `0xf213–0xf2ab`). Затем отсчёт
умножается на 0,006. При выходе за ±0,999 значение становится ±1.
Строка `hero.tbl` умножает результат на долю оборота 0,15
(RVA `0x10a50`, сложение с углом и перенос через границу оборота
по `0xfb40`). Из нейтрального состояния 100 единиц X при штатной
чувствительности дают 0,0855 оборота, около 31°. Предел одного отсчёта
составляет 54°. Вызов DLL подтвердил величину команды, насыщение и
перенос через границу в обе стороны.

В `Control.dll` команда прибавляется к фазе поворота с нейтралью 0,5
(чтение по RVA `0xdeb4`, запись по `0x4500`). За шаг применяется угол
не больше произведения длительности шага на угловую скорость из слова 11
профиля (`0x14780`). Control вычитает исполненную часть из фазы.
При шаге 10 мс герой «Огневого рубежа» поворачивается максимум на 0,502
радиана. Из команды в 0,15 оборота на следующий шаг остаётся около 0,440
радиана. Вызов DLL через чтение и запись фазы дал этот остаток, и второй
шаг завершил поворот с неподвижной мышью.
[Сборка Control.dll](../reference/original-binaries.md).

На каждом шаге FParkan переводит направления из осей корпуса в мировые
координаты, измеряет высоту поверхности на старой и новой позиции и
сохраняет высоту героя над поверхностью. В словах 6 и 7 действующего
профиля Control хранятся поперечный и продольный пределы. Для героя
«Огневого рубежа» это около 1 и 14 единиц в секунду. Слова 0 и 1
задают ускорение. Скорость сохраняется между тиками и постепенно
снижается до нуля после отпускания клавиши. Например, при подъёме земли
на две единицы корень героя тоже поднимется на две единицы. При переходе на
настил или пол здания движок измеряет прежний зазор над опорой и переносит
его на новую поверхность. На мосту «Огневого рубежа» это сохраняет высоту
камеры над наклонным въездом, стыком двух секций и съездом. Опору дают грани
модели моста, поэтому правило действует и когда русло лежит ниже настила.
Пока коллайдер героя приближённый, верхний предел зазора берётся из
стартовой позы над рельефом. Для старта под рельефом, как в бункере
«Двух крепостей», используется минимальный зазор над полом.

Для ходьбы профиль Control с режимом 2 хранит предельный угол подъёма
в слове 23. У героя это 0,6 радиана, около 34°. В `Control.dll` по RVA
`0x153c0` берётся нормаль опоры, а скалярное произведение её горизонтальной
части с движением определяет спуск. На спуске скорость сохраняется.
При подъёме и ходе вдоль горизонтали склона предел скорости умножается на
`clamp(2 * (normal.z - cos(limit)) / (1 - cos(limit)), 0, 1)`.
Вызов DLL подтвердил коэффициент на ровной земле, на склонах 0,3, 0,5 и
0,7 радиана и при обратном направлении на крутом склоне. FParkan выбирает
нормаль той же грани рельефа, которая даёт высоту, и повторяет пробу опоры
для укороченного шага. На склоне Control сначала обновляет скорость по
вводу, затем приближает её к пределу с ускорением в 1,5 раза выше разгонного.
Эта последовательность подтверждена вызовом DLL с сохранением скорости
между тиками. Когда героя несёт пол строения, он следует этому полу.
Смещение на склоне FParkan считает по скоростям на концах короткого шага.
На грани с нулевым пределом шаг удерживает героя у входа на склон, пока
сохранённая скорость продолжает уменьшаться.
[Сборка Control.dll](../reference/original-binaries.md).

Если отрезок между позициями пересекает стену строения, шаг сохраняет
старую позицию и применяет поворот. Камера, рендер объекта и сценарий
читают полученную позу из одного мира. Повтор кадра после resize
повторно управление не применяет.

Порядок операций должен быть детерминированным: пары collision objects
сортируются по стабильному ID, contacts обрабатываются в фиксированной
последовательности, а интеграция использует одну политику `dt` и округления.
Иначе одинаковая миссия постепенно расходится даже без сети.

Go, Patrol и сближение с целью передают маршрут и запрошенную скорость одному
контроллеру. Он расходует время кадра сначала на разворот, затем на ход до
следующего узла. При скорости `10` и кадре `200` мс прямой отрезок длиной `1`
занимает `100` мс. Если за узлом есть ещё отрезок, контроллер расходует на него
оставшиеся `100` мс, учитывая следующий поворот. Зазор над рельефом сохраняется.

Перед каждым отрезком контроллер проверяет, не пересекает ли он проекции
стоящих на карте строений. Проекция охватывает границы узлов основной
модели в мировой позе. Её расширяют на радиус машины, чтобы планировать
путь для центра корпуса с запасом для краёв. Если отрезок перекрыт,
контроллер ищет короткую цепочку видимых углов. Например, путь через два
соседних корпуса строится с проверкой каждого отрезка против обоих.
Если машина уже находится внутри проекции, первая цель лежит у ближайшей
доступной стороны. Цель внутри здания даёт точку подхода снаружи.

Транспорт использует ту же проекцию для погрузки и разгрузки. Например,
в «Двух крепостях» маршрут останавливал машину примерно в 74 единицах
от центра шахты, а прежний порог в 48 единиц оставлял её без руды.
Теперь транспорт выбирает точку на грунте вдоль расширенного контура.
Обмен начинается, когда корпус подходит к границе снаружи. Точные порты
и темп перегрузки остаются приближёнными.

Другие машины тоже занимают место на пути. Перед ходом берётся снимок их
позиций. За уже сдвинувшейся машиной до конца кадра сохраняется весь
пройденный участок с запасом под корпус. Это позволяет избежать пересечения
маршрутов при длинном кадре. Если конечная точка занята, машина подходит
к свободному краю и продолжает приказ после освобождения цели.

`unit_route_motion_approx` считает шаги контроллера. Препятствия имеют
прямоугольную форму, а очередь хода машин влияет на разъезд. Открыты узкие
проезды и посадка.

#### Опора наземного корпуса

Высота корня модели и высота её нижней точки различаются. Поэтому контроль
рельефа по одному центру может оставить часть ноги или гусеницы в земле.
Контроллер берёт нижнюю вершину в каждой четверти шасси в его начальной
позе. В новой позиции он сравнивает каждую опору с грунтом под ней и
выбирает самую большую требуемую высоту корня. Это также работает при
развороте на месте. Зазор, который уже был над опорой, сохраняется, а при
съезде с возвышения высота вновь уменьшается.

Это опора жёсткого корпуса по нескольким пробам. Она ещё не учитывает
пружины, наклон машины и перенос веса между лапами во время шага.

#### Высота автономных машин

Летающая машина использует тот же поворот и те же путевые точки. Контроллер
берёт радиус корпуса из модели и поднимает центр примерно на два радиуса
над поверхностью. Подъём расходует часть интервала кадра с текущей
запрошенной скоростью. На оставшемся интервале машина продолжает путь.
Пробы рельефа между началом и концом шага позволяют заметить гребень раньше
его пересечения. Над низиной высота остаётся прежней.

Пока маршрут и преграды проверяются в плоскости карты. Управляемое снижение,
инерция и разделение потоков по высоте остаются открытыми.

#### Звук двигателя

Звуки двигателя привязаны к корпусу через строки CTL типа 3 и команды `Op2`.
В GOG `Control.dll` по RVA `0x2972` такая строка задаёт ресурс и узел
крепления. Для этих звуков FParkan использует запись со смещением узла
ноль, которую содержат штатные шасси.
Например, у `eng_rb_01` зацикленный звук начинается с фазы `0,01`,
а у `eng_rl_03` вместе с фазой растёт частота проигрывания.
Effect.dll по RVA `0x5c60` в режиме 5 делит длину линейной скорости
на длину вектора пределов. В режиме 15 берётся больший из двух таких
отношений, для линейной и угловой скорости.

FParkan берёт пределы из текущего профиля Control, а скорости оценивает
по смещению и повороту между двумя тиками миссии. Поэтому разворот на
месте тоже может включать двигатель, а после остановки фаза возвращается
к нулю. Первый тик нового корпуса не наследует скорость старого.
Угловая скорость пока оценивается по углам Эйлера.

#### Прокат колёс

На колёсном шасси `R_L_03` управляющий ресурс связывает четыре узла с
зацикленными строками CTLD. Ключи каждой строки задают полный оборот вокруг
неподвижной локальной оси. FParkan подключает такие строки, когда ключи
образуют равномерный оборот и размер колеса можно прочитать из модели.
Один оборот соответствует пути `2πr`. Пройденное за кадр расстояние вдоль
корпуса сдвигает фазу, задний ход крутит колёса в обратную сторону,
пауза сохраняет угол. Появление новой машины начинает новый цикл.

Фаза отбирает исходные позы узлов MSH, поэтому за ними обновляются и
крепления деталей. Радиус оценён по габаритам модели, вертикальное
движение и проскальзывание не учитываются.

#### Походка

Профиль `WalkChassis` отмечает шагающие шасси. В проверенных CTLD нет границ
шага. В ключах MSH можно найти последовательность кадров с поступательным
движением корня, у которой начальная и конечная позы совпадают после
вычитания движения вперёд, а между ними узлы меняют позу. Так выделяется
по одному замкнутому циклу у лёгкого, среднего и тяжёлого шасси.

Фаза цикла зависит от фактического пути по земле и масштаба машины.
Например, движение на половину длины шага переводит модель на половину
пути, записанного в ключах корня. При отрисовке продвижение из ключей
вычитается из позы, поскольку положение в мире уже изменил контроллер.
Вертикальное и поперечное движение узлов сохраняется. Пауза удерживает фазу,
а при остановке следующий кадр мира возвращает модель к позе покоя.

#### Гусеничные ленты

У гусеничного шасси `ChassisType = 4`. На проверенных моделях ленты
отмечены флагом `0x4` в группах треугольников. Их материалы содержат
зацикленные фазы MAT0. Например, `R_RL_25` показывает четыре текстуры
за 200 мс, а `R_RL_25REV` перечисляет те же фазы в обратном порядке для
поверхности с противоположным направлением развёртки.

FParkan подаёт в выборку этих материалов фазу от фактического смещения
шасси. В качестве длины одного цикла используется путь за длительность
материала при исходном пределе скорости Control с учётом масштаба модели.
При остановке рисунок ленты замирает, при заднем ходе фазы идут в обратную
сторону. У каждой машины своя фаза, поэтому стоящая машина может оставаться
неподвижной рядом с едущей.

В GOG `Behavior.dll` ([сборка](../reference/original-binaries.md)) задача Go
(RVA `0x2b670`) обращается к MWalker, а не изменяет transform сама.
Проверка MWalker (RVA `0x3dd80`) требует нуля в трёх полях `+0xec`, `+0x100`
и `+0x114`. Управление этими контейнерами и физический шаг Control пока
не воспроизведены.

#### Reference controller в текущем runtime

`fparkan-runtime::advance_reference_movement` — намеренно маленький
детерминированный мост между сохранённым mission transform и `TerrainWorld`.
Он получает `OriginalObjectId`, явную XY-цель и положительный максимум шага,
находит только live/registered object по исходному ID, двигает XY не более чем
на этот шаг и записывает высоту из `TerrainWorld::height_at`. Orientation и
scale остаются исходными IEEE-754 words; функция не изменяет clock, очередь
World3D или animation state. Возвращаемое значение означает достижение именно
заданной XY-цели.

Это **не** восстановленный Control, Behavior или navigation controller:
функция не строит маршрут, не использует `dt`, скорость, terrain normal,
коллизии, acceleration и оригинальные AI decisions. Она существует как
проверяемый reference path, который фиксирует границу будущих controller-ов и
не позволяет renderer-у или gameplay обходить terrain query. Non-finite input,
неположительный шаг, отсутствующая миссия/объект и XY вне поверхности дают
явную ошибку без частичного изменения transform.

Licensed test на GOG `Autodemo.00` запускает этот путь для live mission object,
находит существующую поверхность и проверяет точные XY/Z words после snap. Это
доказывает связывание current runtime data, но не доказывает семантику
оригинального движения.

`Control.dll` пересобрана при неизменных размере, imports и пяти именах/ordinals
exports; RVA всех пяти exports изменились. Форматы и cross-module boundary
сохранились, но точное physical/collision behavior нельзя считать побайтно тем
же.

Покадровая привязка выше описывает начальную позу компонента. Она не задаёт
семантику CTLD shape records и не восстанавливает contact solver.

Differential test обеих частей должен воспроизводить движение без препятствий,
slope following, pair collision, timing collision event и удаление объекта в
callback. Сравниваются transforms и contact events по tick, а не только факт
успешной загрузки.

## Ввод, камера и управление

World3D нормализует клавиатуру, мышь и joystick в общие scan codes и manual
commands. Win32 message handler вызывает `UpdateManualEventsList`; перед
обработкой новой порции сообщений основной цикл вызывает
`ClearManualEventsList`. Снимок клавиатуры очищается отдельно через
`stdClearKeyboard`.

Публичная поверхность включает `WinMsg2ScanCode`, converters для
keyboard/mouse/joystick/predicate, `ScanCode2Str`, `ManualCommand2Str`,
`stdIsKeyPressed`, lock/unlock keyboard и чтение mouse shift. Это позволяет
хранить конфигурацию управления независимо от физического устройства.

### Event, state и axis

Ввод имеет минимум три семантики:

- **edge event** -- нажатие или отпускание в текущей порции сообщений;
- **held state** -- клавиша остаётся нажатой между кадрами;
- **analog value** -- смещение мыши или положение joystick axis.

Manual command дополняет источник коэффициентом, режимом wrap, dead
zone/threshold и временной характеристикой. Строки camera bindings показывают
команды `MCMD_STATE`, `MCMD_ANGLE_X`, `MCMD_ANGLE_Y`, режимы `MAN_WRAP` и
`MAN_NOTWRAP`, а также параметры ускорения в миллисекундах.

В `hero.tbl` вертикальное движение мыши без Shift отправляет
`MCMD_ANGLE_Y` башне. С Shift эта же ось направлена камере.
В `World3D.dll` свежий отсчёт Y перед фильтром умножается ещё на 1,2
(RVA `0xf277`). Команда использует коэффициент 0,25 из `hero.tbl`
и направление из `[CS] MOUSE_REV_Y`. `MAN_NOTWRAP` ограничивает
относительное изменение дорожки её концами (RVA `0xfb40` → `0x10a50`).
Вызов DLL подтвердил прибавление 0,171 к доле дорожки при движении
мыши на 100 отсчётов вверх с включённым `MOUSE_REV_Y`, а также
удержание на 0 и 1 при попытке выйти за предел.

Нейтраль и размах задаёт вторая дорожка записи Control типа 1. У башни
скафандра в «Огневом рубеже» доля нейтрали равна 3/11, а размах —
110°. Нижнее положение получается на −30°, верхнее на +80° от
нейтрали. Ручная ветвь `0x200` обновления `Control.dll` по RVA
`0x27470` передаёт ограниченную долю вертикальной дорожке в тот же
шаг. Вызов этой ветви подтвердил значения для нейтрали, обеих границ
и промежуточных углов. В FParkan один угол задаёт наклон взгляда и
долю основной дорожки башни. Прицел и подвижные детали читают позы
из дорожек `CTL` и кадров `MSH`. Точка `CameraCenter` остаётся
в кабине, корпус героя сохраняет прежнюю высоту.

С зажатым левым Shift `World3D.dll` направляет обе оси к
`CICLS_CAMERA`. В ходе выбора привязки по RVA `0xf37c` нажатый
модификатор выбирает свою строку. В `hero.tbl`, `m1.tbl` и `m2.tbl`
горизонталь прибавляет к фазе отсчёт с коэффициентом 0,1 и переносит
его через границу оборота. Вертикаль использует коэффициент 0,15 и
ограничивает фазу диапазоном 0–1. Отпускание Shift и правая кнопка
мыши при зажатом Shift записывают 0,5 в обе оси. Вызов диспетчера
`0xfb40` подтвердил относительный ход, перенос, ограничение и возврат.

Ручная ветвь камеры `Control.dll` по RVA `0x23788` переводит фазы
в углы `(0,5 − x) × 2π` и `(0,5 − y) × π`. Сначала камера
поворачивается вокруг своей вертикали, затем вокруг поперечной оси.
Вызов этой ветви подтвердил направление и порядок поворотов, в том числе
для совмещённого движения мыши. Повороты сохраняют точку обзора.
Угол башни сохраняется, а корпус может закончить поворот, запрошенный
до нажатия Shift.

На участке устойчивой ходьбы героя в запущенной GOG-сборке высота
камеры менялась на 0,35 единицы от нижней точки до верхней. Полный
цикл занимал примерно 0,45 секунды. Положение снималось с активной
камеры GOG `iron3d.dll` через экземпляр игры по RVA `0x10a5f8`.
[Сборка оригинала](../reference/original-binaries.md).

FParkan приближает это движение
вертикальной синусоидой. Она идёт, пока герой смещается после проверки
столкновений, и затухает на остановке. Высота корпуса и точки выстрела
по-прежнему определяются позой объекта и оружия.

Нижняя точка этого цикла даёт звук шага. У героя в `bases.rlb` запись
`r_h_02.ctl` перечисляет эффекты для разных поверхностей и обеих ног.
FParkan берёт из неё `step_hg` для грунта и `step_hf` для пола здания.
Поверхность определяется тем же принятым шагом, который переносит
героя через стык земли и пола. Когда столкновение останавливает ходьбу,
звуки шагов прекращаются.

В GOG `Control.dll` (SHA-256
`bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`)
фабрика по RVA `0x2d4b0` создаёт контроллер башни из записи типа 1.
Две первые строки его карты задают горизонтальную и вертикальную оси.
Загрузчик `0x8b10` присоединяет к контроллеру дорожки с флагом `0x08`.
Обновление `0x27470` применяет вертикальную долю к связанным дорожкам
через `0x28200`. При выборе дополнительной дорожки флаг `0x40` исключает её
из этого прохода, а `0x2000` выбирает отдельную ветвь.
FParkan переводит угол относительно нейтральной позы в долю диапазона
ресурса и вычисляет кадр между концами дорожки. Поправки отдельных
орудий ещё требуют сверки.

Simulation читает подготовленный input snapshot. Renderer не должен
самостоятельно опрашивать OS, иначе одно и то же нажатие будет зависеть от
частоты кадров.

### Ручной огонь

В `hero.tbl` кнопки от 1 до 8 выбирают орудие, а 0 выбирает все.
Нажатие левой кнопки мыши включает непрерывный огонь выбранных
орудий, отпускание его прекращает. В GOG `World3D.dll` по RVA
`0xd7b0` имена `MCMD_STATE` и `MCMD_SELECT` превращаются в команды
1 и 13. SHA-256 этой сборки указан в
[перечне модулей](../reference/original-binaries.md).

Герой получает орудия из записей Control типа 2. Запись указывает
ресурс снаряда и строки CTL, которые выбирают точки выстрела в CPT.
У пушки героя в «Огневом рубеже» строка указывает узел ствола, а
связь эффекта этого узла ведёт к звуку `H_fire_cannon.wav`. В
`Control.dll` с хешем из раздела выше RVA `0x29ca0` ведёт цикл
орудия, `0x2a190` запускает эффект и создаёт снаряд на соседних
фазах, а `0x2800` связывает строки эффектов с узлами командой 14.

У ракеты героя звук пуска задан в начальной группе CTL самого снаряда.
`bm_h_01.ctl` запускает `hero_gunfire_missile`, где команда Op2 с
начальной фазой 0 указывает на `H_fire_missile.wav`. Вызов GOG
`Effect.dll` по RVA `0x5c60` подтвердил, что режим 1 отсчитывает фазу
от начала эффекта. FParkan ставит этот звук в очередь в точке пуска.
Двигатель ракеты задан отдельной зацикленной командой Op2. Time mode 5
берёт длину текущей скорости и делит на длину предельной скорости из
профиля (`Effect.dll` RVA `0x5c60`). При скорости 70 у ракеты героя фаза
равна единице и входит в окно 0,1–1. Три точки CPT ставят источник
`H_eng_missile.wav` на 0,40465 единицы позади центра. Источник следует
за ракетой и останавливается при столкновении или истечении её времени
жизни. Вызов DLL подтвердил фазы при скоростях 0, 7 и 70.

У лазера вертолёта звук привязан к узлу орудия строкой типа 3.
В начале цикла четвёртое слово записи орудия выбирает группу CTL
(`Control.dll` RVA `0x2a190` → `0x221e0` → `0x2800`).
Команда 10 находит созданный эффект по номеру компонента и селектору
строки и ставит его часы в режим 1 с началом в текущем времени
(`Effect.dll` RVA `0x4b00` → `0x7b00`). Вызовы обеих DLL подтвердили
выбор строки и смену времени. Для `gun_las_01_sfx` флаг `0x20`
складывает фазу по треугольнику. В первые полсекунды фаза растёт
вдвое быстрее обычного, поэтому порог 0,25 для `gun_las_01.wav`
пересекается на первой выборке после 125 мс подготовки выстрела.
На точной вершине фазы Op2 запоминает ноль, поэтому следующий кадр
может запустить звук повторно. Это правило подтверждает вызов
`Effect.dll` RVA `0x12eb0`.
[Хеш сборки Effect.dll](../reference/original-binaries.md).

Каждый ствол проходит половину хода анимации перед выстрелом и вторую
половину после него. Длительность половины хода равна
`500 мс / скорость строки CTL`. Две отдельные задержки задают паузу
после выстрела и паузу перед открытием нового цикла. Если фаза закончилась
между двумя выборками, следующая ненулевая фаза стартует с её границы,
а после нулевой задержки часы фазы привязываются к текущей выборке.
Этот порядок задаёт планировщик Control по RVA `0x2d260`.

Обе половины цикла двигают модель оружия. Например, ствол пушки героя
проходит кадры 58–60, а в середине цикла выпускает снаряд. Код Control
по RVA `0x21a30` интерполирует фазу между её границами и обращает шкалу
для строки с флагом 2. Вызов GOG DLL с 125 мс на половину хода дал
фазы `0 → 0,25 → 0,5` перед выстрелом и `0,5 → 0,75 → 1` после него.
FParkan обновляет позу ствола перед расчётом его точки пуска.

Например, у лазера половина хода длится 125 мс, а пауза между циклами
равна 200 мс. При выборке раз в 17 мс исходный Control и FParkan дают
выстрелы на 136, 595 и 1054 мс от включения. В этом опыте использовались
исходные параметры CTL и изолированная обвязка Control. Ракетница
чередует две исходные точки пуска, и их скорости анимации различаются.

Начальный боезапас берётся из первого числового параметра записи типа 2.
В исходной `Control.dll` RVA `0x29650` округляет его до целого, а RVA
`0x2a190` уменьшает конечный остаток при завершении цикла. Значение
`−1` означает бесконечный боезапас. На старте «Огневого рубежа» у
пушки 500 патронов, у плазмопушки 150, у ракетницы четыре ракеты, а
лазер работает без расходуемых зарядов. Единица списывается в конце
цикла даже после отпускания кнопки. Когда боезапас выбранного орудия исчерпан, оно замолкает,
а остальные выбранные орудия продолжают стрелять.

У варботов таблицы `m1.tbl` и `m2.tbl` связывают те же клавиши и кнопку мыши
с командами выбора и огня. При пересадке FParkan переключает управление на
орудия варбота. У каждого корпуса свой выбор орудий и остаток зарядов.
Система читает точку выстрела из компонента со стволом, поэтому орудие
сохраняет свою точку пуска и на отдельной детали. Снаряд запоминает
стрелявший корпус и продолжает полёт после высадки.

### Полёт снаряда

Нативный выстрел создаёт объект класса 9 из указанной орудием пары
«архив и имя». Control получает точку и направление через запрос CPT
и задаёт локальную ось +Y снаряда вдоль полёта (`Control.dll` RVA
`0x1b4f0`, `0x2b0f0`, `0x2a190`). Профиль корневого компонента
загружается из 27 слов CTL (`0x8b10`). Из этих слов FParkan берёт
скорость и предельный возраст. Например, снаряд пушки героя
использует 350 единиц в секунду и 1000 мс.

В FParkan снаряд игрока появляется в точке ствола и летит по прямой
вдоль прицела башни. Поворот головы с левым Shift меняет обзор.
За каждый шаг он проходит отрезок длиной `скорость * время`. Запрос
треугольников рельефа проверяет весь отрезок, поэтому быстрый снаряд
может встретить поверхность между кадрами. На контакте или по истечении
возраста модель исчезает. Этот проход использует исходные MSH и материалы.

Автономные орудия тоже берут точку из CPT своего компонента. Сначала CPU
выбирает текущие кадры узлов Control, затем проходит цепочку сокетов от
орудия к корпусу. У установленной детали корневая поза MSH заменяется
позой крепления: повторное сложение этих поз сместило бы ствол. После этого
применяются масштаб и положение корпуса. Масштабирование CPT перед мировой
матрицей проверено вызовом GOG `Control.dll` (SHA-256
`bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`),
RVA `0x1b4f0`, и преобразований `Ngi32.dll`. При масштабе (2, 3, 4),
повороте на 90° вокруг Z и переносе (30, 40, 50) тройка (1, 2, 3)
даёт точку (24, 42, 62) и вектор (−6, 2, 12). Мировую матрицу для
вектора ствола FParkan ещё предстоит восстановить.

Дальность выстрела задаёт устройство оружия. Если слово 22 профиля
снаряда положительно, `Control.dll+0x297e0` подставляет его в селектор 8
орудия. Ветка `0x29e23` сравнивает квадрат этой дальности с квадратом
расстояния до цели по трём осям. Например, `bl_m_01` в штатном AutoDemo
передаёт 1000 единиц, а `bm_l_01` в той же машине передаёт 350.
Огонь на этой дистанции возможен, пока корпус идёт по своему маршруту.
FParkan отдельно проверяет, пора ли корпусу остановиться для атаки.

Проверка рельефа начинается у выбранного ствола, поэтому низкий гребень
перед корпусом не закрывает орудие, установленное выше него. Цель переводится
в систему координат крепления башни. Две строки CTLD связывают азимут и
возвышение с кадрами MSH. Например, проверенные башни AutoDemo используют
кадры 7–11 для полного оборота и 12–14 для подъёма ствола. Окно и расчёт
точки выстрела используют одинаковые углы наведения.

Снаряд пока направляется в центр цели по прямой. Скорость приводов и отдача
ещё открыты. Как и оконный рендер, неподдержанную анимацию этот путь
заменяет начальной позой Control, но считает такие выборки по объекту и
компоненту. Неизвестное крепление пропускает выстрел и попадает в отчёт,
вместо пуска из центра корпуса.

У лазеров героя и двух варботов «Огневого рубежа» видимый след задают две
команды `Op5` в эффекте самого снаряда. Они задают ширину слоёв и материалы.
В GOG `Effect.dll` (SHA-256
`386a3e8db1ce23f61957825d633c7dae1ed40c25cab0cf10a534385fd7cee789`)
обновление по RVA `0x2a20` запоминает первую позицию и включает отрисовку
после второй, когда позиции различаются. Вызов с точками `(10, 20, 30)` и
`(18, 26, 30)` дал середину `(14, 23, 30)` и радиус `5`. В FParkan оба
слоя располагаются на отрезке, пройденном за текущий шаг. При попадании
отрезок заканчивается в точке контакта даже в кадре исчезновения снаряда.
Автономные орудия передают отрисовщику такие же отрезки. Модели и следы
занимают места в пуле независимо, поэтому снаряд, выпущенный в том же
такте, может появиться рядом с последним следом предыдущего выстрела.

При выпуске снаряда выбранная пушка передаёт отрисовщику связанный с
ней эффект из таблицы Control. Ручной и автономный выстрел используют
одну привязку. Например, пушка героя в «Конструкторе» запускает
`hero_cannon` из `effects.rlb`. Свет `Op1` и спрайты `Op3` берут
цвет и размеры из эффекта, а точки CPT и поза оружия задают положение.
В GOG `Control.dll` (SHA-256 `BCB86318089028548A178B03A21ACCDCE15DF0CC85DDD91674CF3C2F55012C6E`) команда 14 в обработчике по RVA `0x2800` связывает эффект с узлом.
`Effect.dll` (SHA-256 `386A3E8DB1CE23F61957825D633C7DAE1ED40C25CAB0CF10A534385FD7CEE789`)
запоминает эту привязку в `0x4b70` и в режиме 4 запрашивает фазу узла
по `0x5d3f`. В GOG `AniMesh.dll` (SHA-256
`65659bf67f20e5be77d67a5b2f59968f61b94293143807fa59ca451c560c4f7e`)
метод `0x5630` сохраняет фазу анимации, а метод `0x5600` возвращает её
для указанного узла. Вызов обеих DLL подтвердил, что эффект читает фазу
выбранного узла. Флаг `0x20` преобразует фазы 0,25, 0,5 и 0,75 в
0,5, 1 и 0,5. У ручного оружия с такой привязкой вспышка получает
ту же фазу, что и ствол. Автономные и непривязанные вспышки пока занимают
одну выборку при выпуске снаряда.

Орудие героя хранится на спине. Дорожки крепления типа 24 в
`o_tur_ht_02.ctl` подают пушку и плазмомёт к рукам, а лазер и ракетницу
выводят к плечам. Группа дорожек определяется по предкам узла дульной
точки CPT. Дочерний узел ствола к этому движению добавляет цикл
выстрела. У пушки дорожки крепления идут от кадра 42 к кадру 48. В
обратную сторону они возвращают её на спину. В вызове GOG `Control.dll`
по RVA `0x20900` скорость из CTL приводила к фазам 0,45 на 225 мс, 0,9
на 450 мс и 1 на 500 мс. Обратный ход занимал те же 500 мс.

В FParkan нажатие огня переводит выбранное оружие в боевое положение.
Выстрел начинается, когда все дорожки крепления дошли до конца. Короткое
нажатие сохраняется до готовности. После завершения цикла оружие
убирается. Точное условие активации у оригинала требует сверки.

В изолированном вызове `Control.dll` по RVA `0x1b4f0` смещение узла меняло
дульную точку, а поворот менял и точку, и направление. Стволы всех четырёх
орудий в конечной фазе крепления направлены вперёд. Точка выпуска в
FParkan уже следует этой позе, направление полёта по-прежнему берётся с
прицела. Сверка направления с живыми матрицами, баллистика и порядок фаз
в полёте остаются открытыми.

Полёт также проверяет пересечение отрезка с живым юнитом. Сфера корневой
модели ограничивает поиск, а у варбота внутри неё проверяются треугольники
шасси. Повреждённый узел с собственным запасом расходует его отдельно
и запускает свой `EXPL` при истощении. Если узел не задаёт отдельную модель
разрушения, он исчезает с корпуса. В GOG `Control.dll` ветвь по RVA
`0x11220` при достижении последней стадии вызывает `0x11920` для обновления
видимости. Например, у тяжёлого гусеничного варбота `w_b_trk1` исчерпание
узла 7 скрывает одну гусеничную секцию. Проверку ещё не подключённых
навесных моделей заменяет выход из сферы. Срабатывает первое пересечение
по ходу отрезка, включая рельеф. Животные класса `0x20000000`
используют сферу. Например,
у медузы в «Конструкторе» попадание расходует запас её корневой записи NDP,
а исчерпание запаса удаляет животное из мира. Вооружённое животное
использует ту же проверку дальности, клана и видимости, что и варбот,
и стреляет с места. CTL медузы `a_a_l3.ctl` задаёт снаряд `ba_a_03`
и точку `Gun_Y`. У точки указан узел 12, второй индекс равен `-1`.
Животное использует темп и боезапас из этого оружия.

Входящий урон пока берётся из начального объёма NDP снаряда.
У цели с силовым полем первым отвечает один из шести секторов. Сектор
выбирается по направлению к точке попадания в координатах корпуса. В
GOG `Control.dll` выбор выполняется по RVA `0x2c590`, а сила сектора
по `0x2ca30` равна произведению базового запаса устройства 9, доли его
заряда и коэффициента устройства 21 для этой стороны. Вызов DLL с
базовым запасом 500 дал силы 250 и 175 у двух секторов. Сброс первого
по `0x2ca80` оставил второй на 175.

Ветвь по RVA `0xd1b4` сравнивает силу сектора с объёмом снаряда.
Поле останавливает снаряд и расходует его объём из запаса сектора,
если силы хватает. В штатном AutoDemo попадание объёмом 899 уменьшило
силу сектора с 3040 до 2141. При пробое сектор опустошается, а к корпусу
проходит разность. FParkan выполняет эту проверку в найденной точке
контакта. Отдельная поверхность поля ещё открыта.
Полное поглощение завершает полёт снаряда и учитывается как отработавшее
попадание в щит. Отчёт о неподдержанных контактах учитывает случаи, в
которых движок не смог обработать цель.

Попадание в заряженный сектор запускает эффект из устройства 9,
например `r_shield_g` у одного из варботов AutoDemo. Оригинал по RVA
`0x2c9ed` передаёт матрицу с осью на сторону удара, а вызов
`0x25ca0` запускает один из трёх экземпляров в режиме 1. FParkan
проигрывает две полусферы `Op9` с цветом MAT0 и звук `Op2` за время
из ресурса. У проверенных щитов оно равно половине секунды.

У варбота импульс охватывает корпус вместе с башней и внешними орудиями. В GOG
`AniMesh.dll` (SHA-256 `65659bf67f20e5be77d67a5b2f59968f61b94293143807fa59ca451c560c4f7e`)
ветвь RVA `0x9510` переносит сферы моделей к их точкам крепления
и усредняет центры с весами, равными радиусам. Затем она выбирает
наибольшую сумму расстояния от нового центра до центра модели и её
радиуса. Запрос `0x14580` переносит результат в мировые координаты.
У первого варбота AutoDemo шесть моделей дают радиус 7,17 вместо 3,80 у
шасси. FParkan собирает сферу для вспышки по начальной позе креплений.
Она даёт радиус 6,47 у этого варбота. Точное положение подвижных деталей
в расчёте AniMesh ещё открыто.

Для прошедшего к цели с записью Control 27 урона действует формула
`clamp(вход × (a + вход × b), 0, вход)`. Загрузчик берёт `a` и `b`
из второго и третьего коэффициентов записи. Для примера один варбот в
запущенном AutoDemo получил 90,95 единицы урона из входящих 235. В GOG
`Control.dll` (SHA-256 `bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`)
кэш заполняется по RVA `0x2d7f2`, а расчёт идёт по `0x10218`.
При известном узле FParkan вычитает результат из него.
У первой мишени без этого снижения 500 единиц, а у лазерного снаряда 249.
Три попадания дают остатки 251, 2 и 0. Пока объём положителен, Control обновляет его
через тот же механизм, что и другие изменения состояния узла.
При нуле FParkan удаляет объект из мира перед очередным вызовом
сценария, а рендер скрывает его модель, тень и привязанные эффекты.
Перед удалением сохраняется положение корпуса и ссылка на `EXPL` из
корневой записи NDP. Для `EXPL` версии 1 движок читает ссылку на FXID,
запускает его звук `Op2` и по времени с момента попадания отрисовывает
свет `Op1` и обращённый к камере спрайт `Op3`. Вершины спрайта идут по
периметру, а две его грани сходятся по диагонали между вершинами 0 и 2.
Например, у `exp_rbr_b`
спрайт с материалом `expl5` расширяется за 0,3 секунды, а свет сужается
и затухает за 2,4 секунды. Эффект остаётся на месте гибели машины,
даже если её слот уже занял другой объект.

Если FXID содержит `Op10` с пустой ссылкой на геометрию, FParkan
берёт уже загруженную геометрию. При гибели корпуса это навесные детали,
а при истощении секции шасси без замещающей модели это её собственные
треугольники. Например, `exp_rbr_l` у гусеницы тяжёлого варбота содержит
такой `Op10` и показывает обломок до шести секунд. Поза детали в последнем
кадре становится началом полёта. Скорость броска выбирается по размеру
детали. Смысл параметров `Op10` и точная баллистика ещё открыты.

В оригинале `Control.dll+0x10f30` при исчерпании корневого или критического
узла начинает процедуру уничтожения. В AutoDemo обработчик `0x10030`
получал прямые попадания в узлы 0, 9, 16 и 26. Расчёт входящего урона,
проверка навесных моделей и фазы разрушения ещё открыты.

Для строения FParkan проверяет треугольники корневой модели и вычитает
объём снаряда из запаса встреченного узла. Это важно для малого завода
из «Двух крепостей». У его корневого узла всего одна единица, а запас
всего здания складывается из запасов его частей и равен 238 002.
В запущенном оригинале урон изменил несколько узлов этого завода.
В GOG `Control.dll` (SHA-256 из раздела выше) процедура по RVA `0x10030`
принимает номер поражённого узла и передаёт рассчитанную потерю запаса в
`0x10f30`. Заголовок окна FParkan показывает оставшуюся долю общего запаса
заводов клана после первого повреждения.

При полном истощении узла FParkan запускает его `EXPL` в точке попадания.
У узла 3 малого завода `splant01.dat` запас составляет 10 000
единиц, а `explode_frt_b.exp` ссылается на трёхсекундный `exp_frt_b`.
В оригинале `Control.dll+0x11220` запрашивает эффект, когда стадия узла
повышается, и берёт матрицу узла. Промежуточные стадии и смещение эффекта
ещё открыты.

### Захват нейтральной машины

В таблице управления оригинала из `README/readme.htm` захват назначен
на Enter. В «Огневом рубеже» два нейтральных варбота принадлежат клану
с режимом 3 в TMA, а мишени и вражеский варбот — кланам с режимом 2.
FParkan использует исходный селектор клана размещённого объекта как
начального владельца в своём мире. Enter передаёт ближайшего живого
нейтрального варбота или мобильный центр управления в пределах 12 единиц
клану героя. Машина остаётся на месте и сохраняет исходный ID. Сценарий
проверяет текущего владельца. В «Огневом рубеже» это даёт цель за двух
варботов, а в «Телепорте» засчитывает захват мобильного центра.
Число 12 — временный радиус. Дальность и наведение оригинала ещё открыты.

В «Телепорте» сценарий отдельно спрашивает, есть ли в клане свободный
варбот для захвата. `ai.dll` по RVA `0x86fb` просматривает список клана
по порядку и возвращает логический ID первого варбота без задачи,
для которого Behavior сообщает размер 1 или 2. При пустой выборке
результат равен `0xffffffff`. Это проверено изолированным запуском
GOG `ai.dll` (SHA-256
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`).
FParkan пока берёт размер штатного шасси по ключу прототипа согласно
таблице GOG `Behavior.dll` по RVA `0xcee0` (SHA-256 указан ниже).

### Спуск под уровень земли

Контур BAS вырезает часть рельефа под заводом и соединяет край проёма с
окружающей землёй. Ходьба запрашивает те же треугольники, что участвуют
в отрисовке. Там, где контур убрал грунт, опорой становится геометрия
здания. Короткая вертикальная проба ищет ближайший пол в пределах шага.
Когда проба пропускает стык, герой сохраняет высоту и по-прежнему
сталкивается со стенами и дверями. При выходе наружный откос BAS снова
может стать опорой.

Со штатного старта «Конструктора» можно пройти через боковую дверь
большого завода в подземную рубку и вернуться по тому же спуску. Тест
строит путь по Res17 и подаёт обычный ввод ходьбы.

### Вода под ногами

Треугольники озера в «Конструкторе» несут бит `0x20000`. Вызов GOG
`Control.dll` (SHA-256 из [таблицы бинарников](../reference/original-binaries.md))
по RVA `0x1f670` переводит этот бит поверхности в бит `0x02` состояния.
FParkan учитывает воду в той же пробе, которая выбирает высоту грунта.
Настил строения может стать опорой над водой. Когда принятый шаг опирается
на воду, герой погибает на этом такте, и миссия засчитывает поражение.

### Посадка в варбота

Оригинальная подсказка `T02_H05` предлагает выбрать своего ведомого, подойти
и нажать Enter. Esc возвращает героя из машины. В GOG `iron3d.dll` по RVA
`0x39c00` этим действиям соответствуют `CMD_ENTER_STATE` и
`CMD_ROLLBACK_STATE` (SHA-256
`d1dc4ea8535e2069b0a05c9e8be2724dd438ba44cca7a83007d8b2e50f9e35fa`).

Команда `Enter` в `iron3d.dll` (RVA `0x72120`, ветвь `0x723D3`)
проверяет выбранный объект и расстояние между центрами в горизонтальной
плоскости. На RVA `0x72437` сравнение с константой из RVA `0xe4bc4`
отклоняет дистанцию от 20 единиц включительно. Для
варбота проверка допуска `0x77180` находит первое устройство с текущей
меткой `1` и требует положительное значение запроса `0x52`. В
`Control.dll` (RVA `0x2E690`, SHA-256 в [таблице бинарников](../reference/original-binaries.md))
этот запрос читает `0x400` у того же устройства. Значение берётся по
ключу узла. Поэтому выключенное или повреждённое оборудование с нулевым
значением закрывает доступ к пилотированию.

FParkan применяет эту проверку к выбранному дружественному варботу с
точкой `CameraCenter`. Клавиша F назначена в `addition.man` команде
`CMD_JAMES_SELECT_FRIEND`. В FParkan она запоминает союзника в центре
взгляда, а Enter использует сохранённый выбор, даже если игрок отвернулся.
Стрелки меняют положение его объекта, камера следует за ним, а герой едет
внутри. При выходе герой появляется сбоку у машины. Захваченный нейтральный
варбот становится дружественным после первого Enter, а следующее нажатие
позволяет сесть в его кабину при работоспособном устройстве. Правила выбора и
высадки пока приближённые.

При ручном ходе наземный варбот берёт пределы поперечного и продольного
движения из слов 6 и 7 действующего профиля Control. На рельефе
положение корпуса уточняют те же опорные точки шасси, которыми
пользуется автономное движение. Высота зависит от земли под вынесенными
лапами или колёсами. На полу здания опору задаёт геометрия пола.

### Полёт из кабины варбота

В начале «Телепорта» рядом с героем стоит лёгкий вертолёт. Брифинг
предлагает на нём перелететь через гребень к заводу в долине.
В `ui_bots.man` оригинала команды движения вверх и вниз назначены на
PgUp и PgDn. FParkan использует эти же клавиши. После отпускания клавиши
машина гасит скорость и сохраняет высоту относительно мира. На этой
высоте пилот может пересечь склон или долину. При снижении машина
останавливается у земли, а
обычная проверка строений действует вдоль всего шага, в том числе при
вертикальном движении.

В GOG-сборке `AniMesh.dll` по RVA `0x2FF0` шестая пара ссылок корневого
прототипа передаётся в `CreateBehaviour`. `Behavior.dll` по RVA `0x17660`
связывает поле `CanFly` из этого профиля. FParkan читает его при посадке.
Например, `R_T_02` и `R_M_02` ссылаются на `chas_fly.var`, а `R_T_01` на
`chas_wlk.var`.

В GOG `Control.dll` по RVA `0x153c0` три оси меняют скорость независимо.
Цель равна доле хода по оси, умноженной на предел из слов 6–8 текущего
профиля. За интервал обновления скорость приближается к цели не более
чем на ускорение из слов 0–2, умноженное на время. При отпускании цель
становится нулевой. В изолированном вызове DLL контроллер штатного
вертолёта `R_T_02` наращивает продольную скорость на 10 единиц в секунду
за четверть секунды, пока не достигнет предела.

FParkan применяет эту формулу к ручному полёту и интегрирует путь до
достижения целевой скорости и после него. При посадке и блокировке
сброшенная скорость не продолжает толкать машину сквозь преграду.
Способ интегрирования положения и контакт корпуса ещё приближены.
[Сборка оригинала](../reference/original-binaries.md).

### Текст подсказок миссии

Сценарий передаёт номер сообщения. В `messages.cfg` этому номеру соответствуют
отдельные ключи текста и голоса. Например, у подсказки о движении в
«Огневом рубеже» номер 14 и текстовый ключ `T01_H02`.
`DATA/TextRes.cfg` связывает ключ с номером строки в таблице
`TextRes.dll`. В GOG `iron3d.dll` (SHA-256
`d1dc4ea8535e2069b0a05c9e8be2724dd438ba44cca7a83007d8b2e50f9e35fa`)
чтение `messages.cfg` начинается по RVA `0x951c0`.

FParkan показывает эти строки поверх сцены по порядку поступления.
Время чтения зависит от длины текста и идёт по игровым часам.
Шрифт пока системный. Отдельный файл `Mistips.mis` относится к экрану
сведения о миссии. В исходной GOG DLL его путь собирается по RVA `0x695f0`.

### Состояние героя и базы

В одиночной миссии верхняя строка окна показывает героя или варбота, которым
управляет игрок. Здоровье — оставшаяся доля запаса корневого узла Control,
по которому сейчас считаются попадания. При посадке строка показывает запас
машины. Руда — текущий запас в буфере клана. Два числа энергии показывают
подачу и суммарный запрос по последнему такту распределителя. Когда запрос
выше подачи, строительство и другие потребители конкурируют за энергию.
Сообщения о паузе и исходе миссии имеют приоритет.

### Коммуникатор здания

В «Конструкторе» главный машинный зал отмечен указателями. Подсказка
`T02_H01` направляет игрока на зелёную площадку, с которой доступен
компьютер завода. FParkan находит площадку по обращённым вверх
треугольникам материала `B_COMP_4G` в модели здания. Пол и потолок рубки
используют этот материал. Проверка по полу позволяет захватить завод
после спуска по лестнице со штатной позиции героя. После нажатия Enter
на площадке нейтральное строение переходит к клану игрока.
Сценарий считывает нового владельца
при следующей проверке целей. Захваченный завод также переходит в
распределитель нового клана, откуда получает руду и энергию по запросу.
При переносе распределители пересчитывают доли участников.

У генератора в «Полевом лагере» внутреннюю площадку обозначает материал
`B_MTP_07G`. FParkan использует обращённую вверх поверхность этой геометрии
и обычный допуск по высоте. После захвата генератор подаёт энергию игроку,
а сценарий засчитывает первую цель и включает следующую реплику.

Тот же материал обозначает пол рубки ангара и зелёную площадку
в «Телепорте».

При ходьбе движок опускает короткий отрезок от предполагаемого положения
героя до ближайшей поверхности здания. Так высота следует за полом
или лестницей в пределах одного шага. В «Конструкторе» пол машинного зала
завода лежит ниже поверхности карты. Без такой проверки высота ландшафта
удерживала героя над залом.

На подъёме проверка корпуса сначала поднимается, затем проходит над
ступенью. На спуске порядок обратный. Возле края пола бывшая опора
проверяется под исходной позицией. Когда поверхность земли уже доступна
и потолок её не закрывает, она подхватывает героя на выходе.
Это позволяет пройти по размеченным в `Res17` коридорам среднего бункера
в «Двух крепостях» от стартовой комнаты наружу.
Если кадр длится дольше 20 мс, ходьба проверяет промежуточные точки.
Иначе длинный шаг мог пересечь сразу несколько ступеней и упереться
в лестницу. Когда следующий отрезок перекрыт, герой остаётся в последней
доступной точке и сохраняет поворот мыши.

Наружные створки выбирают узлы по записям Control типа 12. В GOG-сборке
`Control.dll` диспетчер по RVA `0x2d4b0` создаёт для них общий
контроллер, а его метод по RVA `0x20900` меняет положение связанной
детали. Измерение в запущенном оригинале показало движение одной из
створок. FParkan открывает её при приближении героя, используя два
исходных кадра. Коллизия и видимая модель получают одну и ту же позу.

В GOG-сборке `Behavior.dll` (SHA-256
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`)
обрабатывает захват здания в ветви RVA `0x8ef9`. В этой ветви RVA
`0x8f71` и `0x9032` вызывают снятие объекта со старого клана и добавление
к новому. Операции списка (`0x1abf0` и `0x1aac0`) пересчитывают доли
через `0x1ac90`. Точные границы
срабатывания и открытие интерфейса МЦУ ещё исследуются.

Обработчик `iron3d.dll` по RVA `0xa4840` выбирает реплику по прежнему
владельцу строения. FParkan ставит в очередь `VOICE_NBUILD_CAPTURE` для
нейтрального здания и `VOICE_EBUILD_CAPTURE` для вражеского. Имена голосов
разрешаются через `ui/game_resources.cfg`. Реплика подтверждает именно
смену владельца и предшествует голосу о выполнении цели миссии.

В большом заводе «Конструктора» запись CTLD типа 13 связывает две
дорожки зелёного заграждения с узлами модели. На начальных кадрах
створка убрана. На конечных она охватывает коммуникатор, и снаряд
останавливается при пересечении её треугольников без урона строению.
FParkan подаёт одну фазу в отрисовку и расчёт попадания. В GOG
`Control.dll` (SHA-256 `bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`)
метод `0x20900` выбирает следующую фазу. В расчёте по RVA `0x22120`
длительность отрезка задаёт самая медленная из связанных дорожек.
Для постоянного входа скорость равна произведению коэффициента записи
и скорости дорожки. Вызов DLL с данными большого завода дал 0,2 фазы в
секунду и пять секунд на полный ход. Возобновление ходьбы пока служит
сигналом подъёма поля.

### Выход из миссии через телепорт

У главного телепорта есть переход с верхней площадки на нижний ярус.
Герой захватывает сооружение у коммуникатора и входит на верхнюю площадку
телепортации. В модели `FR_M_MTP.msh` входы помечены `0x8000`.
Штатная точка прибытия ниже поверхности и помечена `0x10000`.
В GOG `Behavior.dll` обработчик по RVA `0x18ac0` проверяет владельцев героя,
сооружения и генераторов перед переносом. FParkan проверяет владельцев
действующих генераторов миссии и переносит героя в точку прибытия.

Последняя подсказка «Телепорта» просит нырнуть под арку. Центр зоны
под аркой задан в потоке `Res17` модели `FR_M_MTP.msh` и привязан к узлу
модели. У обычной точки выхода с флагом `0x4000` радиус равен 5 единицам,
а высота составляет по 3 единицы вверх и вниз от центра.

В GOG-сборке `Behavior.dll` с указанным выше SHA-256 подготовка точек
начинается по RVA `0x186b0`. Проверка цилиндра по RVA `0x22c80` включает
стенку и обе крышки, что подтвердил прямой вызов функции из DLL. Ветвь
по RVA `0x1914f` проверяет героя и передаёт событие выхода сценарию.

FParkan пересчитывает центр по положению здания, его масштабу и
исходной позе узла. Оригинальный обход кандидатов по RVA `0x18310`
берёт их положение из матрицы, которую запрашивает функция по RVA
`0x14b30`. Точка опоры FParkan лежит ниже центра героя. Поэтому для
выхода движок проверяет также точку над опорой с зазором из штатного
старта. Когда герой пешком входит в зону главного телепорта,
движок вызывает `Hero_Teleported` из сценария миссии. В «Телепорте»
команда сценария завершает миссию. Игра выводит «Миссия выполнена»
в заголовке окна и ставит в очередь голосовое сообщение о победе.

### Месторождение и шахта

В «Полевом лагере» запас руды задан в конце TMA. Загрузчик MisLoad.dll
по RVA `0x1530` отдаёт первые шесть слов записи. Хост по RVA `0x81c60`
передаёт ArealMap координаты в плоскости и исходный запас. Стандартная
задача шахты в Behavior.dll подбирает залежи в радиусе 250 единиц и ограничивает
добычу вместимостью буфера. Базовая скорость из конструктора профиля
равна 50 единицам в секунду. Для этих сборок см. [хеши модулей](../reference/tma.md#placedobject).
Вход выбора залежей находится в Behavior.dll рядом с RVA `0x2cda2`,
шаг добычи начинается по RVA `0x2cf60`.

В FParkan шахты, уже стоящие на карте, начинают добывать руду из близких
залежей. Клавиша M возле свободной залежи заказывает малую шахту из
`BuildDat.lst`. Союзный строитель в зоне заказа отдаёт 100 руды из своего
запаса. Добытая руда сначала попадает в буфер шахты, затем её может забрать
распределитель клана. Временный порядок ставит шахту сразу на координаты
залежи и использует базовую скорость. Ручной выбор строителя и площадки,
движение к ней, фазы сборки и регулировка питания пока открыты.

### Исследование в лаборатории

В «Телепорте» клан уже знает, как построить корпус большого летающего
варбота. Чтобы поставить на него башню, герой захватывает лабораторию
и даёт заказ. На своём коммуникаторе клавиша R выбирает первую деталь,
доступную для исследования по таблице клана. После завершения знание
остаётся у клана. Проверка деталей платного заказа на заводе учитывает
новое состояние.

В GOG `Behavior.dll` со SHA-256 из главы о захвате лаборатория читает
`FreeTechnoNum` и `FreeResearchTime` по RVA `0x0b110`. Ветка RVA
`0x2f8f1` расходует одну бесплатную работу и обнуляет цену исследования
в руде и энергии. FParkan отсчитывает время бесплатного заказа по часам
миссии. В данных «Телепорта» лаборатории выделены пять работ по пять секунд,
а первым доступен для разработки один вариант большой башни.

Клановый AI заказывает целую схему из своего каталога. Обёртка `41` в GOG
`ai.dll` по RVA `0xd4a3` передаёт имя DAT в приказ лаборатории через
RVA `0x11100`: команда `0x10`, цель `0x205`, режим вставки `3`.
В `Behavior.dll` подготовка задачи находится по RVA `0x2f470`, сбор строк
проекта — `0x23790`, начало — `0x2f710`, обновление — `0x2f730`.
SHA-256 этой DLL:
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`.

Обновление задачи ограничивает таймер объекта Behavior по смещению `+0x930`.
Конструктор RVA `0x398f` задаёт ему слова периода и разброса `1/1`, а
обработчик RVA `0x54a0` допускает задачу через проверку RVA `0x4c550`.
Нулевой срок допускает первый шаг. Остальные шаги проходят только при
`now > deadline`; равенство не расходует RNG. Новый срок вычисляется так:

```text
deadline = now + 64 + ((rand() & 255) * 64 >> 8)
```

При запоздании следующий срок отсчитывается от фактического времени вызова.
Исполнение нативного таймера подтвердило строгую границу, перенос срока и
расход RNG только на допущенном шаге. Живой вызов лаборатории дал интервалы
70–132 мс: к периоду 64–127 мс добавляется ожидание очередного вызова обработчика.
FParkan применяет этот таймер к активной задаче лаборатории и использует
общий RNG Behavior с распределителями ресурсов. Фаза бездействующего
объекта и полный порядок событий ещё отмечены `script_lab_clock_approx`.

Помимо часов задачи у лаборатории есть ресурсные часы Control. Их бюджет
обновляет множитель рабочего устройства, а затем `E00` определяет темп
исследования. При пустом запасе и отсутствии внешней подачи энергии
энергетическая работа останавливается, хотя время задачи продолжает идти.
После восстановления питания работа продолжается с сохранённых накопителей.
Бесплатное исследование с нулевыми ценами по-прежнему ограничивается временем.

Каждая технология накапливает три величины: руду, выполненную работу по
энергии и время. Продвижение ограничивает самая медленная из трёх долей.
Темп берётся из суммы коэффициентов `E00` устройств Control. Профиль
`prof_institute.var` задаёт расход энергии `Use_Power = 3` и руды
`Use_Ore = 1`. За шаг длительности `dt` задача прибавляет к работе
`E00 * Use_Power * dt`, а к руде — минимум доступного буфера и
`E00 * Use_Ore * dt`. Это выполненная работа; саму энергию распределяет
Control через запрос `500`, установленный в `Use_Power`.

После шага рудный буфер обнуляется. Новый запрос равен оставшейся цене,
а при остатке больше пяти единиц — половине остатка. Поэтому лаборатория
получает руду через общий распределитель, а не списывает всю цену сразу.
Прогресс клана увеличивается на разность новой и прежней минимальных долей;
технология готова при `progress + 0.001 >= 1`. Вызов оригинальной задачи с
x87 `0x007f` подтвердил шаг с ценой 10 руды и 30 энергии: при `E00 = 2`
за секунду накопились 2 руды, 6 работы, прогресс 0.1 и запрос ещё 4 руды.

`FreeResearchTime` ограничивает снизу длительность и платной работы.
По умолчанию это две секунды (конструктор RVA `0x3a52`). Бесплатная квота
расходуется при начале каждой технологии и обнуляет обе цены, сохраняя
ограничение по времени. Вызов той же задачи подтвердил бесплатное
завершение без подачи ресурсов. FParkan хранит общий прогресс технологий
клана, освобождает лабораторию после заказа и продолжает сценарное ожидание
`PBM_MAKE_RESEARCH` до освобождения или уничтожения здания.

Завершение учитывается при проверке деталей производства и строительства.
В GOG `MisLoad.dll` (SHA-256
`c607762bb67db14ca530927c8e1347339b62b0a163ac90c708ee83142292e2bf`)
метод RVA `0x2c10` сначала проверяет включённость строки, затем устанавливает
доступность и изученность, сохраняя остальные биты. После этого он сканирует
все строки таблицы: ещё недоступная включённая строка открывается, когда
каждая предпосылка из `TRF2/TRF3` включена и изучена. Пустой список
предпосылок удовлетворяет условию. Выключенная строка не меняет таблицу.

Помощник `Behavior.dll` RVA `0x23aa0` затем обходит прямых потомков из
`TRF4/TRF5` в исходном порядке. Доступного неизученного потомка с ценами
руды и энергии ровно ноль он завершает тем же способом, сразу углубляясь
в его потомков. Отрицательная цена не считается бесплатной. FParkan
передаёт полученное знание клану без дополнительной работы лаборатории
и считает открытия строк в `script_research_available`.

Вызовы обоих оригинальных методов подтвердили маски флагов, проверку всех
предпосылок и порядок бесплатного каскада. На штатном `scream.trf`
завершение строки 20 изучает также строки 68 и 69. Первая технология AI,
строка 19, новых строк не открывает; то же наблюдается в оригинале.

При новом приказе лаборатории выбирается следующий проект.
В GOG `ai.dll` обёртка `41` по RVA `0xd4a3` сначала ищет лабораторию;
при успешном поиске RVA `0xd524` вызывает chooser `0x10f90`, затем передаёт
выбранный DAT через `0x11100`. Изолированный вызов подтвердил обновление
состояния каталога даже перед отказом для уже изученного кандидата.
FParkan повторяет этот порядок: пересчитывает кандидатов по изменённой
таблице клана и начинает очередной проект. Поэтому сценарий со штатного
старта продолжает исследования после первой технологии, включая бесплатных
потомков новых проектов.

Запрос `56` читает сохранённый результат обхода каталога, а не разрешение
на исследование. В той же GOG `ai.dll` RVA `0xe430` возвращает 1, если байт
`AI+0x431` ненулевой, и 0 в противном случае. Сам обход `0x10f90` начинает
с единицы и сбрасывает её в ноль, встретив хотя бы одного кандидата с нулевым
статусом. Поэтому обработка последнего такого кандидата ещё не меняет ответ:
единица появится после следующего обхода, уже не встретившего непроверенных
записей. Запрос не обновляет каталог. Вызовы DLL подтвердили сохранение
этого состояния и нормализацию ненулевого байта; FParkan передаёт его
сценарию и считает ответы по клану в `script_research_scan_status`.

Параметр `69` относится к выбору схемы для завода. По инструкциям потребителя
RVA `0x10abc` он задаёт диапазон случайного смещения в отсортированном
списке; исполнение этой ветки и восстановление свойств кандидатов для `65`
ещё открыты. Пересчёт проекта выполняет `41`.

### Заказ завода

Во время сборки у завода отдельно накапливается время работы. В бесплатной
ветви оригинал выбирает длительность по мощности завода и типоразмеру
робота. Например, большой завод собирает лёгкий корпус за 20 секунд, средний
за 40, большой за 60. После завершения завод расходует одну единицу
бесплатного запаса и создаёт робота своего клана. В GOG `Behavior.dll` с хешем
из раздела выше таблица находится в ветви RVA `0x29ff3`, проверка
завершения начинается в RVA `0x2a75c`, а запас уменьшается по RVA `0x2a816`.

Оригинал читает список `prebuild` из `mission.cfg` и ищет его схемы в
`units/units/prebld`. Это делает GOG `iron3d.dll` по RVA `0x4e190`
(SHA-256 указан в разделе о пополнениях AutoDemo). В «Полевом лагере»
первая запись указывает на `tut3_p1.dat`.

В оригинале заводы доступны из тактической панели уже со старта. FParkan
открывает список B и показывает пары «свой завод и готовая схема».
Размер шасси ограничивает выбор. Стрелки меняют выбор, B или Enter
подтверждает одиночный заказ, Esc закрывает список. Владелец завода
проверяется при подтверждении. На коммуникаторе B показывает схемы этого
завода или сразу заказывает единственную подходящую. При запуске можно
указать одну схему через `--build-scheme`. Повторяемый параметр
`--build-part СТАРАЯ=НОВАЯ` заменяет внутренние детали этой схемы.
Например, `i_pws_b_02=i_pws_b_01` ставит другой аккумулятор в тот же
разъём большого корпуса. У записи Unit DAT сохраняются родитель, номер
крепления и остальные поля. Схема хранится в памяти до конца миссии.
На заводе она появляется под именем `custom.dat`. При заказе завод
проверяет доступность и исследованность деталей, включая бесплатную сборку.
Тики миссии отсчитывают время сборки выбранного робота.
При завершении новый робот входит в реестр мира и становится виден скрипту
и рендеру. Следующий заказ можно дать после выпуска. Каждый робот получает
свою запись мира, а после уничтожения его место можно занять новым корпусом.
FParkan подготавливает для каждой схемы восемь таких мест. Заказ занимает
свободное место в резерве выбранной схемы.
Если завод исчез или сменил владельца во время сборки, заказ снимается.
Готовая машина появляется над центром завода. В штатных «Двух крепостях»
GOG `Behavior.dll` (SHA-256 из раздела выше) по RVA `0x146b0` нашла лучом
крышу на высоте 90,06 и прибавила 100. Код выпуска по RVA `0x2a9c4`
прибавил ещё 15. Координаты первого робота, переданные по RVA `0x2aa14`,
составили `X=1824,21 Y=2032,02 Z=205,06`. Луч по геометрии завода в FParkan
даёт ту же высоту крыши. Если модель недоступна или луч её не находит,
сохраняется выпуск на свободный грунт снаружи.

FParkan проверяет, есть ли за пределами площадки свободное место с запасом
под ширину корпуса. Если место занято или предыдущая машина ещё выезжает,
готовый заказ ждёт. Новый корпус движется к выходу обычным контроллером и
снижается до опоры ходовой либо до высоты полёта. Пока он над проекцией
завода, спуск ограничен высотой крыши с запасом под корпус. Ускорение спуска
и выбор стороны выхода пока приближённые.
В оригинале вызов по RVA `0x2aae7` также поставил отдельную задачу выхода,
а первый последующий приказ попал в очередь по RVA `0x456c`. В FParkan
во время выезда приказы ждут и орудия не открывают огонь.

`B_Sphere_*` записаны в заводских CTL как эффекты типа 5. GOG
`Control.dll` по RVA `0x2e0e` получает имя ресурса и строит его матрицу
по центру и радиусу сферы объекта. В запуске «Двух крепостей» эти вызовы
прошли при загрузке строений. При первых двух выпусках они не повторились.
Меняют ли заказы фазу уже загруженного эффекта, пока открыто.

Число машин ограничивает запас «мозгов» клана. `Handler(49)` в GOG `ai.dll`
(SHA-256 `c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`,
RVA `0xdb2e`) считает только свободные слова `0xffffffff` в массиве AI
`+0x83c`. Ноль уже означает занятое место. Со штатного старта «Двух крепостей»
у противника заняты пять из девяти мест, у игрока — шесть, включая героя.
Вызов DLL подтверждает ответы 4 и 3 для свободного и зарезервированного
следующим заказом места противника.

Резерв возникает до выпуска робота: `Behavior.dll` (SHA-256 указан выше)
записывает ноль по RVA `0x2a0bb`. Перед созданием машины ветвь `0x2a7e5`
снимает резерв, после чего место занимает ID новорождённого. Эти записи
проверены аппаратной точкой останова на первом заказе штатной миссии.
FParkan пока проецирует занятость по живым мобильным объектам и заказам
действующих заводов своего клана. Выпуск заменяет резерв машиной без изменения
свободного остатка; потеря машины или отмена заказа освобождает место.
Сценарий получает текущий остаток, поэтому заполненный клан прекращает
ставить новые заявки. Собственные ID нативных «мозгов» и правила допуска
заказа при полном массиве остаются открыты.

В платной ветви завод находит каждую деталь схемы в TRF-таблице клана.
Для сборки нужны оба разрешающих флага записи, а две одинаковые пушки
оплачиваются дважды. Стоимость берётся из двух полей сборки TRF0.
Например, для `tut3_p1.dat` сумма деталей составляет 125,6 руды и 72,7
энергии. Платный заказ делит рудную цель на коэффициент завода, если тот
достаточно велик. Завод запрашивает руду у распределителя и расходует её
из своего буфера. Выпуск ждёт обе цели и минимум пять секунд. Обход деталей
проверен исполнением в той же GOG-сборке Behavior.dll, RVA `0x29810`.
Начало и ход заказа восстановлены по RVA `0x29ba0` и `0x2a4f0`.
Заводская задача проходит через таймер владельца, описанный выше:
диспетчер RVA `0x34a30` вызывается только после допуска в RVA `0x54a0`.
В живом оригинале завод имеет слова таймера `1/1`; последовательные вызовы
RVA `0x2a4f0` подтвердили период 64–127 мс с ожиданием следующего кадра.
Это влияет на оплату: запрос руды содержит постоянную прибавку `0,07`
за вызов, поэтому обновление на каждом кадре ускоряло её накопление.
FParkan допускает шаг активного заказа тем же таймером и общим RNG Behavior.
После задержки выполняется один шаг, без серии догоняющих списаний.
Счётчик `script_factory_clock_approx` показывает число таких шагов по клану
и заводу; фаза таймера до заказа и общий порядок вызовов владельцев открыты.
Передаваемая кланом энергия меняет множители устройств Control. Ресурсный
бюджет завода распределяет её между потребителями, включая добавку платной
сборки, и меняет множитель её устройства tag `26`. Поэтому темп работы теперь
берётся из текущего `E00`, а не из проверки наличия генерации у клана.
При недостатке бюджета устройство получает часть запроса и работает медленнее.
Полный Control tick остальных владельцев и сравнение времени выпуска на всей
миссии ещё открыты.

### Ремонтная площадка

Площадку задают точки `Rech_w`, `Rech_h` и `Rech_d` в CPT здания.
Например, у большого завода по одной тройке снаружи и внутри, а у ангара
одна тройка. По тем же точкам движок находит площадки внутри укрепления
и на генераторе в «Двух крепостях». Узлы модели задают положение и
поворот каждой тройки.
FParkan берёт векторы ширины и длины как полуоси от центра настила,
а третий вектор задаёт высоту над ним. Поэтому герой под площадкой и
машина, стоящая рядом, не попадают в её объём.

Машина или герой своего клана восстанавливает прочность корпуса на
очередном ресурсном шаге Control. Временная скорость составляет десять
процентов максимальной прочности в секунду. Данные о внутренних и внешних
площадках берутся из ресурсов оригинала. Расход питания, боеприпасы и
точный темп обслуживания ещё открыты.

### Наблюдение за автономным боем

Чтобы сравнивать ход боя, недостаточно времени первого выстрела во всей
миссии: нужно знать, какая машина стреляла и кого она уничтожила. Общий
цикл окна и `--sim-report` собирает число выстрелов и уничтожений для каждой
пары стрелок–цель, время первого и последнего события в миллисекундах миссии.
Например, `sim_combat shots=12 shooter=7:0 target=9:0 first_ms=25000`
означает двенадцать выпущенных снарядов по этой цели, начиная с 25-й секунды.
Уничтожение учитывается при обработке попадания, а не при выборе цели.

В AutoDemo ноль этой сверки — первое пополнение при запуске. Обе версии
сразу добавляют по одной машине на клан. В оригинале наблюдение
`Control.dll` по RVA `0x2a398` фиксировало первый выстрел через
0,33–0,54 секунды. В одном запуске первая машина исчерпала корневой запас
через 29,36 секунды и в тот же тик вызвала новое пополнение. Измерение
истощения использует ветвь `0x110b1` для корня мобильного объекта.
В FParkan со штатного старта первым стреляет варбот 3 по варботу 0.
Расстояние между ними около 405 единиц. Выстрел происходит через
0,15 секунды, а первое уничтожение с учётом силовых полей — через
23,43 секунды.
Вызов атаки
`Behavior.dll+0x25320` до первого выстрела оригинала не наблюдался,
поэтому время само по себе не задаёт правило выбора цели.

В «Двух крепостях» первый заказ оригинала завершился примерно через
10,1 секунды после его создания, в точке `Behavior.dll+0x2aa14`.
Обе версии выпускают `12spd1.dat`. В FParkan первый выпуск происходит
примерно через 10 секунд после заказа. В запуске оригинала первый
снаряд `Control.dll+0x2a398` был выпущен через 56,71 секунды после рождения
варбота. Через 0,71 секунды открыла огонь другая сторона.
В повторном запуске первый выстрел вертолёта произошёл через 53,37 секунды
после выпуска.
Первое исчерпание запаса мобильного объекта `Control.dll+0x110b1`
наступило через 90,36 секунды после первого выпуска. Эти адреса относятся
к GOG `Control.dll` с SHA-256
`bcb86318089028548a178b03a21accdce15df0cc85ddd91674cf3c2f55012c6e`.

В FParkan вертолёт клана противника начинает огонь на 24,72 секунде
от старта, уничтожает первую машину на 57,83 и продолжает маршрут.
Стоящий рядом с заводом варбот игрока отвечает на 88,73 секунде.
На 197,40 секунде вертолёт доходит до рубки генератора и меняет
его владельца. В оригинале запись, начатая после выпуска, зафиксировала
захват малого завода через 573,77 секунды после выпуска. Начало записи
не позволяет считать этот захват первым. Выбор первой цели и порядок
захватов в двух версиях остаются открытыми.

В записи сохраняются исходный ID объекта, слот и поколение. Поколение
различает старую машину и подкрепление, которому достался тот же слот;
данные стрелка сохраняются в снаряде до его попадания. Поэтому удаление
участника боя не стирает его из отчёта. В окне первые события каждой пары
пишутся в лог, а итоговый отчёт добавляет накопленные количества.

`unit_combat_unavailable` разделяет пропуски по объекту и причине: подготовка
снаряда, пуск, движение, контакт и точка ствола. Ответ обработчика урона без
изменения состояния (`damage_unavailable`) отделён от ошибки (`damage_error`);
первый такой контакт также пишет цель, узел и ответ обработчика. Отдельная причина
`empty_weapon_bank` относится к подготовке машин без доступного оружия,
включая невооружённых строителей и подготовленные резервные схемы; она не доказывает пробел в
алгоритме. Эти наблюдения описывают исполнение FParkan. Совпадение времени
боя с оригиналом проверяется отдельно, при одинаковом старте и условиях запуска.

### Завершение приказа атаки

В каждом такте Attack проверяет, доступна ли цель. Если lookup больше не
находит объект, состояние цели несёт маркер истощения `0xfffe` или запрос
позиции возвращает служебный нулевой вектор, задача заканчивается и освобождает
очередь. Статическое строение при этом может оставаться в мире: его стадия
разрушения и время существования модели обрабатываются отдельно.

FParkan использует эту проверку перед выбором цели огня и при переходе к
следующему приказу. Так варбот штатного рейда `CAMPAIGN.04/Mission.02` после
истощения бункера может исполнить Go для отхода и последующий ShutDown.
Если следующих приказов нет, завершённый Attack снимается. Условие проверяет
полный handle с поколением, чтобы состояние прежней машины в том же слоте
не завершило атаку на новую. Лог `script_attack_finished` отмечает переход;
наведение, движение и анимации выключения ещё требуют отдельной доводки.

### Оборона в одиночных миссиях

В «Двух крепостях» герой начинает со своей базой. Исходный сценарий
проверяет, сколько у противника осталось машин и строений. Для клана,
чей сценарий остановился при запуске, FParkan включает временную оборону.
Вооружённые машины стреляют, когда в пределах дальности появляется
противник и рельеф не закрывает линию огня.
Свободный вооружённый варбот может наводиться и стрелять из текущей позиции.
В штатной миссии без приказа диспетчер GOG `Behavior.dll` (SHA-256
`ddfbdbde07832358fe6e35e01c8dba9b58e7313789498b6049ed51d4ed9baf99`)
по RVA `0x34a4f` вызвал обработчик варбота `0x31e10`. Он передаёт оружию команду
`[2, 0xffffffff, 0.5]` через `0x23f30` и сбрасывает состояние
движения через `0x3c540`.

Режим 2 в `0x240ae` вызывает поиск `0x254b0`. Он измеряет расстояние по
XY между корнями объектов и оценивает кандидата как `1 / (10 + расстояние)`.
Граница поиска строго меньше 500 единиц. При равенстве оценок после
округления сохраняется первый кандидат. Вызов DLL подтвердил границу,
равенство на разных высотах и смену цели при смещении стрелка. После выбора
ствол наводится на цель, а возможность выстрела по-прежнему зависит от
дальности конкретного орудия и линии огня.

Опрос оружия использует слова таймера 1/1 из RVA `0x23edb`, а обновление
цели внутри опроса — 31/15 из `0x23eee`. Оба работают в единицах 64 мс и
используют генератор Behavior. Поэтому ствол может ещё следить за прежней
целью, когда другой противник уже подошёл ближе. FParkan собирает кандидатов
из живых машин враждебных кланов. Наполнение и порядок списка восприятия
оригинала и общий порядок вызовов RNG пока открыты.

Когда в машине находится игрок, её вооружение остаётся под ручным
управлением. Автономное орудие сохраняет возможность стрелять, пока
контроллер ведёт машину к указанной точке. Выключение и заводской
выезд прерывают поиск целей.

На штатном старте «Двух крепостей» вертолёт с двумя `bl_t_01` открывает
огонь на ходу. В GOG `Control.dll+0x2a398` два его залпа разделяли
1,225 секунды и 17,6 единицы пути. До первого залпа вызов задачи атаки
`Behavior.dll+0x25320` не наблюдался. В FParkan стрельба по найденной
цели проходит в такте движения, а точка назначения сохраняется.
Таблица отношений из TMA определяет противников, поэтому на карте с тремя
кланами вражеские машины могут стрелять и друг в друга.
При проверке линии огня расстояние до поверхности корпуса сравнивается
с расстоянием до рельефа. У стоящего на земле героя центр сферы модели
может лежать под поверхностью. Если луч сначала задевает открытую
часть сферы, варбот может выстрелить, а снаряд попадёт до контакта с землёй.

На отдельных картах `Single.*` сценарий может содержать групповой приказ
атаковать завод. Тогда исходные боевые машины клана с остановленным
`Init` получают маршрут к ближайшему вражескому
заводу из начальной расстановки. По дороге они могут вступить в бой с
защитниками. Если видимая машина вне дальности, AI может открыть огонь
по назначенному заводу. Групповой приказ восстанавливается по `ai.dll` (GOG, SHA-256
`c19cd6cd31cd2896f8c4ba0f0e700dd3408aec8182daaf4863d98a7d233a2abc`,
RVA `0xba01`), где он рассылается участникам выбранной группы. В оригинале
«Двух крепостей» машины AI подходили к базе, пока герой оставался на старте.
FParkan использует временный маршрут с начала миссии. Когда собирать группу,
кого включать в неё и когда переключать цель, ещё предстоит восстановить.

На зелёном коммуникаторе вражеского здания клавиша Enter передаёт
его клану игрока. Дипломатия из TMA определяет, кого можно атаковать
и чьи здания можно захватывать. Сценарий считает строения по текущему
владельцу, поэтому захваченный завод сразу перестаёт числиться за
противником. В GOG `iron3d.dll` со SHA-256 из следующего раздела
обработка уведомления о захвате начинается по RVA `0xa4840`. У неё
есть отдельное голосовое сообщение для захвата вражеского здания.

### Поражение при гибели героя

В «Двух крепостях» отдельный путь игры отвечает за гибель героя.
В GOG `iron3d.dll` со SHA-256 `d1dc4ea8535e2069b0a05c9e8be2724dd438ba44cca7a83007d8b2e50f9e35fa`
обработчик удаления по RVA `0x755f0` проверяет класс героя и его
принадлежность локальному клану. Затем процедура по RVA `0x61d90`
запускает голос поражения и записывает исход.

FParkan запоминает единственного героя местного клана при загрузке
одиночной миссии. Если его убрали из мира во время активной миссии,
тот же тик объявляет поражение. Игра меняет заголовок окна и один
раз ставит в очередь оригинальное голосовое сообщение. В Windows
победа и поражение также выводятся поверх сцены. Итог вытесняет
текущую подсказку и остаётся на экране, даже если у миссии нет
`messages.cfg`.

### Joystick через DirectInput

`Joystick.dll` экспортирует:

```text
QueryJoy
CreateJoy
ReleaseJoy
SetJoyRange
PeekJoyMessage
GetJoyCaps
```

`QueryJoy` обнаруживает устройство, `CreateJoy` получает интерфейс DirectInput,
`SetJoyRange` нормализует оси в диапазон движка, `PeekJoyMessage` выдаёт
очередное унифицированное событие.

При потере устройства чтение может вернуть ошибку acquired state. Интерфейс
следует повторно получить, очистить устаревшее состояние и продолжить.
Hot-unplug не должен оставлять последнюю ось навсегда отклонённой.
`GetInstalledJoyNames` и `SetActiveJoy` в World3D связывают device list с
game-facing выбором.

### Два camera interface

World3D предоставляет `stdSetCurrentCamera`/`stdGetCurrentCamera`: это камера
как часть игрового состояния. Terrain имеет
`stdSetCurrentCamera2`/`stdGetCurrentCamera2`: concrete camera, которую world
renderer использует для matrices, viewport и visibility.

`LoadCamera` экспортирован обоими модулями. По call graph World3D-вариант
играет роль component bridge, а Terrain-вариант связан с concrete
camera/world implementation. Это архитектурный вывод: точные class names и
layout не восстановлены.

Минимальные данные камеры:

```text
world position and orientation
view matrix
projection parameters / field of view
near and far planes
viewport rectangle
camera mode and target object
manual angles/state
```

Такая граница позволяет game code работать с абстрактной камерой, не зная
внутреннего renderer representation.

### Camera commands и порядок кадра

Подтверждены команды `CMD_CAMERA_LEFT`, `CMD_CAMERA_RIGHT`, `CMD_CAMERA_UP`,
`CMD_CAMERA_DOWN`, `CMD_CAMERA_CENTER`, `CMD_CAMERA_INFRARED`, а также
spotlight и внешние/миссионные camera modes. Горизонтальный угол использует
wrap, вертикальный -- ограниченный диапазон. Center плавно возвращает обе оси к
заданному значению.

Порядок кадра:

1. собрать manual events;
2. обновить camera controller во время calculation;
3. вычислить итоговый transform и ограничения;
4. перед render установить current camera;
5. передать её Terrain и sound listener;
6. после кадра сохранить mode-specific state.

Camera smoothing должно использовать игровое время или специально
подтверждённые часы. Привязка к render delta делает управление разным при 30 и
144 FPS.

## Звуковая подсистема

Ngi32 создаёт низкоуровневый DirectSound backend. `services.dll` публикует
`ISoundServer`. Game, Terrain и FX работают уже через эти интерфейсы:
воспроизводят 2D/3D sources, меняют volume и связывают listener с camera.

### Звук выстрела

Событие выстрела автономного орудия хранит ссылку на его эффект и ту же
мировую точку дула, из которой запущен снаряд. При подготовке сцены FParkan
читает из эффекта команду `Op2`. Для отдельного компонента с одним орудием
подходит единственная безусловная строка, у которой первая точка эффекта
совпадает с точкой дула. Команда задаёт запись звука, радиус слышимости и
начальную частоту. Одноразовый источник размещается у дула с учётом
положения текущей камеры.

Событие обрабатывается при получении нового результата симуляции. Если
миссия на паузе, отрисовка повторяет последний результат без нового звука.

### Погода, осадки и звуковые события

Погода для игрока — это одновременно движущиеся точки на экране и звуковой
фон. Расписание `sky.ske` говорит, в какой момент действует дождь, снег или
молния, а `sky.wea` назначает имена материалов. Система окружения каждый
кадр превращает это состояние в два списка: мировые частицы для renderer-а и
звуковые переходы для audio backend-а.

```text
sky.ske + sky.wea
  -> состояние погоды
  -> EnvironmentFrame
       -> Particle / Lightning (renderer)
       -> StartLoop, SetLoopVolume, StopLoop, OneShot (sound)
```

Такое разделение нужно для понятной границы ответственности. Система погоды
решает, **что** произошло и где находится источник. Renderer решает, как
нарисовать прозрачный квадрат или молнию. Audio backend разрешает архив и
имя, создаёт источник звука и сравнивает его с текущим listener.

У осадков есть объём перед наблюдателем. Эталонные границы имеют глубину
`2..50`, половины углов `0.65` и `0.4875` радиана. Для текущей камеры:

```text
half_y = tan(vertical_fov / 2) * 50
half_x = half_y * aspect_ratio
```

Размер осадков получает тот же camera query, что и native `Terrain`: ширина
viewport делится на горизонтальный FOV в радианах.

```text
horizontal_fov = 2 * atan(tan(vertical_fov / 2) * aspect_ratio)
precipitation_scalar = viewport_width / horizontal_fov
rain_size = precipitation_scalar * 0.0065
snow_size = precipitation_scalar * 0.0195
```

Число точек получает масштабирование по отношению текущего объёма к
эталонному и округляется к ближайшему чётному целому:

```text
N = round_even(clamp(current_volume / reference_volume, 0, 1)
               * density * intensity * 1000)
```

В рабочем эмиттере `density` равна единице. Точка сначала появляется в
локальных координатах этого объёма, затем получает мировую позицию. Дождь
движется с мировым вектором `[0.5, 0, -60]`, снег — `[0.5, 0, -4]`.
Поворот камеры меняет видимую область и проекцию, но не вращает эти векторы.
Когда точка пересекает грань, она переводится в локальные координаты,
циклически переносится на противоположную грань и возвращается в мир.

Поэтому источник звука и положение частицы должны храниться в мировых
координатах. У дождя хвостом экранной полосы становится предыдущая мировая
позиция; у снега остаётся квадрат в текущей позиции. Scalar вычисляется из
projection и реального viewport каждого кадра, поэтому отдельная настройка
размера не нужна.

Дождевой loop следует жизненному циклу состояния:

| Событие | Действие audio backend |
| --- | --- |
| `StartLoop` | открыть объявленный sample и начать пространственный loop |
| `SetLoopVolume` | сохранить loop и применить новую интенсивность как громкость |
| `StopLoop` | остановить текущий loop |
| `OneShot` | создать отдельный источник и воспроизвести sample молнии один раз |

Интенсивность между ключами `sky.ske` интерполируется, поэтому `SetLoopVolume`
может приходить на каждом кадре. Имя из расписания сохраняется. Если указано
только `atm_rain1.wav`, архив остаётся пустым и audio owner использует
библиотеку миссии; запись `archive/name` задаёт архив явно. Ресурс загружается
лениво и кэшируется после проверки, чтобы не читать все возможные погодные
звуки при запуске миссии.

Молния использует отдельный таймер. Для интенсивности `I` и случайного `U` из
15-битного диапазона задержка имеет вид

```text
delay_ms = round_even((1 - min(I, 0.95)) * 60000 * U)
```

После срока выбираются мировые X и Y из `LightningBounds`, а Z копируется из
границ. Затем объект ждёт 6000 миллисекунд перед новой попыткой. Визуальный
контракт передаёт renderer-у material и numeric body opcode 3; native
descriptor `[40, 40, 600]` начинается на `sampled_z + 300`. При нулевом
локальном смещении его концы находятся на `sampled_z` и `sampled_z + 600`.
Opcode 1 в это же время отдельно обновляет point light; он не задаёт размеры
или UV quad. Звуковой `OneShot` использует ту же позицию, а его opcode 2
параметры `min_distance=100`, `max_distance=1500`, `frequency_ratio=1`
проходят в spatial source. Renderer и audio backend применяют numeric FX
поля и lifetime из заголовка эффекта, а CPU не подменяет их собственной
шириной или fade-кривой.

Подробные поля `EnvironmentFrame`, правила wrap и границы CPU-модуля собраны
в [справочнике эффектов окружения](../reference/environment-effects.md).

### Ambient variations и переход день/ночь

`ambient_music_loop` запускает `THEME` сразу после открытия миссии. Вариации
не выбираются последовательным счётчиком: audio owner получает `dt_seconds`
как приращение времени кадра и после строгого условия `elapsed > delay`
выбирает один sample.
Первый положительный tick поэтому запускает первую вариацию, а задержка между
следующими попытками равна `10 + rand() % 10` секунд.

В `ambient_music_variation` поддерживаются три независимых пула:

| Пул | Ключи | Когда выбирается |
| --- | --- | --- |
| default | `DEFAULT_VARIATION1..n` | когда отсутствуют оба пула `DAY` и `NIGHT` |
| day | `DAY_VARIATION1..n` | длина базового RGB активного небесного объекта больше `1.1` |
| night | `NIGHT_VARIATION1..n` | длина базового RGB активного небесного объекта не больше `1.1` |

Базовый RGB передаётся до camera-dependent glare и берётся у первого активного
небесного объекта. Если существует хотя бы один day/night пул, выбранный
пустой пул остаётся пустым: он не заменяется default или противоположным пулом.
`LIBRARY` у `ambient_music_variation` может отличаться от библиотеки theme;
если поле отсутствует, используется библиотека loop.

Индекс выбирается двумя 16-битными состояниями Iron3D:

```text
a = (a << 1) xor b
b = (b >> 1) xor a
index = b % pool_length
```

При длине пула больше одного предыдущий индекс отбрасывается одной или более
повторными выборками. Последний индекс сохраняется при переходе между day и
night; для пустого пула sample не создаётся, но следующий таймер продолжает
работать. При пустом пуле native сбрасывает индекс в `-1`. Пауза окна сохраняет
логическое состояние таймера и индекса, поэтому
возобновление не перескакивает на случайную вариацию.

Публичные функции Ngi32:

```text
niCreate3DSound
niGet3DSound
niGet3DSoundCaps
niMuteSound
```

Backend динамически вызывает `DirectSoundEnumerateA` и `DirectSoundCreate`;
параметр `DisableDSound` может полностью отключить этот путь.

### Устройство и capabilities

Конфигурация учитывает `3D Sound`, качество, reverse sound, частоту buffer,
режим постоянного воспроизведения и автоматический выбор лучшего устройства.
Эти значения преобразуются во внутренний capability/profile object до создания
sources.

Код содержит отдельный no-device state и строку `3D Sound was not initialized`.
Отсутствие 3D sound обрабатывается отдельно от ошибок simulation/resources.
Новый runtime не должен позволять отсутствию звука разрушать simulation и
обязан возвращать звуковым командам явный no-device result.

Общий sound object разделяется между подсистемами и использует счётчик
владельцев. Закрывать DirectSound следует после остановки всех sources и
atmosphere/FX managers.

### Sound resources и SWAV

Основная библиотека называется `sounds.lib`; `mission.cfg` также создаёт
именованные sound resources и variations. Legacy API `rsLoadWave` загружает
waveform из archive. Импорт `MSACM32` подтверждает путь преобразования сжатых
wave-данных в формат playback buffer.

Resource identity состоит из library и name. Один sound asset может иметь
несколько runtime sources с различными position, volume, pitch/flags и временем
запуска. Поэтому кэшировать следует decoded sample/buffer, а source object
создавать на событие.

FX opcode 2 хранит `archive[32] + name[32]` и обычно создаёт sound command.
Atmosphere использует отдельные loop/variation sources, например rain
background. Миссионный слой содержит voice events для завершения или провала
задания.

Проверенный SWAV-корпус:

```text
Часть 1: 399 — 306 MS ADPCM, 93 PCM
Часть 2: 540 — 446 MS ADPCM, 93 PCM, 1 empty entry
```

Все непустые записи имеют RIFF/WAVE framing и частоту 22 050 Hz. В Части 2
entry `ALIEN_ME.WAV` имеет размер 0. Это присутствующий archive key без
decodable waveform.

Sound loader должен различать:

- `entry_missing`;
- `entry_empty`;
- `wave_invalid`;
- `decoded_sample`.

Нулевой payload не передаётся RIFF parser-у и не должен приводить к чтению
header за границей.

### 3D listener и sources

Перед world traversal `stdRenderGame` обновляет listener из camera transform.
Listener содержит position, orientation и, при наличии, velocity. Source
содержит world position и параметры затухания. Spatialization выполняется
backend-ом либо совместимой программной моделью.

```text
camera transform
  -> listener position/front/up
object or effect transform
  -> source position
sample + source parameters
  -> DirectSound 3D buffer
```

Прямо подтверждено обновление listener в начале `stdRenderGame`, до world
traversal. Sound events могут создаваться и в calculation/FX path, поэтому
нельзя утверждать, что listener предшествует созданию каждого source. Важно,
что spatial backend получает camera state текущего отображаемого кадра до
завершения его обработки. Перенос listener update после world render создаст
как минимум однокадровое рассогласование presentation.

### Громкость, mute и CD-аудио

`iron3d.dll` применяет отдельные настройки эффектов и CD sound. Параметр
`FORCE_CD_SOUND` меняет политику выбора музыкального источника. `niMuteSound`
должен временно остановить вывод без разрушения sample cache и logical playback
state.

В новой реализации полезно разделить buses: master, effects, ambient, voice и
music/CD. Это проектное решение совместимого backend-а, а не доказанный layout
оригинального mixer-а. Оно позволяет применять старые коэффициенты, не
переписывая individual source volume.

### Граница service layer

`Ngi32.dll` с DirectSound/backend code не изменилась между Частями 1 и 2, но
`services.dll` пересобрана и уменьшилась на 4 096 байт. Поэтому low-level
decoder/device path подтверждается одной машинной реализацией, а service
lifecycle, GUI/audio wiring и defaults требуют раздельной трассировки обеих
частей.

## Сетевая подсистема

Net инкапсулирует DirectPlay4A и lobby/service-provider API. World3D строит над
транспортом player identity, mirror objects и игровые сообщения. Эти уровни
следует разделять: DirectPlay отвечает за доставку bytes между players,
World3D -- за смысл сообщения и владение объектом.

Application GUID:

```text
{3C1D1F01-A870-11D1-8400-000021B14415}
```

Он передаётся network instance и service layer. Экземпляры с другим GUID не
принадлежат одному логическому приложению.

### Lifecycle соединения

Публичные функции Net покрывают полный цикл:

```text
CreateNetworkInstance
  -> select/use service provider
  -> setup connection
  -> enumerate or create session
  -> join/create session
  -> create local player
  -> send/receive messages and player data
  -> destroy player
  -> close session
  -> close connection
```

Поддерживаются providers эпохи DirectPlay: TCP/IP, IPX и modem/lobby варианты,
если они установлены в системе. Функции явно проверяют, что DirectPlay enabled
до enumeration, session и player operations. Неверный порядок вызовов должен
возвращать понятную ошибку, а не разыменовывать пустой interface.

### Sessions, players и адреса

Net предоставляет enumeration service providers и sessions, выбор host/join,
player name/password/data, latency, максимальный размер сообщения, размер
очереди, server player info и provider address. Lobby launch обрабатывается
отдельной веткой.

Внутренняя модель должна хранить как минимум:

```c
struct NetPlayer {
    TransportPlayerId transport_id;
    uint16_t game_player_number;
    string name;
    RawBytes player_data;
    bool is_local;
    bool is_host;
};
```

Transport ID нельзя использовать как постоянный `ObjectId`. NetWatcher связывает
временный DirectPlay identifier с номером игрока и World3D entities.

### Игровые сообщения World3D

Подтверждённые имена message surface:

```text
GMSG_CREATE_REMOTE_PLAYER
GMSG_APPEND_RESOURCE
GMSG_CHANGE_OBJECT_OWNER
GMSG_SET_PLAYER_DATA
GMSG_MISSION_DATA_PATH
GMSG_TAKE_OBJECT
GMSG_TEXT_FOR_PLAYER
GMSG_SYNC_STATE
GMSG_CREATE_MIRROR
GMSG_PAUSE_REMOTE_PLAYER
GMSG_CONFIRM_PLAYER_DATA
GMSG_KILL_PLAYER
SYSMSG_SET_TIME
SYSMSG_SET_PLAYER_NUMBER
GMSG_END_MESSAGE_SEQ
GMSG_REMOVE_RESOURCE
```

`GMSG_COLLISION_DETECTED` относится к общей очереди, но не обязательно
передаётся по сети. Message ID, payload size и delivery policy должны быть
частью явной schema. Нельзя сериализовать C++ pointers или native padding.

### Mirror objects и ownership

Удалённо принадлежащий объект представлен local mirror instance. Он участвует в
рендере и spatial queries, но authority над его созданием, ключевыми properties
и удалением находится у owner player. Сообщение смены владельца обновляет эту
границу; оно не должно создавать второй объект с тем же ID.

Типовой путь:

```text
remote create message
  -> validate player and ObjectId
  -> resolve prototype/resources
  -> CreateMirrorObject
  -> apply initial state
  -> AddMirrorObjectToGame
  -> subsequent sync messages update mirror
```

При потере player NetWatcher инициирует предписанное удаление или transfer
ownership через World3D queue. Мгновенное освобождение во время receive callback
запрещено по тем же причинам, что и в calculation pass.

### Сжатие и wire compatibility

`netZipData` и `netUnZipData` образуют встроенный слой упаковки payload. Он
находится выше транспорта: переход с DirectPlay на UDP/ENet не отменяет
необходимость воспроизводить формат упакованного сообщения, если требуется
соединение с оригинальной игрой.

Полный wire schema, framing и алгоритм сжатия пока не доказаны packet
capture-ом. Поэтому нужны два режима:

- **native compatibility** -- отдельный adapter, реализуемый после трассировки
  оригинальных packets;
- **modern multiplayer** -- новая versioned protocol schema, использующая ту же
  game-message семантику, но не заявляющая совместимость с DirectPlay client.

Эти режимы нельзя незаметно смешивать. До доказательства native wire
compatibility современный transport должен быть versioned и отделён от слоя,
который претендует на совместимость с оригинальным клиентом.

### Стабильность сетевого слоя

`Net.dll` и `World3D.dll` побайтно идентичны в обеих частях. Application GUID,
DirectPlay wrapper, mirror-object API и World3D message surface относятся к
одной машинной реализации.

Это подтверждает отсутствие отдельной сетевой реализации для Части 2, но не
закрывает wire schema: без packet/send-receive capture по-прежнему неизвестны
точное framing, reliability flags, payload layouts и алгоритм `netZipData` для
native interoperability.

Для binary regression достаточно одного профиля неизменённых DLL, но message
captures должны включать контент обеих частей, потому что prototype/resource IDs
и mission data различаются.

## Контракты реализации

Совместимая реализация должна фиксировать не только результат, но и момент его
появления в кадре. Для Behavior, Control, input, sound и network особенно важны
tick boundaries: одна и та же команда, применённая на один tick раньше или
позже, меняет дальнейшую симуляцию.

### Trace-события

Минимальный trace для этого тома:

- input snapshot: edge events, held state, analog values;
- camera state: mode, target, angles, matrices, viewport;
- Behavior: target, areal, global path revision, local corridor;
- Wizard: requested vector, constraints, wizard path;
- Control: candidate transform, contacts, correction, final transform;
- World3D queue: message name, ObjectId, dispatch phase, deferred deletion;
- sound: sample key, source owner, position, event tick, listener state;
- network: player mapping, message ID, payload length, delivery policy.

Для рендера это связывается с [render frame](../reference/render-frame.md):
camera и listener должны попадать в trace до world traversal, иначе нельзя
отделить ошибку presentation от ошибки управления.

### Проверки Behavior и сценариев

- script version mismatch даёт отдельную ошибку;
- event table читается lossless;
- VM body сохраняется без потери неизвестных bytes;
- отсутствующий `IArealMap` не замалчивается;
- non-walkable/non-reachable states дают diagnostic condition;
- одинаковый input log воспроизводит одинаковый sequence Behavior commands;
- resource names из TRF разрешаются через общий registry.

### Проверки Control

- движение без препятствий;
- slope/terrain-following;
- симметричные pair-collision tests с переставленными IDs;
- contact event отправляется один раз в предписанной фазе;
- удаление объекта в collision callback безопасно;
- replay одинакового input log даёт одинаковые transforms;
- collision proxy перестраивается после смены component/model state.

### Проверки input и камеры

- edge event не повторяется как held state;
- mouse/joystick axis сбрасывается по правилам snapshot;
- hot-unplug joystick не оставляет старое отклонение;
- camera horizontal angle wraps, vertical angle clamps;
- center command использует подтверждённое время, а не render FPS;
- Terrain и sound получают одну и ту же camera frame.

### Проверки звука

- backend может отсутствовать без нарушения simulation;
- один decoded sample переиспользуется несколькими sources;
- `entry_missing`, `entry_empty` и `wave_invalid` различаются;
- listener совпадает с camera frame;
- loop source корректно переживает pause/resume;
- mute не сбрасывает position и time;
- missing sound resource содержит полную диагностическую цепочку;
- deterministic test сравнивает список sound events, а не waveform устройства.

### Проверки сети

- нельзя создавать queue с активной сетью и нулевым player ID;
- session/player operations до enable/setup возвращают ошибку;
- сообщения проверяют длину до чтения payload;
- sequence/end markers обрабатываются в стабильном порядке;
- duplicate create mirror не создаёт второй instance;
- ownership change атомарно обновляет routing;
- pause/time messages применяются в одной simulation boundary;
- resource transfer имеет timeout `Network_ResourceTransferMaxDelay`;
- disconnect не оставляет objects с несуществующим owner;
- replay записанного message log даёт одинаковое World3D state.

`resnet.log` и `NetWatch.log` следует поддерживать как отдельные каналы: первый
относится к transport/resource exchange, второй -- к связи players и game
objects.

## Границы знания

Подтверждены внешние interfaces, часть runtime order, значимые строки,
конфигурационные параметры, corpus-level counts и стабильность ряда DLL между
двумя частями. Открытыми остаются:

- instruction grammar `.scr` и semantics всех VM opcodes;
- точная семантика всех TRF-записей;
- полный layout CTLD shape records;
- contact solver и порядок всех correction steps;
- class layout камер, контроллеров, sound service и network watcher;
- DirectPlay wire framing, reliability flags и payload schema;
- алгоритм `netZipData`/`netUnZipData`;
- точные defaults service layer там, где DLL пересобраны.

Эти границы должны оставаться видимыми в документации и тестах. Если новая
реализация вводит удобный современный abstraction layer, он обязан быть
отделён от утверждений о native compatibility и покрыт отдельным trace.
